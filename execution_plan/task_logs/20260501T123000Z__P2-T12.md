# P2-T12 — Admin approval flow + non-approved-user lock-out screens

## Preconditions

- P2-T3 (Identity model + roles + approval state + Phase A tester ceiling) is in `completed_tasks`.
- P2-T5 (Admin step-up re-authentication helper + audit chain) provides the `IAuditEventRepository` for audit logging.
- P2-T11 (Admin `sys_config` management UI with audit chain) established the admin config page pattern that this task follows.
- The `UserDocument`, `UserRole`, `UserApprovalState`, `UserApprovalService`, and `IUserRepository` already support the approval lifecycle (pending_approval → approved → deactivated).
- Test-only approve/deactivate endpoints exist at `/api/v1/auth/test/users/` but no production admin user management endpoints existed prior to this task.

## REQ Coverage Attempted

- REQ-ROLE-004 — approval state for users (pending_approval, approved, deactivated)
- REQ-SESSION-012 — unapproved users see approval-pending screen
- REQ-SESSION-013 — deactivated users see deactivation screen

## Actions Taken

### 1. Repository layer — added list and count methods

- **`IUserRepository.cs`**: Added `ListUsersAsync(string? statusFilter)` and `CountPendingAsync()` to the interface.
- **`MongoUserRepository.cs`**: Implemented both — `ListUsersAsync` returns all users sorted by `createdAt` descending with optional status filter; `CountPendingAsync` counts users with `status = "pending_approval"`.
- **`InMemoryUserRepository.cs`**: Added matching implementations for the test double.

### 2. Admin API endpoints — `AdminUserEndpoints.cs` (new)

Created `apps/api/Admin/AdminUserEndpoints.cs` with four endpoints following the same pattern as `AdminConfigEndpoints.cs`:

- **`GET /api/v1/admin/users`** — lists all users with optional `?status=` filter. Admin-role-gated.
- **`GET /api/v1/admin/users/pending/count`** — returns the count of pending-approval users. Used by the frontend nav badge.
- **`POST /api/v1/admin/users/{userId}/approve`** — transitions a user from pending_approval → approved via `UserApprovalService` (ceiling-enforced in Phase A). Writes a `user_approved` audit event on success. Returns 422 if the tester ceiling is reached.
- **`POST /api/v1/admin/users/{userId}/deactivate`** — transitions any user to deactivated. Writes a `user_deactivated` audit event.

### 3. Program.cs registration

Added `app.MapAdminUserEndpoints()` call alongside the existing `MapAdminConfigEndpoints()`.

### 4. Admin approvals frontend — `admin/approvals/page.tsx` (new)

Created the admin user approvals page with:
- Status tab filters: All / Pending / Approved / Deactivated
- User table showing status (Pill), email, display name, provider, role, sign-up date
- Approve button for pending users, Deactivate button for approved users (non-admin)
- Confirmation dialog before each action with notification feedback
- Live pending-approval count fetched from the API on refresh
- Dynamic nav badge using new `adminNavItemsWithApprovals(count)` helper

### 5. Deactivated user page — `deactivated/page.tsx` (new)

Dedicated lock-out screen for deactivated users:
- Verifies the user's session actually returns `deactivated` status before rendering
- Shows a clear "Account deactivated" message with sign-out affordance
- Redirects to login if the user is not actually deactivated

### 6. Auth callback routing update

Changed `auth/callback/page.tsx` to route `"deactivated"` state to `/deactivated` instead of `/login?error=account_deactivated`.

### 7. Pending-approval page — polling added

Updated `pending-approval/page.tsx` to a client component that:
- Polls `fetchSessionStatus()` every 30 seconds
- Automatically redirects to the appropriate screen (`/fyers-required`, `/`, `/deactivated`, etc.) when the status changes
- Shows a "Last checked" timestamp

### 8. Nav badge helper

Added `adminNavItemsWithApprovals(count)` to `primitives.tsx` so admin pages can render the dynamic pending-approval count in the sidebar badge.

### 9. Code comment update

Added REQ-SESSION-013 reference comment to the deactivated state check in `AuthEndpoints.cs` `/session/status` handler.
