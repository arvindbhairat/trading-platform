# HDS/FYERS 500 Bug Fix

**Date:** 2026-06-10
**Incident:** HDS (HistoricDataSeed) failing with HTTP 500 InternalServerError for all 504 symbols

## Timeline

1. **2026-06-09T23:17-23:33** — First EODSR run: OHLCV data missing from PostgreSQL for all 504 symbols. EODSR marked as `failed_for_review`.
2. **2026-06-09T23:38** — Second EODSR run triggered after DS completed for session. Same: all 504 symbols fail.
3. **2026-06-10T01:03:52** — HDS job triggered by admin (`6a27e2f3fd001aa3b3176cd5`).
4. **2026-06-10T01:04:01** — HDS starts seeding. First symbol (360ONE) immediately fails with `HTTP 500 (ERROR)`. All subsequent symbols fail identically.

## Root Cause Analysis

### Bug 1: Incorrect `date_format` parameter

The code sent `date_format = "1"` with dates formatted as `"yyyyMMdd"` (e.g., `"20260610"`).

Per the [FYERS API v3 documentation](https://myapi.fyers.in/static/media/v3.0ce77080e168cb8039ed.yaml):
- `date_format = 0` → epoch timestamp
- `date_format = 1` → `yyyy-MM-dd` format (with hyphens)

Our code sent date `"20260610"` (no hyphens) with `date_format = "1"`, but FYERS expects `"2026-06-10"` (with hyphens). This mismatch causes the FYERS server to return HTTP 500.

**Fix:** Changed to `date_format = "0"` with epoch timestamps (Unix seconds), which is the standard approach used in FYERS sample code.

### Bug 2: 10-year range exceeded 366-day per-request limit

The FYERS API enforces a **366-day limit per request** for daily ("D") resolution. The HDS job requests 10 years (~3652 days) of data in a single call.

**Fix:** Added pagination — splits the date range into chunks of max 365 days, each chunk making a separate throttled API call.

### Bug 3: Wrong Authorization header format

FYERS v3 requires `Authorization: AppID:{access_token}` format (e.g., `Authorization: XC4XXXXM-100:eyJ0...`), **not** Bearer token.

The old code used `AuthenticationHeaderValue("Bearer", token)` which FYERS rejects.

**Fix:** Construct header as `new AuthenticationHeaderValue(_appId, $":{token}")`. The `_appId` is read from `FYERS_APP_ID` env var / `integrations:fyers:app_id` config and injected via DI. `FyersMarketDataProviderExtensions.cs` now fails fast if AppID is missing.

### Bug 4: Missing API request/response logging

When API calls failed, the only output was "Non-retryable HTTP error" — no request parameters, no response body — making debugging impossible.

**Fix:** Added `SendAndParseAsync` helper that serializes the request body, reads the response body as string, and logs both in full on any error (HTTP error, non-ok status, parse failure).

## Secondary Issue: sys_config DuplicateKey Error

A non-fatal `DuplicateKey` error occurs in `SharedTokenHealthService.PersistHealthyStateAsync`:
```
E11000 duplicate key error collection: signalstack.sys_config index: key_1 dup key: { key: null }
```

The `sys_config` collection has a unique index on the `key` field, but `PersistHealthyStateAsync` uses `_id` as the identifier and doesn't set the `key` field on new documents. When `IsUpsert = true` creates a new document, `key` defaults to `null`, violating the unique constraint.

**Impact:** Warning-level log noise only. The in-memory state transitions correctly.
