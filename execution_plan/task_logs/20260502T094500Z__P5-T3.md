## Actions Taken

1. **Created `apps/api/Notifications/NotificationType.cs`** — Static class with `const string` identifiers for all 15 user-facing notification types (REQ-NOTIFY-006) and 19 admin-only operational types (REQ-NOTIFY-006a). Includes `UserFacing` and `AdminOnly` hash sets for validation.

2. **Created `apps/api/Notifications/DeliveryStatus.cs`** — Constants for Telegram (`pending`, `delivered`, `failed`) and email (`pending`, `delivered`, `failed`, `not_attempted`) delivery status tracking.

3. **Created `apps/api/Notifications/NotificationDocument.cs`** — MongoDB document model for the `notifications` collection. Fields:
   - Identity: `Id`, `UserId`, `NotificationType`, `SignalTypeName`, `Timeframe`, `Symbol`
   - Content: `Content` (user-facing text), `DeepLink`
   - Temporal: `GeneratedAt`, `IsRead`
   - Telegram delivery (REQ-NOTIFY-005): `TelegramBotId`, `TelegramDeliveryStatus`, `TelegramDeliveryAttempts`, `LastTelegramAttemptAt`, `TelegramMessageId` (REQ-NOTIFY-023)
   - Email delivery (REQ-NOTIFY-021): `EmailDeliveryStatus`, `EmailAttempts`, `LastEmailAttemptAt`
   - Routing: `IsAdminNotification` (REQ-NOTIFY-006a), `ErrorDetails`

4. **Created `apps/api/Notifications/INotificationRepository.cs`** — Repository interface: `InsertAsync`, `InsertManyAsync`, `GetByUserIdAsync`, `GetAdminNotificationsAsync`, `MarkAsReadAsync`, `CountUnreadByUserAsync`, `CountUnreadAdminAsync`.

5. **Created `apps/api/Notifications/MongoNotificationRepository.cs`** — MongoDB implementation using `IMongoCollection<NotificationDocument>` against the `notifications` collection.

6. **Created `apps/api/Notifications/INotificationWriter.cs`** — High-level writer interface used by all producers (EODSR, LMDS, RME). REQ-NOTIFY-007: producers write to notifications collection; no Telegram dispatch here.

7. **Created `apps/api/Notifications/NotificationWriter.cs`** — Default implementation validating notification types against `NotificationType.All` before persisting.

8. **Created `apps/api/Notifications/NotificationExtensions.cs`** — DI registration: `services.AddNotificationServices()` registers `INotificationRepository`, `INotificationWriter`.

9. **Created `tests/api/SignalStack.Api.Tests/InMemoryNotificationRepository.cs`** — In-memory repository for unit tests.

10. **Created `tests/api/SignalStack.Api.Tests/NotificationWriterTests.cs`** — 15 xUnit tests covering:
    - **EODSR path:** entry_signal single write, batch write of 5 signals (REQ-NOTIFY-006)
    - **LMDS path:** exit_alert, gap_risk_alert, circuit_limit_alert, market_halt_active/cleared
    - **RME path:** portfolio_impact_insight, drawdown_mode_alert, portfolio_heat_warning, pending_entry_superseded, pending_entry_expired
    - **Schema validation:** invalid type rejected, invalid type in batch rejected
    - **Admin routing:** admin notification excluded from user feed
    - **All types accepted:** every user-facing type in REQ-NOTIFY-006 is written and verified

11. **Modified `apps/api/Program.cs`** — Added `using SignalStack.Api.Notifications` and `builder.Services.AddNotificationServices()` after backtesting registration.

12. **Modified `apps/worker/Program.cs`** — Added `using SignalStack.Api.Notifications` and `builder.Services.AddNotificationServices()` before EODSR registration.

### REQ-ID verification

- **REQ-NOTIFY-006**: All 15 user-facing notification types are defined as constants in `NotificationType.cs` (`UserFacing` set). Every type is accepted by the writer's type validation and tests prove each can be written. See `NotificationWriterTests.All_user_facing_notification_types_are_accepted_by_schema`.

- **REQ-NOTIFY-005**: `NotificationDocument` carries all required fields: `UserId`, `NotificationType`, `SignalTypeName`, `Timeframe`, `Symbol`, `Content`, `GeneratedAt`, `TelegramBotId`, `TelegramDeliveryStatus`, `TelegramDeliveryAttempts`, `LastTelegramAttemptAt`. The `TelegramMessageId` field supports REQ-NOTIFY-023 idempotent delivery.

- **REQ-NOTIFY-006a**: 19 admin-only notification types are defined in `NotificationType.cs` (`AdminOnly` set). The `IsAdminNotification` flag on `NotificationDocument` distinguishes admin from user records. `GetAdminNotificationsAsync` and `GetByUserIdAsync` on the repository enforce the routing boundary. Admin type constants are defined ahead of the admin-notification wiring tasks (P5-T4, P5-T14).
