## Actions Taken

1. **Added single-symbol mode** to `BacktestOptions.Symbols` filter and `BacktestEngine` so the optimisation engine can run per-symbol backtests.

2. **Implemented REQ-SLO-007 concurrency cap** (`BacktestConcurrencySemaphore`): SemaphoreSlim-based platform-wide cap of 5, per-user tracking with `ConcurrentDictionary`, queue position tracking for portal visibility. Shared by regular backtests and optimisation runs (U-9).

3. **Created strongly-typed `RmeProfile` model** replacing the freeform JSON/BsonDocument approach. Holds sizing model, stop loss type, trailing stop params, timeframe, and multi-timeframe combo. Includes `ToJsonString()` for backward compatibility with `RmeConfigurationJson`.

4. **Created `ProfileOptimisationGrid`** with developer-defined dimensions for sizing models, stop loss types, timeframes, risk percentages, ATR multipliers, and multi-timeframe combinations. `GenerateAll()` produces the full cartesian grid.

5. **Built `ProfileOptimisationEngine`** — the core engine that:
   - Prevents duplicate active runs per subscription + symbol
   - Validates subscription state, evaluator, and symbol data availability
   - Iterates each profile config from the grid, running single-symbol backtests
   - Computes **Composite Score** (REQ-RME-020a): normalises CAGR, Sharpe, Expectancy, Profit Factor across configs; computes Stability Score, Regime Consistency Score, Capital Efficiency, Trade Quality Score; applies Drawdown Penalty
   - Computes **Robustness Factor** (REQ-RME-020b): Parameter Sensitivity Score (variance across neighbour grid points), Cross-Symbol Consistency Score (defaults to 1.0 for single-symbol), Walk-Forward Stability Score (in-sample vs out-of-sample correlation)
   - Handles **multi-timeframe evaluation** (REQ-RME-020c) via timeframe as a grid dimension and multi-timeframe combos
   - Stores ranked results and marks low-confidence configs

6. **Created MongoDB storage** for optimisation results:
   - `OptimisationResultDocument` — stores per-symbol, per-subscription results with full scoring breakdown
   - `MongoOptimisationResultRepository` — CRUD with indexes for fast lookups
   - Collection: `optimisation_results`

7. **Implemented REQ-RME-021 staleness check** (O-6): read-time `is_stale` computed from (a) newer candle data in SQL Server, (b) changed signal subscription version, (c) code version changes.

8. **Created API endpoints** under `POST/GET /api/v1/backtest/optimise/*`:
   - `POST /optimise/{subscriptionId}/{symbol}` — trigger run (concurrency-gated)
   - `GET /optimise/runs` — list user's runs
   - `GET /optimise/runs/{runId}` — get full results with staleness
   - `GET /optimise/latest/{subscriptionId}/{symbol}` — get latest with staleness

9. **Wired DI** in `BacktestExtensions` — registered `BacktestConcurrencySemaphore`, `ProfileOptimisationEngine`, `MongoOptimisationResultRepository`.

10. **Mapped endpoints** in `MapBacktestingEndpoints()` extension.
