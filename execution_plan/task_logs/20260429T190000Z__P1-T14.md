## Conflict found

**Canonical doc:** `execution_plan/milestones.md` § v0.2  
**Conflicting doc:** `execution_plan/execution_plan.md` P2-T4

**Description:**

`milestones.md` v0.2 acceptance criterion states:

> "BCP / backup configuration is provisioned and verifiable per RPO/RTO
> (REQ-BCP-001..**009**, REQ-LEGAL-009)."

However, `execution_plan.md` P1-T10 declares only **REQ-BCP-001..008**,
and P2-T4 ("Lazy admin bootstrap + admin OAuth restricted to Google/Microsoft
+ `amr` MFA enforcement") declares **REQ-BCP-009**.

REQ-BCP-009 (from `docs/requirements-spec.md` line 207) requires the platform
to validate an MFA authentication-methods claim on every admin sign-in. This is
an **identity-layer** requirement, not a backup/infrastructure configuration
requirement. It belongs architecturally in P2 (Identity and Auth bootstrap),
which is where `execution_plan.md` correctly places it.

The milestones.md entry appears to have been authored with a shorthand range
`REQ-BCP-001..009` that inadvertently swept in REQ-BCP-009.

**Impact:** If taken literally, the v0.2 acceptance criterion cannot be met
within Phase 1 because REQ-BCP-009 has no P1 task and is not in
`phase_coverage["P1"]`. Implementing it in Phase 1 would pull in auth/identity
scope prematurely, violating the phased delivery order.

**Resolution task created:** P1-T15 — "Correct milestones.md v0.2 REQ-BCP scope."
P1-T15 will amend the milestones.md v0.2 criterion to say "REQ-BCP-001..008"
and confirm REQ-BCP-009 is documented under v0.3. Once P1-T15 completes, P1-T14
may re-run with the corrected criterion.
