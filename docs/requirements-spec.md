# Requirements Specification

## Purpose

This file is the canonical source of truth for all platform requirements. Update this file first when any business rule, product constraint, workflow, or UI behaviour changes.

## How to Read This Document

Requirements are grouped by implementing component so that all related requirements for a given service or layer are in one place. Each section carries a short scope note identifying the owning component and what the section covers.

All requirement IDs follow the format `REQ-{DOMAIN}-{NNN}` with three-digit sequential numbers. IDs are stable once assigned — when adding new requirements, use the next available number in the section's sequence.

## Part 1 — Platform Foundation

*Cross-cutting constraints that all components must respect. Implement these decisions before writing any feature code.*

### Product Boundary

*Scope guardrails. Every component must enforce these constraints — they are not optional checks.*

- `REQ-BOUNDARY-001` The platform targets NSE-listed stocks from the Nifty 500 universe only.
- `REQ-BOUNDARY-002` The platform is long-only.
- `REQ-BOUNDARY-003` The platform is for decision support, research, charting, backtesting, portfolio analytics, and notifications.
- `REQ-BOUNDARY-004` The platform must not place orders autonomously on behalf of users.
- `REQ-BOUNDARY-005` User behaviour is not constrained to the platform; users may trade directly in the broker outside this system.
- `REQ-BOUNDARY-006` All user and admin capabilities must be accessible through a unified browser-based portal.

### Regulatory Posture and Operating Phase

*Scope guardrails for the platform's regulatory positioning. These constraints define what the platform is and is not, legally. The platform is not currently registered with SEBI. Violations require phase escalation, not workarounds in code or copy. Every user-facing surface, every signal, every advisory, every disclaimer rule derives from this section.*

- `REQ-LEGAL-001` The platform operates under a defined set of operating phases that gate which commercial activities are permitted. Phase A: private validation, unregistered with SEBI, invite-only, no fees, admin's personal FYERS API application permitted as a known Phase A limitation. Phase B: pre-commercial hardening, SEBI registration workstream active, commercial FYERS API application required, still no fees. Phase C: commercial SaaS, SEBI registration granted, paid plans permitted. The current phase must be recorded in `sys_config` under the key `operations.phase.current` with allowed values `A`, `B`, or `C`. The initial seed value is `A`. Phase transitions are performed only by the admin through the admin portal and must be recorded in `audit_events` with the outgoing phase, incoming phase, timestamp, actor, and the justification entered by the admin at the time of transition.
- `REQ-LEGAL-002` Phase A imposes constraints the platform must enforce by design, not by policy: no paid subscription, billing, invoicing, or fee-collection flows anywhere in the portal or backend; no public marketing surfaces, no SEO-indexable landing pages, no open registration link — registration must require an invite token or admin pre-approval; a hard cap on approved user accounts as defined in REQ-LEGAL-003; no user-facing content that frames platform outputs as investment advice, research recommendations, buy/sell tips, or analyst opinions; and use of the admin's personal FYERS API application is permitted only as a Phase A exception. These constraints must be enforced at the service layer; bypassing them through direct database edits must be surfaced as a violation on the admin Legal Posture widget defined in REQ-LEGAL-010.
- `REQ-LEGAL-003` During Phase A, the platform must enforce a hard cap on the count of non-deactivated approved user accounts. The cap must be stored in `sys_config` under the key `operations.phase_a.tester_ceiling` with a default of 30 and a maximum allowable configured value of 50. The admin approval flow (REQ-ADMIN-001) must refuse to approve a new user when the current count of non-deactivated approved users equals or exceeds the configured value, surfacing a clear message naming the ceiling and the current count. Every change to this configuration value must be recorded in `audit_events` with the previous value, new value, actor, and the justification entered at the time of change. The cap has no enforcement effect when the current phase is B or C but remains a visible value for operational awareness.
- `REQ-LEGAL-004` Every approved user — in all phases — must accept a versioned platform user acknowledgement before gaining access to any protected feature. During Phase A, the acknowledgement must state, at minimum, that: the platform is operating in private evaluation and is not registered with SEBI or any other securities regulator; all platform outputs are tools-generated information derived from the user's own configured scans and risk profile, not investment advice; the user is the sole decision-maker and self-directs all trades; the platform operator accepts no responsibility for trading outcomes. The acknowledgement text per phase is versioned; the current version identifier must be stored in `sys_config` under the key `legal.tester_acknowledgement.current_version`. On accepting, the platform must record the acknowledgement version, user identity, and timestamp in `audit_events`. When the admin increments the acknowledgement version, every active user must re-accept on next login before the portal renders any protected page; this re-acceptance is a distinct user state per REQ-SESSION-013. The acknowledgement text content for each phase must be maintained as versioned documents alongside the Terms of Service (REQ-LEGAL-008).
- `REQ-LEGAL-005` Phase B may be entered only once all of the following conditions are recorded as satisfied in the admin portal: a registered Indian fintech lawyer has reviewed the platform's regulatory posture, ToS, privacy notice, tester acknowledgement, and user-facing content, with the review record captured in `audit_events`; a commercial FYERS API application registered in the platform's operating entity name (not the admin's personal account) is configured as the platform's FYERS integration; the SEBI registration workstream — Research Analyst registration unless an alternative classification is explicitly recorded and justified — has been formally initiated; and the full operational runbook catalog at `docs/operations/runbooks/` exists, with every catalogued runbook reviewed within the past 90 days and the review recorded in `audit_events`. Phase C may be entered only once SEBI registration is granted, the legal review has been updated to cover fee collection, billing, and public marketing, and a qualified external penetration test per REQ-SEC-010 has been completed with high- and critical-severity findings remediated. The phase transition control in the admin portal must refuse to advance the phase value until all gating conditions for the target phase are recorded as satisfied.
- `REQ-LEGAL-005a` The SEBI registration category applicable to the platform — specifically whether the platform's EOD signal output, Telegram notifications, advisory panel, and FYERS widget flow fall under the Research Analyst Regulations 2014, the Investment Adviser Regulations 2013, an algorithmic trading service registration, or none of the above — is legally unresolved and must be definitively determined before Phase B entry. A written classification opinion from a SEBI-registered fintech lawyer must be obtained that: (a) analyses each of the above platform surfaces against all applicable SEBI registration categories; (b) names the correct registration path, or explicitly confirms that no SEBI registration is required and states the legal basis for that conclusion; and (c) identifies any operational conditions the platform must satisfy before initiating the named registration workstream or operating under the chosen classification. The opinion must be stored as a versioned document in `docs/legal/` and its receipt recorded in `audit_events` with the document reference, lawyer name and SEBI registration number, and date received. Until the opinion is received and the `audit_events` record exists, the Phase B transition control must treat this gate as unsatisfied and block the transition with a message identifying this specific unresolved condition. The "SEBI registration workstream" gating condition in REQ-LEGAL-005 is satisfied only by initiating the workstream for the category named in the opinion obtained under this requirement; initiating an RA workstream before the opinion is received does not satisfy the condition if the opinion subsequently identifies a different classification.
- `REQ-LEGAL-006` All user-facing surfaces must use self-directed language that attributes the decision to the user rather than to the platform. User-facing surface for the purposes of this requirement means: Telegram notification content, portal notification feed entries, dashboard labels and helper text, chart-page advisory panel, order confirmation modal, onboarding screens, marketing copy, and any user-visible tooltip, empty state, or confirmation message. User-facing content must frame outputs as matches against the user's own configured criteria — for example, "your scan matched X," "your configured entry is Y," "your stop per your risk profile is Z," "this symbol met the criteria you set in your subscription." User-facing content must not use verbs that attribute a recommendation to the platform, including "buy," "sell," "recommended," "suggested pick," "top pick," "advised," "signal to buy," "signal to sell," or any equivalent phrasing. Internal persistence, internal logs, database field names, code identifiers, API schema, and canonical terminology (Signal, entry signal, advisory, RME) are unaffected by this requirement and must continue to follow `docs/terminology.md`; the constraint applies only to text that reaches a user's eyes. Every UI component, notification template, and marketing asset must pass a documented user-facing-language review before release; the review checklist must be stored alongside the component in source control.
- `REQ-LEGAL-007` A short-form disclaimer must appear on every surface where the platform delivers actionable content to a user: as a footer line on every Telegram notification (including entry signals, exit alerts, and all advisory types); as a persistent footer strip on the portal dashboard; as an inline strip within the chart-page RME advisory panel; and as a prominent strip above the confirm button on the Phase 1 order confirmation modal. The short-form text and the URL to the long-form disclaimer must be stored in `sys_config` under the keys `legal.disclaimer.short_text` and `legal.disclaimer.long_url`. A versioned long-form disclaimer document, together with the current Terms of Service and Privacy Policy, must be reachable from a persistent footer link on every page of the portal. Any change to the short-form disclaimer text or the long-form document version must be recorded in `audit_events`. When the long-form disclaimer version is bumped, user re-acceptance of the tester acknowledgement (REQ-LEGAL-004) is required on next login.
- `REQ-LEGAL-008` The platform's Terms of Service and Privacy Policy must exist as versioned documents, served from the portal at stable URLs, and linked from a persistent footer on every page. On signup, a new user must accept the ToS and the Privacy Policy as two distinct affirmative checkboxes — not a single combined checkbox — and must accept the tester acknowledgement (REQ-LEGAL-004) as a third distinct affirmative action; each acceptance must be recorded in `audit_events` with document version, user identity, and timestamp. When the ToS or Privacy Policy version is bumped, every active user must re-accept the affected document on next login before the portal renders any protected page. Acceptance history must be retained indefinitely, subject only to DPDP erasure obligations (REQ-PRIVACY-004) which must preserve the fact and version of acceptance while redacting personal identifiers as permitted.
- `REQ-LEGAL-009` All user personal data, trade data, notification content, portfolio snapshots, and audit records must be stored in Azure India regions (Central India or South India). This includes MongoDB Atlas clusters or self-managed MongoDB deployments, SQL Server instances for both market data and backtest databases, Azure Key Vault, Azure App Configuration, Redis, and any observability vendor or collector that receives telemetry payloads containing user identifiers or personal data. Secondary and geo-redundant backups must also remain within India. Third-party providers whose processing occurs outside India (for example, market data providers whose APIs are hosted abroad, or Telegram's global infrastructure for notification delivery) are permitted as data processors when the processing purpose is necessary for platform function and is disclosed in the Privacy Policy; cross-border transfers must be documented in the record of processing activities required by REQ-PRIVACY-010. This residency requirement applies in all phases and must not be relaxed for Phase A performance or cost reasons.
- `REQ-LEGAL-010` The admin portal must display a persistent Legal Posture widget on the admin home page. The widget must show: current operating phase (A, B, or C); current count of approved non-deactivated users and the Phase A tester ceiling; whether the configured FYERS API application is the admin's personal registration or a commercial registration; the current ToS version, Privacy Policy version, long-form disclaimer version, and tester acknowledgement version; whether the SEBI classification opinion required by REQ-LEGAL-005a has been received and recorded in `audit_events` (displayed as a distinct gate item with the received date when present, or as an unresolved blocker when absent); whether the legal-review record required for the next phase transition (REQ-LEGAL-005) has been captured; calendar coverage status — the count of unconfirmed weekdays in the next 30 days per REQ-CALENDAR-007, shown as a warning when non-zero and as a phase-transition blocker; and runbook catalog completeness — how many catalogued runbooks exist versus are missing, and how many have been reviewed within the past 90 days. The widget must render in a warning state when any Phase A constraint is at risk — specifically when the approved user count is within 10% of the configured ceiling, when the legal-review record required for the next phase is missing and the admin has begun the phase-transition flow, when a personal FYERS app is still configured and the admin has begun the transition to Phase B, or when any Phase-A-mandatory runbook (DataSync failure recovery, admin FYERS token re-auth, data-breach response) is missing or has not been reviewed in the past 90 days. Clicking any field must navigate to the relevant admin detail view.

### Personas and Roles

*Implemented by the identity and access layer. Defines the two supported personas and their access model.*

- `REQ-ROLE-001` The platform supports normal users and exactly one admin user.
- `REQ-ROLE-002` The admin is also a normal user and uses the same unified portal as all other users.
- `REQ-ROLE-003` The admin receives an additional privileged admin menu inside the same portal.
- `REQ-ROLE-004` New users remain blocked from protected platform features until approved by the admin.
- `REQ-ROLE-005` The first admin account is bootstrapped from a seeded environment-configured email (`SEED_ADMIN_EMAIL`). No admin user record is pre-seeded at database initialisation time; the admin user record is created **lazily on the admin's first successful OAuth sign-in** — at that moment, if the authenticated user's email matches `SEED_ADMIN_EMAIL`, the API must create the user record and assign the admin role in the same transaction. Until that first sign-in occurs the admin approval queue is empty by construction (REQ-ROLE-004 blocks all protected features, so non-admin users cannot generate approval requests before an admin exists), which eliminates the need for a placeholder admin row and dissolves any apparent circularity between `sys_config` seeding (REQ-CONFIG-010, REQ-CONFIG-011) and admin identity. `SEED_ADMIN_EMAIL` is supplied via the bootstrap configuration tier per REQ-CONFIG-004 and REQ-NFR-011 and must never be stored in `sys_config`.
- `REQ-ROLE-006` Admin bootstrap and later admin transfer are operationally controlled, not self-service.
- `REQ-ROLE-007` Admin transfer is performed by updating the seeded admin email in the environment or Azure App Configuration bootstrap source and redeploying or restarting the API application. On restart, the platform must resolve the current admin email from bootstrap configuration, assign the admin role to the matching account if it exists, and revoke the admin role from any account that previously held it. No in-app UI for admin role transfer is provided. The outgoing admin's FYERS token used for shared market data ingestion is not automatically transferred; the incoming admin must complete FYERS authentication to re-establish a valid shared token before EOD sync and background jobs can resume. The admin transfer event must be recorded in the audit trail once the new admin first logs in.
- `REQ-ROLE-007a` On the new admin's first login after an admin transfer, the platform must surface a **transfer recovery summary** on the admin home page before the standard admin dashboard renders. The summary must display: (a) the count of background job runs that completed with outcome `failed` or `skipped` during the transfer window — defined as the period from the last successful job run before the restart to the new admin's first login; (b) for each failed or skipped run: job type, scheduled run time, outcome, and a one-click action to manually trigger a retry or recovery for that job from within the summary screen; (c) a prominent notice if the admin FYERS token is not yet established, with a direct link to FYERS authentication, since EOD sync and LMDS cannot resume until the token is present. The summary is dismissible by the new admin once reviewed; dismissal is recorded in `audit_events`. The data for the summary is sourced from `job_runs` and requires no new persistence; it is a filtered view of existing job outcomes scoped to the transfer window.

### Technology Stack

*Mandatory technology choices. Do not introduce alternatives without updating this section and recording an ADR. Technology choices are intentionally aligned with the primary developer's skill profile: strong C# and .NET, proficient TypeScript, and beginner-level Node.js / full-stack web. Any proposed change must justify itself against that constraint.*

- `REQ-TECH-001` The unified web frontend is a Node.js application using Next.js and TypeScript. Next.js is chosen because it is the most accessible full-stack React framework for a developer who knows TypeScript but is new to Node.js full-stack patterns.
- `REQ-TECH-002` Backend APIs, background jobs, and backtesting services use C# on ASP.NET Core. This is non-negotiable: the primary developer is experienced in C# and all complex server-side logic must remain in the .NET layer.
- `REQ-TECH-003` Backend logging in .NET services must use Microsoft `ILogger` with Serilog as the logging provider.
- `REQ-TECH-004` Cross-system observability must use OpenTelemetry and OTLP so logs, traces, and metrics can be routed to different vendors without code changes.
- `REQ-TECH-005` The frontend must not grow complex server-side logic beyond API route proxying, authentication session handling, and lightweight data transformation. Any business logic, risk calculations, or data-intensive processing must live in the .NET backend.

### Canonical Data Ownership

*Defines which database owns which class of data. Every data model decision must be consistent with this section.*

- `REQ-DATA-001` MongoDB stores live operational data: user state, strategies, credentials metadata, tokens, signals, notifications, audits, and portfolio analytics.
- `REQ-DATA-002` SQL Server stores shared historical Nifty 500 market data and persisted backtest results; these are kept in two separate databases.
- `REQ-DATA-003` SQL Server data is shared reference data and is not user-specific.
- `REQ-DATA-004` The SQL Server market data database holds only OHLCV history for active and archived Nifty 500 symbols. The SQL Server backtest database holds all backtest run data including trades, positions, and portfolio performance records.
- `REQ-DATA-005` MongoDB may also store admin-managed runtime system settings in a `sys_config` collection for values that should be editable through the portal.
- `REQ-DATA-006` Redis may be used for WebSocket fan-out, hot caches, and job coordination locks.
- `REQ-DATA-006a` Redis is a critical infrastructure component for this platform: a Redis failure simultaneously disables real-time WebSocket stop-breach alerts (users receive no intraday push notifications), distributed job-coordination locks (risk of concurrent FIFO corruption per REQ-PORT-031), and hot caches. The Redis deployment must therefore meet the following availability requirements: (a) **Deployment:** Azure Cache for Redis at the Standard tier or above, deployed with zone redundancy enabled across at least two Availability Zones in the Central India region. A self-managed single-instance Redis without replication is not acceptable for any phase. (b) **Persistence:** AOF (Append-Only File) persistence must be enabled with `appendfsync everysec` so that a Redis restart after a crash loses at most one second of writes; RDB snapshots are a secondary safeguard only. (c) **Degradation behaviour when Redis is unreachable:** (i) WebSocket fan-out — background workers must log a warning and fall back to writing events only to the `notifications` MongoDB collection; portal clients that are connected but not receiving WebSocket events must surface a "Live alerts paused — real-time monitoring is temporarily unavailable" banner and continue polling for notifications manually; (ii) Job-coordination locks — any code path that requires a Redis distributed lock must treat a Redis connection error as a failed lock acquisition and apply the caller-appropriate skip/timeout/abort behaviour defined in REQ-PORT-031; it must not proceed without a lock and must not silently corrupt the ledger; (iii) Hot caches — callers must fall through to the authoritative MongoDB or SQL Server source on a cache miss; increased latency is acceptable, silent staleness is not. All Redis availability events — connection failures, AOF errors, eviction storms — must be emitted as OpenTelemetry metrics and surface on the admin System Health widget (REQ-ADMIN-014).

### Configuration Model

*Implemented by a shared configuration service consumed by all .NET applications. No application may query `sys_config` ad hoc from business logic.*

- `REQ-CONFIG-001` The platform must use a hybrid configuration model with bootstrap config, shared technical config, and admin-managed runtime config.
- `REQ-CONFIG-002` Mutable admin-managed runtime settings may be stored in MongoDB `sys_config`.
- `REQ-CONFIG-003` `sys_config` records must use a stable schema with key, category, value type, current value, default value, validation metadata, editability, restart requirement, audit metadata, and version.
- `REQ-CONFIG-004` `sys_config` must be limited to non-secret runtime settings and must not store connection strings, provider secrets, or seeded admin identity.
- `REQ-CONFIG-005` The admin portal must allow viewing, editing, filtering, and resetting allowed `sys_config` values with audit trail.
- `REQ-CONFIG-005a` **sys_config mutation audit trail (U-4).** Every write to a `sys_config` record — whether a value edit, a reset to default, or a step-up-gated category change — must produce an immutable record in the `audit_events` collection before the `sys_config` document is updated. The audit record must carry: the `sys_config` key, category, the prior value (as stored before the write), the new value, the admin user ID performing the change, the ISO 8601 UTC timestamp of the change, and — when the change is gated by a step-up re-authentication per REQ-SEC-011 — the reference to the step-up `audit_events` record that authorised it. The `sys_config` write and the `audit_events` write must be performed as an application-layer atomic sequence: if the `audit_events` write fails, the `sys_config` write must not proceed and the caller must receive a clear error. Read operations on `sys_config` do not require an audit record. Computed or read-only `sys_config` fields must be rejected at the repository layer if a caller attempts to write them directly; the rejection must emit a structured Warning log identifying the calling component and the field name, but does not require an `audit_events` record.
- `REQ-CONFIG-006` Applications must load configuration through a dedicated configuration service rather than querying `sys_config` ad hoc from business code.
- `REQ-CONFIG-007` Runtime config must support category-based grouping at least for: jobs, market data, strategies, risk, position sizing, notifications, UI, feature flags, and operations.
- `REQ-CONFIG-008` If `sys_config` is unavailable, startup-critical application behaviour must still work from bootstrap configuration, and runtime features must degrade safely.
- `REQ-CONFIG-009` A complete seed table listing every required `sys_config` key, its category, value type, default value, and the requirement that mandates it must be maintained in `docs/system-config.md`. This seed table is the authoritative reference for the database seeding script and for operators validating a fresh deployment. When a new requirement introduces a `sys_config` key, the key must be added to the seed table at the same time the requirement is written.
- `REQ-CONFIG-010` The empty-database boot sequence must be declared explicitly so a first deploy is deterministic and a missed deployment step is a loud failure rather than a silent self-repair. On every deployment the GitHub Actions deployment workflow must run, in order: (1) FluentMigrator for the SQL Server databases, (2) Mongo.Migration for MongoDB, (3) the `sys_config` seeder defined in REQ-CONFIG-011. Only after all three steps report success may the API service and Worker service be activated. Neither the API nor the Worker may seed `sys_config` from its own startup path; both services must, on startup, read the sentinel row `platform.seed.version` from `sys_config` and must **fail fast with a clear error** if that row is absent. The seeded admin identity is not part of `sys_config` (REQ-CONFIG-004, REQ-NFR-011); the `SEED_ADMIN_EMAIL` value continues to be supplied via the bootstrap configuration tier.
- `REQ-CONFIG-011` The `sys_config` seeder must be a distinct .NET console application, versioned in the same repository and deployed alongside the API and Worker services. Its behaviour must be: (a) read the manifest that mirrors the seed table in `docs/system-config.md` (a source-controlled JSON or YAML file is the canonical source, and the table in the doc is its rendered view); (b) for every key in the manifest, insert the row into `sys_config` if and only if no row with that `key` already exists — the seeder must never overwrite an existing row; (c) for keys flagged `*(seeded per deployment)*` in the manifest, resolve the value from a pipeline parameter named after the key, and fail the pipeline with a clear error listing every unresolved per-deployment key if any is missing; (d) after all manifest rows are processed, upsert the sentinel row `platform.seed.version` with the deployment's release identifier so REQ-CONFIG-010 startup checks succeed; (e) emit a structured report — keys inserted, keys skipped because already present, per-deployment keys resolved, sentinel version written — as a release-pipeline artefact for operator review; (f) be safe to re-run on every deployment, including upgrades that add new keys to the manifest. The seeder runs against the same bootstrap configuration tier as the API and Worker so it can resolve MongoDB connection strings and Key Vault references; it must not read `sys_config` to configure itself.

### Non-Functional Requirements

*Platform-wide quality and operational requirements. Apply to all components.*

- `REQ-NFR-001` Prioritise correctness and reproducibility over ultra-low latency in early milestones.
- `REQ-NFR-002` Keep interactive requests responsive where practical.
- `REQ-NFR-003` Degrade gracefully during FYERS or Telegram outages.
- `REQ-NFR-004` Every production issue must be investigable through logs, metrics, and audit events.
- `REQ-NFR-005` The platform is hosted on Azure and delivered through GitHub (GitHub Actions for CI/CD).
- `REQ-NFR-006` Third-party credentials must be protected with encryption and strict access controls.
- `REQ-NFR-007` Risk controls and sizing defaults must remain conservative by default.
- `REQ-NFR-008` All applications must emit logs, traces, and metrics through a shared OpenTelemetry and OTLP-based observability model.
- `REQ-NFR-009` Application telemetry must target a stable OTLP collector or gateway endpoint so downstream vendors can be changed through configuration.
- `REQ-NFR-009a` The OTLP collector or gateway must be deployed with at least two replicas behind a load balancer so that a single collector instance failure does not create a total observability blackout. Telemetry loss during an incident is the worst-case scenario, since degraded observability makes diagnosis impossible at exactly the moment it is most needed. All applications must emit telemetry with fire-and-forget semantics (non-blocking) so that a collector outage never causes the application to degrade or fail; telemetry loss during a collector outage is acceptable, but application slowdown caused by blocked telemetry export is not. The collector configuration must include an Azure-hosted fallback endpoint (for example, a second collector deployment in South India or an Azure Monitor OTLP ingestion endpoint) so that if the primary collector cluster becomes unavailable, telemetry can be re-routed via configuration without a code deployment. The fallback endpoint must be documented in the operational runbook and verified at least annually.
- `REQ-NFR-010` Startup-critical configuration must not depend solely on MongoDB; applications must be able to bootstrap with environment or Azure-hosted configuration.
- `REQ-NFR-011` Database connection strings, seeded admin identity, and other security-sensitive bootstrap values must remain outside `sys_config`.
- `REQ-NFR-012` Shared non-secret technical configuration must be centrally managed and consumable by all applications from one place.
- `REQ-NFR-013` The platform must use WebSockets for real-time push delivery of time-sensitive events to connected portal clients. The following events must be pushed via WebSocket rather than polled by the client: stop level breach alerts, add and reduce level advisory triggers, and pending-entry supersede notifications. All other data — dashboard portfolio figures, position summaries, notification feed contents — may be fetched on demand or on page load. Redis must be used as the WebSocket fan-out layer so that push events generated by background workers reach all connected portal instances. Clients that are not connected at the time an event fires must receive the alert through the portal notification feed on their next active session.
- `REQ-NFR-014` The platform must meet the testing coverage and depth targets defined in `docs/engineering-standards.md` (Testing Standards section). Targets include unit-test coverage minimums per stack, integration-test coverage of every critical workflow, a load test executed before the Phase B transition, and chaos or failure-injection exercises before the Phase C transition. Failure to meet a target before a phase transition gates the transition per REQ-LEGAL-005.
- `REQ-NFR-015` All HTTP API routes exposed by the ASP.NET Core backend must be versioned from the first endpoint added. The versioning scheme is URI path prefixing: every route is prefixed with `/api/v{major}` where major is a positive integer starting at 1 (e.g., `/api/v1/portfolio/snapshot`). A new major version is introduced only when a breaking change — removal of a field, rename of a field, change in response shape, or removal of an endpoint — is required; non-breaking additions (new optional fields, new endpoints) do not require a major bump and may be added to the current version. The prior major version must remain supported for at least one full release cycle after a new major version is published, during which time both versions must be served concurrently; deprecation must be surfaced in the API response headers (`Deprecation` and `Sunset` headers per RFC 8594). The ASP.NET Core API project must use `Asp.Versioning.Mvc` (or the equivalent current Microsoft-supported versioning package) to implement this scheme consistently. No endpoint may be deployed to any environment without a version prefix.
- `REQ-NFR-016` A contract test suite must exist that validates the schema contract between the Next.js portal (TypeScript consumer) and the ASP.NET Core API (provider) before every deployment to the staging environment and as a mandatory CI gate on every pull request that modifies either the API response shapes or the portal's API client types. The contract tests must verify: (a) every response field the portal reads is present and the correct type in the API response; (b) every required request field the portal sends is accepted by the API without a 4xx error; and (c) the API version prefix matches what the portal is configured to call. A contract mismatch must fail the CI pipeline and block the pull request from merging. Contract tests must be written using a lightweight schema-comparison approach (e.g., a TypeScript type assertion test against a serialised API response fixture, or an OpenAPI schema diff); a full integration environment is not required for contract tests. This requirement must be satisfied before Phase 7 (execution assistance) implementation begins, because a schema mismatch in the order placement flow — specifically the Phase 1 modal reading incorrect field names or types from the position or RME API responses — can cause silent failures where the user believes an order has been submitted correctly when it has not.
- `REQ-NFR-017` **Backtest Engine / live RME parity check (U-5).** The platform must maintain a nightly scheduled parity check that runs as part of the CI/CD pipeline — specifically as a standalone nightly scheduled GitHub Actions workflow — to assert that the Backtest Engine (BTE) and the live Risk Management Engine (RME) produce identical outputs for a fixed synthetic fixture. The fixture is a developer-maintained set of test scenarios committed to the repository alongside the RME and BTE code; each scenario specifies a symbol identifier, a fixed OHLCV data slice, a Signal Subscription parameter set, an RME configuration, a sequence of simulated fill events, and the expected outputs (position sizing in shares and INR, stop loss level, trailing stop level, add and reduce advisory levels). The parity check must assert that for each scenario, BTE and RME output values match within a declared tolerance — exact match for price levels expressed in INR rounded to 2 decimal places, within ±1 share for quantity outputs subject to lot-size rounding. Divergence between BTE and RME on any scenario must: (a) fail the nightly pipeline with a structured error identifying the scenario name, the diverging field, the BTE value, and the RME value; (b) emit an `admin_bte_rme_divergence_detected` admin notification via Telegram and email; (c) block the Phase 7 deployment gate if any divergence is present. The fixture must include at minimum: a basic long entry with Fixed % sizing and a fixed ATR stop; a trailing ATR stop ratchet scenario; a pyramiding add scenario; and a time stop expiry scenario. The fixture and the fixture runner are Phase 6 deliverables and must exist in the repository before any Phase 7 (execution assistance) code is deployed to staging. A `sys_config` key `operations.bte_rme_parity.enabled` (default `true`) allows the admin to disable the nightly check for incident response; disabling must emit a one-time admin Telegram and email notification and must be recorded in `audit_events`.

### Data Protection and Privacy

*Implements the platform's obligations under the Digital Personal Data Protection Act, 2023 (DPDP). These requirements apply in all phases from the first external user onward, including Phase A tester accounts. The admin is the data fiduciary unless a separate operating entity is later established.*

- `REQ-PRIVACY-001` The platform is a data fiduciary under the DPDP Act, 2023. All personal-data handling — collection, storage, processing, transfer, retention, and erasure — must comply with DPDP obligations regardless of the current operating phase. Phase A does not reduce DPDP obligations; the first tester who is not the admin triggers full compliance.
- `REQ-PRIVACY-002` At signup, the platform must present a plain-language privacy notice stating: the categories of personal data collected (identity, contact, FYERS-linked trading data, portfolio analytics derived from trading data, Telegram chat identifier if linked, audit records); the purposes for which each category is processed; the retention period for each category; the third parties with whom data is shared or to whom processing is delegated (FYERS, configured market data provider, Telegram, Azure-hosted infrastructure, observability vendor); and the user's rights under DPDP. The notice must be linked from the privacy-consent checkbox on signup and must remain accessible from the persistent portal footer at all times. The notice must be versioned; version changes that materially alter purposes or third-party recipients require refreshed consent per REQ-PRIVACY-008.
- `REQ-PRIVACY-003` User consent to personal-data processing must be captured as a distinct affirmative checkbox at signup, separate from the Terms of Service acceptance and the tester acknowledgement acceptance required by REQ-LEGAL-008 and REQ-LEGAL-004. Consent must be specific, informed, and unambiguous. The privacy notice version accepted, user identity, and timestamp must be recorded in `audit_events`. Pre-checked consent boxes and bundled consent are not permitted.
- `REQ-PRIVACY-004` The platform must support the following data-subject rights: access (an export of the user's stored personal data in a machine-readable format, including profile fields, linked accounts, consent history, and notification history); correction (of profile fields editable by the user directly, and of other fields by raising a ticket); erasure (soft-deactivation of the account combined with redaction of personal identifiers from fields where erasure is lawful, while preserving the fact and version of prior consent and ToS acceptances, audit events, and trade ledger records that are retained under lawful record-keeping obligations); and grievance redressal. For V1, the data-subject request workflow may be email-driven: requests received by the grievance officer's email are logged into an admin-portal ticket queue; the admin resolves each ticket through an audited flow. A fully self-service request portal is not required for V1. Acknowledgement of access and correction requests must not exceed 7 calendar days; completion must not exceed 30 calendar days. Erasure requests must be acknowledged within 7 calendar days and completed within 30 calendar days subject to lawful retention carve-outs, with the retained categories and their basis disclosed to the requester.
- `REQ-PRIVACY-005` The platform must designate a named grievance officer whose name, role, and contact email are published in the Privacy Policy and displayed on a dedicated "Contact and Grievances" page accessible from the persistent portal footer. During Phase A the admin is the grievance officer by default. The designation — including any change of grievance officer — must be recorded in `audit_events`.
- `REQ-PRIVACY-006` The platform must implement a personal-data breach procedure. A personal-data breach is any unauthorised access, disclosure, loss, or alteration of personal data. Detected or suspected breaches must be recorded immediately in `audit_events` with scope (data categories affected, approximate user count, systems involved), detection time, discovery actor, and initial containment steps. Notification to the Data Protection Board of India and to affected data principals must be issued within 72 hours of detection, with content conforming to the Board's prescribed format. A runbook covering detection, triage, notification content, and post-incident review must exist in the repository and be referenced from the Privacy Policy. Test exercises of the breach procedure must be performed at least once per calendar year and recorded in `audit_events`.
- `REQ-PRIVACY-007` The platform must not accept signups from minors (data principals under 18 years of age as defined by DPDP). The signup flow must include a distinct self-declaration checkbox that the user is 18 or older. Accounts later found to belong to minors must be deactivated immediately, their personal data erased subject to lawful retention carve-outs, and the event recorded in `audit_events`. No feature that specifically targets or appeals to minors is in scope.
- `REQ-PRIVACY-008` Personal data must be processed only for the purposes disclosed in the privacy notice accepted by the user. Introducing a new processing purpose, a new third-party data recipient, or materially expanded data categories requires the privacy notice version to be bumped and all affected users to provide refreshed consent on next login before the new processing occurs for them. Collection of personal data beyond what is necessary for the disclosed purposes is prohibited.
- `REQ-PRIVACY-009` Personal-data retention windows for each collection must be aligned with the mechanisms documented in `docs/data-management.md`. When Phase C is entered, SEBI record-keeping obligations may require longer retention for trade-related and advisory records than the archive thresholds documented for Phase A; `docs/data-management.md` must be updated to reflect Phase C retention windows before the Phase C transition is recorded as complete. In all phases, retention of personal data beyond the disclosed windows is prohibited unless a specific lawful retention basis is documented.
- `REQ-PRIVACY-010` The platform must maintain an internal Record of Processing Activities (RoPA) covering: each category of personal data collected; the purposes for which it is processed; the categories of data principals (Phase A testers, Phase C paying users, admin); retention periods; third-party recipients and their processing location (including cross-border transfers); the lawful basis for processing; and the security measures applied. The RoPA must be reviewable at any time by the admin and must be refreshed whenever the privacy notice version changes. The RoPA is stored as a versioned document in the repository under `docs/privacy/ropa.md` and is the source of truth for the privacy notice content served to users.
- `REQ-PRIVACY-011` The platform must maintain processor agreements (or equivalent contractual safeguards) with all third parties that process personal data on behalf of the platform, including hosting (Azure), market data provider, Telegram, and observability vendor. Evidence of the agreement must be recorded with the admin legal-posture records and must be reviewable at any time. Adding a new processor requires completing the agreement before production traffic routes personal data to that processor and requires the privacy notice update flow in REQ-PRIVACY-008.
- `REQ-PRIVACY-012` The "View as user" admin impersonation mode (REQ-ADMIN-015) constitutes a distinct personal-data processing activity in which the admin accesses a user's live portfolio, positions, FYERS holdings, notification history, and all other data visible in the target user's portal session. This processing activity must be explicitly documented in the RoPA (REQ-PRIVACY-010) with: purpose (operational support and platform troubleshooting by the designated admin); lawful basis (legitimate interest of the data fiduciary in operating and maintaining the platform, subject to the safeguards listed here); safeguards (step-up re-authentication required per REQ-SEC-011; read-only enforcement with server-side write rejection; full audit trail of session entry, exit, and pages visited in `audit_events` per REQ-ADMIN-015; idle-timeout auto-expiry). The Privacy Policy served to users must disclose, in plain language, that the admin may access a read-only view of any user's account for operational support purposes and that each such access is recorded. The user-facing disclosure must be present before the first non-admin user is onboarded in any phase. The `docs/privacy/ropa.md` document must be updated to include an impersonation processing activity entry before Phase A onboarding begins.

### Business Continuity and Backups

*RPO and RTO guarantees per data class, secret rotation cadence, restore drills, and admin-identity MFA enforcement. Applies in all phases.*

- `REQ-BCP-001` MongoDB operational data must have a Recovery Point Objective (RPO) of 1 hour and a Recovery Time Objective (RTO) of 2 hours. Point-in-time recovery must be enabled, with continuous backup (MongoDB Atlas PITR or an equivalent managed backup stream) retaining at least 24 hours of restorable history. All MongoDB collections catalogued in `docs/data-management.md` are covered by this requirement, including `trade_ledger`, `positions`, `equity_curve`, `audit_events`, and `portfolio_snapshots`.
- `REQ-BCP-002` The SQL Server market data database must have RPO 24 hours and RTO 4 hours. Daily full backups plus transaction log backups at least every 6 hours during trading days are required. If the database is lost, DataSync and HistoricDataSeed must be able to rebuild daily candles from the configured market data provider; pre-computed weekly and monthly candles are re-derivable from daily data.
- `REQ-BCP-003` The SQL Server backtest database must have RPO 7 days and RTO 8 hours. Weekly full backups are sufficient. Stored backtest results are reproducible from retained market data, Signal code, and Signal Subscription parameters, so a longer recovery horizon is tolerable for this database.
- `REQ-BCP-004` Azure Key Vault must have soft-delete enabled with 90-day retention and purge protection enabled. Secrets covered include FYERS API application credentials, Telegram bot token, third-party market data provider credentials, session signing keys, and any other secret referenced by the platform at runtime. Accidental or malicious permanent secret loss must not be possible within the soft-delete window.
- `REQ-BCP-005` All backups — MongoDB continuous streams, SQL Server full and transaction log images, and Key Vault snapshots — must be geo-redundantly replicated to a secondary Azure India region. Central India is the primary region; South India is the secondary. Cross-region replication must satisfy the data residency requirement in REQ-LEGAL-009: both regions are within India. No active-active application footprint is required for Phase A; the secondary is a restore target only.
- `REQ-BCP-006` A documented restore procedure must exist for each data class. Each procedure must cover: identifying the correct point-in-time target; restoring to a new instance rather than over the live database where possible; validating the restored dataset; and cutting the application over. Procedures must be stored in operational docs and referenced from the admin portal runbook index.
- `REQ-BCP-007` A full restore drill must be executed at least once per calendar year and its outcome recorded in `audit_events`. The drill must exercise MongoDB PITR restore, SQL Server market data restore, SQL Server backtest restore, and Key Vault secret recovery. Any drill step failure is a Priority 1 follow-up that must be tracked to closure, with resolution recorded in `audit_events`.
- `REQ-BCP-008` Secret rotation cadence: FYERS API application secret rotated annually and immediately on any suspected compromise or operator change; Telegram bot token replaced on demand per REQ-NOTIFY-015 with no forced schedule; Key Vault-managed encryption keys auto-rotated every 90 days using Azure Key Vault rotation policies; session signing keys rotated every 90 days with a 7-day overlap window during which both the outgoing and incoming keys are valid for verification. Database, Azure App Configuration, and Azure service connections must use Azure Managed Identity wherever supported so that rotatable secrets are avoided entirely. Every rotation event — successful, failed, or manually triggered — must be recorded in `audit_events`. **Intent HMAC key retention for audit (S-13):** The HMAC signing key used for intent payload signing (REQ-ORDER-009b) must be retained in Azure Key Vault under a versioned secret rather than being permanently deleted at rotation time. Azure Key Vault's built-in secret versioning satisfies this requirement: the new key becomes the active version, and all prior versions remain accessible in Key Vault under the same secret name. The old key versions must be usable only for audit-verification of historical `intent_ledger.payload_signature` records — never for signing new payloads. After rotation, newly signed payloads carry the new key version identifier in their signature; historical payloads signed under an old key version remain re-verifiable against the corresponding old Key Vault secret version. Purging old HMAC key versions is not permitted; soft-delete and purge protection (REQ-BCP-004) apply. This design means post-rotation, historical intent signatures remain independently verifiable for compliance and dispute resolution without relying solely on the immutability guarantee in REQ-ORDER-014b.
- `REQ-BCP-009` The admin OAuth identity (seeded per REQ-ROLE-005) must have multi-factor authentication enforced at the identity provider. The platform cannot enforce MFA directly at the IdP, but on admin sign-in it must validate that the OAuth token carries an authentication methods claim indicating an MFA factor was used (for example, an `amr` claim including `mfa`, `mca`, `hwk`, `otp`, or equivalent). Sign-in without an MFA claim for the admin identity must be blocked with a clear message directing the admin to enable MFA at the IdP before retrying. The MFA-verified state must be recorded on the admin session record in `sessions`. **Admin OAuth provider restriction:** The admin-bound OAuth provider must be either Google or Microsoft (Azure AD / Entra ID). Facebook/Meta is not permitted as the admin's OAuth provider because Facebook's standard OAuth response does not reliably expose an MFA authentication-methods claim, making MFA validation impossible at the platform layer. Regular users may continue to use any of the three configured providers (Google, Microsoft, Facebook/Meta). The admin-bootstrap validation at REQ-ROLE-005 must enforce this restriction: if the seeded admin email is associated with a Facebook/Meta OAuth credential at first sign-in, the sign-in must be refused with a clear message directing the admin to link a Google or Microsoft identity before the admin account can be activated.

### Service Level Objectives

*Quantified operational targets for user-facing latency, background job lag, notification delivery, and concurrency. Phase A baseline; tightened Phase C targets called out where relevant.*

- `REQ-SLO-001` Dashboard first-paint of primary portfolio content (served from `portfolio_snapshots` per REQ-DASH-015) must meet p95 ≤ 2 seconds in Phase A and p95 ≤ 1 second in Phase C, measured from portal navigation start to snapshot data fully rendered. The underlying dashboard API call must have TTFB p95 ≤ 800 ms in Phase A.
- `REQ-SLO-002` Chart page load — technical chart rendered with historical data and the RME advisory panel populated — must meet p95 ≤ 3 seconds in Phase A, measured from chart page navigation start to first chart render.
- `REQ-SLO-003` Intraday account sync end-to-end lag must be p95 ≤ 2 minutes per user, measured from the configured interval fire time to portfolio snapshot write completion. If sync for a user consistently exceeds this target, the batch must be split or the interval lengthened via `sys_config` per REQ-PORT-019.
- `REQ-SLO-004` The Live Market Data Scan (LMDS) must complete each scan cycle within 70% of its configured poll interval (`jobs.live_market_scan.poll_interval_seconds`). Cycles exceeding this threshold must log a warning and surface on the admin System Health widget (REQ-ADMIN-014). Persistent breaches require the admin to lengthen the poll interval.
- `REQ-SLO-005` Telegram notification delivery lag from `notifications` record write to first successful Telegram send must meet p95 ≤ 30 seconds, subject to Telegram's own upstream availability. Pending notifications older than 5 minutes must surface as a warning on the admin System Health widget. Repeated delivery failures follow REQ-NOTIFY-008 and REQ-NOTIFY-019.
- `REQ-SLO-006` Phase A concurrent approved user ceiling is governed by REQ-LEGAL-003 (30). Maximum concurrent portal WebSocket connections per user is 3; exceeding this must invalidate the oldest connection rather than reject the newest.
- `REQ-SLO-007` Concurrent backtest execution must be capped at 5 platform-wide and 1 per user. Additional backtest requests must be queued with a visible queue position shown to the user in the portal. Queue depth and average wait time must be observable via OpenTelemetry metrics.
- `REQ-SLO-008` All SLO breaches — both background job SLOs and user-facing request SLOs — must be observable through the OpenTelemetry pipeline as dedicated SLO-breach metrics so that budget burn rate can be monitored and alerted on without bespoke log parsing. **SLO breach alert routing (N-8):** Critical SLO breaches — specifically the RME event processing p95 target (REQ-SLO-009) and the stop-detection-to-notification p95 target (REQ-SLO-010) — must also emit a one-time admin notification via Telegram and email on the first breach per session (defined as the first calendar day's occurrence, not per individual event). The notification must name the breached SLO, the observed p95 value, the target, and the time of first detection. A cooldown of `sys_config.slos.breach_notification_cooldown_minutes` (default 60 minutes) must apply per SLO per session to prevent alert storms during sustained degradation. Without this routing, SLO breaches that are not proactively checked in Grafana will go unnoticed until the next manual operator review.
- `REQ-SLO-009` RME event processing latency — from an `RmeEvent` being enqueued to a position's channel (per REQ-RME-CONC-001) to the resulting position document write completing in MongoDB — must meet p95 ≤ 5 seconds under normal Phase A load (≤ 150 concurrent open positions). This duration must be emitted as an OpenTelemetry histogram `rme.event_processing_duration_ms` tagged with `event_type`. A sustained breach of this target across two or more consecutive LMDS poll cycles must surface as a warning on the admin System Health widget. This SLO is a correctness boundary, not merely a performance target: a stop-breach event enqueued but not yet written to the position record represents an advisory state that is not yet visible to the system — the longer this window, the greater the risk that a subsequent event (e.g., a further price drop or a user-initiated action) acts on stale RME state.
- `REQ-SLO-010` The end-to-end latency from a stop breach being detected within an LMDS cycle to the corresponding `notifications` record being written to MongoDB — encompassing RME event enqueue, channel consumer processing, and notification record creation — must meet p95 ≤ 15 seconds under normal Phase A load. Combined with REQ-SLO-005 (Telegram delivery p95 ≤ 30 seconds from record write), this bounds the total stop-detection-to-first-alert pipeline at p95 ≤ 45 seconds under normal conditions. This composite latency must be instrumented as an OpenTelemetry histogram `stop_breach.detection_to_notification_ms`, measured from the LMDS detection timestamp to the `notifications` record `created_at` timestamp, so both the component and composite targets can be tracked independently. If pre-Phase A load testing demonstrates this target cannot be met with the current architecture, the gap must be logged as a Priority 1 architectural issue and resolved before any Phase A tester beyond the admin uses live execution features.
- `REQ-SLO-011` The LMDS must emit the total count of open positions evaluated per poll cycle as an OpenTelemetry counter `lmds.positions_evaluated_per_cycle`. The Phase A design capacity — the maximum number of positions that can be evaluated within a single cycle without breaching REQ-SLO-004 at the default poll interval — must be validated by a load test before Phase A user onboarding begins; the validated ceiling must be recorded in the Phase A readiness checklist. When the per-cycle position count exceeds a configurable percentage of the validated ceiling (`sys_config` key `jobs.lmds.capacity_warn_pct`, default 80%), the admin System Health widget must surface a capacity warning showing the current position count, the validated ceiling, and a prompt to either adjust the poll interval or plan for Phase C horizontal scaling. The validated ceiling must be re-established whenever LMDS evaluation logic changes materially or when the default poll interval is changed.

### Security Posture

*Baseline security requirements that apply in all phases. These must be in place before the first non-admin user accesses the platform. Items that complement `docs/engineering-standards.md` — which sets coding conventions — here take the form of explicit product requirements that must be verifiable.*

- `REQ-SEC-001` All authenticated, state-changing API endpoints must be protected by CSRF tokens. The Next.js portal and the ASP.NET Core API must jointly enforce token presence and validity on every POST, PUT, PATCH, and DELETE request originating from the portal. Missing or invalid tokens must return HTTP 403.
- `REQ-SEC-002` Every HTML response served by the portal must include a strict Content Security Policy (CSP) header limiting script, style, font, image, connect, and frame sources to the platform's own origins plus explicitly whitelisted third parties (TradingView iframe embeds, FYERS API Connect widget origin, observability vendor endpoint). Inline scripts must be disallowed except via cryptographic nonces.
- `REQ-SEC-003` Every HTTP response from the portal must include the following security headers: `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`; `X-Content-Type-Options: nosniff`; `X-Frame-Options: DENY` or equivalent CSP `frame-ancestors 'none'`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy` locked to the minimum capability set the platform actually uses.
- `REQ-SEC-004` TLS 1.2 or higher must be enforced on every public endpoint. TLS 1.0 and 1.1 must be disabled at Azure Front Door and at the application gateway layer. HSTS preload registration must be completed before Phase C launch.
- `REQ-SEC-005` The public-facing portal must be fronted by Azure Front Door with the Web Application Firewall enabled. The Azure-managed OWASP Core Rule Set must be active. Custom WAF exclusions must be approved by the admin and recorded in `audit_events` with justification and scope.
- `REQ-SEC-006` Authentication and session-management endpoints (OAuth callback, FYERS auth callback, session refresh) must be rate-limited at the edge. At minimum: 10 authentication attempts per IP per hour; exponential back-off on the same user identity after 3 consecutive failures. Exceeding the limit must return HTTP 429.
- `REQ-SEC-007` The CI pipeline must run dependency vulnerability scanning on every build for both the .NET and Node.js codebases. High-severity and critical-severity findings must block merge to the main branch. A weekly scheduled scan must run against the main branch to surface regressions introduced by published CVEs.
- `REQ-SEC-008` The CI pipeline must run static application security testing (SAST) on every pull request. Findings must be reviewed and triaged before merge.
- `REQ-SEC-009` Secret scanning must run both pre-commit (via git hooks) and in CI. Any accidentally-committed secret must be rotated immediately per REQ-BCP-008 and the event recorded in `audit_events`.
- `REQ-SEC-010` A qualified external penetration test must be completed before Phase C launch, scoped to the portal, API layer, background workers, and admin portal. High- and critical-severity findings must be remediated before Phase C is entered. The test record and remediation status are a Phase C gating condition additional to those defined in REQ-LEGAL-005 and must be captured in `audit_events`.
- `REQ-SEC-011` The admin must complete a step-up re-authentication — a fresh OAuth handshake with the identity provider within the previous 5 minutes — before executing any of the actions listed in the table below. If the admin's last OAuth handshake is older than 5 minutes, the action must be blocked with a prompt to re-authenticate; the blocked action must not be partially executed. Each step-up authentication must be recorded in `audit_events` together with the subsequent action it gated, so that the chain of custody is fully auditable.

  | Action requiring step-up | Reference |
  |---|---|
  | Activate or deactivate the global RME kill switch | REQ-ADMIN-007 |
  | Deactivate or reactivate a user account | REQ-ADMIN-001a, REQ-ADMIN-001b |
  | Suspend or re-enable signals for a specific user | REQ-ADMIN-010 |
  | Disable or re-enable a Signal type platform-wide | REQ-ADMIN-011, REQ-ADMIN-013 |
  | Edit any `sys_config` value in the `risk`, `legal`, or `operations` categories | REQ-ADMIN-006 |
  | Transition the operating phase | REQ-LEGAL-001 |
  | Replace the Telegram bot token | REQ-NOTIFY-015 |
  | Toggle the Telegram global-disable break-glass flag (`notifications.telegram.global_disable`) | REQ-NOTIFY-022a |
  | Replace the FYERS API application credentials | REQ-BCP-008 |
  | Perform an admin-assisted account recovery | REQ-RECOVERY-005 |
  | Trigger a per-user "Rebuild trade ledger from broker" | REQ-PORT-027 |
  | Enter a "View as user" impersonation session | REQ-ADMIN-015 |
  | Manually suspend a user position | REQ-PLC-005a (`ADMIN` source) |
  | Release an admin-suspended position | REQ-ADMIN-016 (`ADMIN` source resolution flow) |
- `REQ-SEC-012` Step-up re-authentication for regular users on sensitive actions (for example, manual trade-ledger adjustments, RME profile changes on live positions) remains deferred to REQ-NEXT-008. The admin step-up requirement in REQ-SEC-011 does not apply to regular users.
- `REQ-SEC-013` An annual security review must be performed and recorded in `audit_events`, covering at minimum: CSP drift, dependency scan backlog, access-control audit, authentication flow integrity, admin MFA enforcement, and step-up coverage against the current list of destructive actions.

### Schema Migration and Versioning

*Governs how MongoDB collections and SQL Server tables evolve across releases without downtime or data loss. Complements `docs/engineering-standards.md`, which sets coding conventions; this section defines the product-level requirements that releases must meet.*

- `REQ-MIGRATION-001` Schema migrations must be managed by a versioned migration framework per storage stack: FluentMigrator or an equivalent deterministic tool for SQL Server; Mongo.Migration or an equivalent deterministic framework for MongoDB. Migrations must live in the repository as reviewable code, not applied ad hoc through database admin tools.
- `REQ-MIGRATION-002` Migrations must be applied at application startup, gated by a distributed lock so that only one application instance applies a given migration at a time. Instances that arrive after a migration has been applied must boot normally without re-applying. Startup must fail fast with a clear error if the lock cannot be acquired or the migration fails.
- `REQ-MIGRATION-003` Each migration must be either idempotent or paired with an explicit rollback migration. One-way migrations — those that cannot be safely rolled back, such as destructive column drops or data collapses — must be marked as one-way in the migration metadata and require an additional admin confirmation at deployment time before they can run.
- `REQ-MIGRATION-004` DDL operations that would span many per-symbol SQL Server tables — specifically the `D_`, `W_`, and `M_` tables whose count equals the symbol master — must not execute at application startup. They must be implemented as a batched background migration job triggered by the admin from the admin portal. The job must write progress to `job_runs` on a per-batch basis, be resumable after failure from the last successfully completed batch, and surface overall progress through the admin portal. This requirement governs fleet-wide schema evolution across already-existing per-symbol tables (e.g., adding a column, changing a data type, rebuilding an index across every symbol). It is distinct from and does not conflict with REQ-HIST-009a, which governs the per-symbol-scoped creation of the three `D_`, `W_`, `M_` tables at the moment a new symbol joins the symbol master. The two requirements share a single DDL schema template so that evolution and creation cannot diverge.
- `REQ-MIGRATION-005` When a per-symbol DDL migration introduces a column or changes a data shape that application code reads, the platform must support a documented dual-read window during which both the old and new schemas are accepted. The dual-read flag must be stored as a sys_config value; the admin flips it off only after the batched migration has been verified complete across the full symbol master.
- `REQ-MIGRATION-006` Every migration run — full, partial, successful, failed, or rolled back — must be recorded in `audit_events` with the migration identifier, framework version, outcome, affected scope, duration, and actor. Migration history must be retrievable by the admin from the admin portal.
- `REQ-MIGRATION-007` Production deployment must verify that all pending migrations apply cleanly against a restored snapshot of production data before the release is cut over. This verification is a release-pipeline obligation and must be recorded in the deployment artefact.

## Part 2 — Identity and Session

*Implemented by the ASP.NET Core API layer (auth middleware, session management) and the Next.js frontend (OAuth flow, FYERS lock UI). Must be fully operational before any other user-facing feature is built.*

### Portal Session Management

*Governs the platform's own OAuth session lifecycle and the FYERS token lock behaviour.*

- `REQ-SESSION-001` Portal OAuth sessions must be valid for 24 hours from the time of login; after expiry the user must re-authenticate via OAuth before accessing any protected portal features.
- `REQ-SESSION-002` Concurrent portal sessions for the same user are not permitted; a new login from any device must immediately invalidate any existing active session for that user.
- `REQ-SESSION-002a` Portal OAuth sessions must be stored server-side in a MongoDB `sessions` collection. Each session record must store the user ID, session token, issued-at timestamp, expires-at timestamp, and the device or user-agent context. On new login, any existing session record for the same user must be invalidated before the new session record is written, in a single atomic operation. All authenticated API requests must validate the session token against this collection. A TTL index must expire session documents automatically 24 hours after the issued-at timestamp.
- `REQ-SESSION-003` When a user's FYERS token expires, becomes dirty, or is marked as requiring re-authentication, the portal must lock immediately and display a prominent modal notification requiring FYERS re-authentication before the user can continue.
- `REQ-SESSION-004` The portal lock on FYERS token expiry must block all FYERS-dependent features including the dashboard, positions, charts, portfolio analytics, signal workflows, and any other feature requiring live or synced FYERS data.
- `REQ-SESSION-005` The FYERS re-authentication modal must remain dismissible only by completing the FYERS re-auth flow successfully; it must not be closeable without action.
- `REQ-SESSION-006` Step-up re-authentication for sensitive portal actions is deferred to a future version.
- `REQ-SESSION-007` The portal must warn the user before their OAuth session expires. A non-blocking indicator must appear when fewer than a configurable number of minutes remain before session expiry (default 30 minutes), allowing the user to re-authenticate proactively without losing their current context.
- `REQ-SESSION-008` When a portal OAuth session expires mid-use, the portal must redirect the user to the OAuth login page with a clear session-expired message. In-progress actions at the time of expiry must not fail silently; the user must see an unambiguous explanation of what happened.
- `REQ-SESSION-009` When the admin's own FYERS token is dirty, expired, or missing, the admin portal must display a persistent high-visibility warning making clear that EOD sync and all admin-token-dependent background jobs will fail until the token is re-established. Unlike the user FYERS lock (REQ-SESSION-003), this warning must not block the admin portal — the admin must remain able to navigate and take recovery action while the warning is displayed. This is the reactive complement to REQ-NOTIFY-022, which defines the proactive daily check that warns the admin before the token expires.
- `REQ-SESSION-010` The platform login journey for a regular user must enforce a strict two-step sequence: portal OAuth first, then FYERS authentication. No protected platform feature — including the dashboard, charting, strategies, portfolio analytics, and notifications — is accessible until both steps are complete and a valid FYERS token is on record for the user.
- `REQ-SESSION-011` After a user's portal OAuth login is confirmed and the platform identifies them as an approved user with no valid FYERS token on record, the portal must automatically redirect them to the FYERS authentication flow. The redirect must happen before rendering any protected page. A clear explanation must be shown stating that FYERS authentication is required to proceed.
- `REQ-SESSION-012` A user who has completed OAuth but whose account is still pending admin approval must see a dedicated approval-pending screen after login. The screen must state that their account is awaiting admin approval and must not expose any protected portal content. The user must be redirected automatically to the FYERS auth flow once the admin approves their account and they next attempt login.
- `REQ-SESSION-013` Users in an unapproved, FYERS-not-connected, FYERS-locked, deactivated, or pending-acknowledgement state must all be shown purpose-specific screens that clearly describe their situation. The states — pending approval, pending FYERS connection, FYERS token expired or dirty, account deactivated, and pending acceptance of a bumped ToS, Privacy Policy, long-form disclaimer, or tester acknowledgement version — must each produce a distinct, unambiguous UI state so users are never left confused about why they cannot access the platform. The account-deactivated screen must instruct the user to contact their platform administrator. The pending-acknowledgement screen must present the changed document inline and block access to every protected page until the user re-accepts each bumped document with a distinct affirmative action per REQ-LEGAL-004 and REQ-LEGAL-008.
- `REQ-SESSION-014` The platform adopts **latest-tab-wins** semantics for the FYERS Price Level Data (PLD) WebSocket stream. A user may have at most one active PLD stream open at any time, because the PLD connection is made using the user's individual FYERS token, and holding duplicate PLD streams consumes FYERS token quota and is a predictable UX failure mode. The policy is enforced as follows: (a) when a user's browser tab opens a PLD WebSocket subscription, the API writes a session entry to a Redis key `session:fyers:pld:{user_id}` containing a unique session ID for the new tab, with a TTL of `sys_config.session.fyers.lease_ttl_seconds` (default 1800 seconds); (b) if a Redis entry already exists for that user at the moment of the new subscription, the API sends a WebSocket close notification to the connection holding the existing session ID (close code 4001 with message "disconnected: another tab on your account opened a live chart"), and then writes the new session ID; (c) the evicted tab must display an in-portal banner — "This tab was disconnected because you opened a live chart in another tab" — and must not attempt to reconnect automatically; the user must manually navigate to re-establish the stream; (d) the new tab's session entry must be renewed on a heartbeat interval shorter than the TTL (suggested half the TTL, i.e., every `lease_ttl_seconds / 2` seconds) to keep the session alive as long as the tab is active; (e) on tab close or explicit WebSocket disconnect, the session entry must be deleted from Redis; (f) OHLCV chart data and all non-live-quote UI elements continue to render from SQL Server and the notifications collection regardless of PLD session state — only the live price stream is affected by this requirement.

### Authentication and FYERS Integration

*Covers OAuth login with third-party providers and FYERS token lifecycle for both the admin (shared data ingestion) and regular users (personal account data).*

- `REQ-AUTH-001` The portal must support OAuth login with Google, Microsoft, and Facebook/Meta.
- `REQ-AUTH-001a` Each unique combination of OAuth provider and email address creates a distinct platform account. No automatic account merging is performed. If a user registers via two different OAuth providers or with two different email addresses, two separate accounts are created. The admin may deactivate duplicate accounts through the user management portal per REQ-ADMIN-001a.
- `REQ-AUTH-002` A user must complete portal OAuth before starting the FYERS authentication workflow.
- `REQ-AUTH-003` The platform uses a single shared FYERS API application registered and managed by the admin. Users authenticate their individual FYERS brokerage accounts against the platform's shared FYERS API app using the FYERS OAuth flow. Users do not need to register or manage their own FYERS API applications. FYERS App ID and Secret credentials do not expire once created; there is no credential rotation or renewal lifecycle to manage. FYERS regulations require separate app registrations for data access and algo trading. The platform requires an algo trading app registration because it uses the FYERS API Connect JS widget (REQ-ORDER-006/014) for user-initiated order placement, which falls under the algo trading app type. The same app registration also covers market data access when FYERS is the configured market data provider. The admin must register a single FYERS algo trading app and provide its credentials for platform use; a data-only app registration is not sufficient. During Phase A (REQ-LEGAL-002), the admin's personal FYERS algo trading app is permitted as a known Phase A limitation. Before the transition to Phase B, the FYERS app must be replaced with a commercial registration in the name of the platform's operating entity per REQ-LEGAL-005; the admin portal Legal Posture widget (REQ-LEGAL-010) must reflect which app type is currently configured. Using a personal FYERS app to serve Phase A testers may be constrained independently by FYERS's own developer terms; confirming this permitted use with FYERS in writing before adding any tester beyond the admin is the admin's responsibility.
- `REQ-AUTH-003a` The platform's FYERS API application credentials (app_id and secret_key) must be stored in Azure Key Vault or equivalent secret storage and must never be placed in `sys_config`, environment variables accessible outside the deployment context, or source control.
- `REQ-AUTH-004` The admin must authenticate with FYERS and provide the token used for shared symbol and market-data ingestion.
- `REQ-AUTH-005` Each regular user must authenticate with FYERS using their own account so profile, positions, holdings, trades, and orders can be fetched.
- `REQ-AUTH-006` User-scoped FYERS tokens must never be used for shared market-data jobs.
- `REQ-AUTH-007` FYERS token state must be persisted in MongoDB with ownership, issue date, expiry metadata, status, and dirty or reauth-required state.
- `REQ-AUTH-008` FYERS access tokens must be treated as day-scoped operational tokens. Token validity beyond a single trading day must not be assumed by any component; workflows must handle token expiry as a routine, expected event rather than an exceptional error.
- `REQ-AUTH-009` If a sync or broker workflow fails because the persisted FYERS token is invalid, expired, or otherwise unusable, that token must be marked dirty and the user must reauthenticate with FYERS.
- `REQ-AUTH-010` A dirty FYERS token must block dependent sync workflows until the token is re-established successfully.
- `REQ-AUTH-011` The login page must always display all three supported OAuth providers (Google, Microsoft, Facebook/Meta) regardless of individual provider availability. Provider buttons must not be hidden or pre-screened based on server-side availability checks; the user's selection triggers the OAuth redirect and any provider error is then surfaced clearly.
- `REQ-AUTH-012` For an existing user with an established OAuth provider binding, cross-provider fallback is not permitted even if the bound provider is temporarily unavailable. The bound OAuth provider is the fixed authentication identity for that account. If a user's bound provider is unreachable at login time, the platform must detect the OAuth failure and surface a dedicated screen: "Your sign-in provider is currently unavailable. Please try again later. If the problem persists, contact your platform administrator for account migration." The screen must not offer any workaround that would allow the user to sign in via a different OAuth provider under the same account, as that would permit account takeover via a shared-email provider. Cross-provider fallback remains prohibited even when two providers report the same email address; a distinct affirmative admin-assisted rebind per REQ-RECOVERY-005 is the only path to changing an account's bound provider.
- `REQ-AUTH-013` On every token-refresh attempt (performed on a configured schedule or at a sensitive action), if the OAuth provider responds with a token-revocation or access-denied error indicating the user has revoked consent or their provider account has been disabled, the platform must: immediately terminate the user's platform session; flag the user's record as `require_reauth`; propagate a WebSocket close to any active real-time connections with close code 4002 and message "session ended: provider access was revoked"; and redirect the user's next page load to the OAuth sign-in screen with a clear message: "Your access via [provider] has been revoked. Please sign in again." The platform must not silently extend sessions past provider-side revocation. This requirement applies to all three supported OAuth providers. **OAuth token refresh interval (EC-8):** To ensure provider-side revocation is caught within hours rather than at the next 24-hour session boundary, the platform must perform a proactive token refresh at a configurable interval during active sessions. The interval must be stored in `sys_config` under the key `sessions.oauth_refresh_interval_hours` (default 4 hours). On each scheduled refresh the platform makes a minimal OAuth introspection or userinfo call to the provider; a revocation response triggers the same immediate-termination flow above. The first refresh occurs 4 hours after login; subsequent refreshes occur at the configured interval for the duration of the session.
- `REQ-AUTH-014` **FYERS account re-binding is not supported (EC-3).** The platform assumes a stable one-to-one mapping between a platform user account and a single FYERS broker account for the user's entire platform lifetime. Re-binding to a different FYERS account — replacing a user's stored FYERS credentials with those of a different brokerage account — is not a supported workflow. If a user attempts to enter FYERS credentials for a different account (distinguished by a different FYERS user ID), the FYERS credential management flow must detect the mismatch and block the update with a clear message: "Your FYERS account ID has changed. Re-binding to a different brokerage account is not supported because it would invalidate your existing trade ledger, open positions, and portfolio history. Please contact the admin for assistance." If the user's FYERS account has genuinely changed (for example, they opened a new demat account), the admin may assist by closing all open positions through the original account, archiving the old FYERS binding, and then allowing the user to link the new FYERS account as a fresh start. This procedure is admin-assisted and must be recorded in `audit_events`. The rationale is that every open position, FIFO ledger entry, equity-curve record, and RME advisory references the original FYERS account's trades; silently re-binding would produce massive ledger mismatches that REQ-RECON-001..008 cannot resolve automatically.

### Account Recovery

*OAuth-only authentication means account loss if the user loses IdP access. This section defines the preventive option (a linked secondary IdP) and the reactive option (admin-assisted rebind). Both paths preserve all existing user state — trade ledger, positions, notifications, Signal Subscriptions — untouched.*

- `REQ-RECOVERY-001` Users must be able to link a secondary OAuth identity provider to their platform account from the user settings page (REQ-PROFILE-009). The secondary identity must differ from the primary in provider, email, or both; linking an identical identity is a no-op. Either linked identity must be sufficient on its own to complete portal sign-in and resume the same platform account. Both link and unlink events must be recorded in `audit_events` with the identity details and the actor.
- `REQ-RECOVERY-002` At most two OAuth identities may be linked to a single platform account at any time. Linking a third requires unlinking one first. Unlinking the identity currently being used to maintain the active portal session is not permitted — the user must switch to the alternate identity first, then unlink the former primary.
- `REQ-RECOVERY-003` The user settings page must surface a clearly visible warning when only a single OAuth identity is linked, explaining that loss of access to that identity would require admin-assisted recovery. The warning must link directly to the "Link alternate sign-in" flow.
- `REQ-RECOVERY-004` When a user has lost access to all linked OAuth identities, the user may request admin-assisted recovery by emailing the grievance officer. The request must provide verification items sufficient to establish identity: the original OAuth email used on the platform, the linked FYERS account number or client ID, and a recent trade reference (an order ID, or a trade date with symbol and approximate quantity). The admin must not accept recovery requests that supply fewer than all three items.
- `REQ-RECOVERY-005` Admin-assisted recovery rebinds the platform account to a new OAuth identity provided by the user. The admin must perform the rebind through a dedicated admin-portal flow — not via direct database edits. The flow must: display the user's current linked identities and supplied verification items; accept the new OAuth identity as input; require admin step-up re-authentication per REQ-SEC-011; and record the before state, after state, admin identity, target user identity, verification items supplied, and timestamp in `audit_events`. The user's existing trade ledger, positions, portfolio snapshots, notifications, Signal Subscriptions, and all other state remain untouched; only the OAuth identity binding on the `users` record changes.
- `REQ-RECOVERY-006` After admin-assisted recovery the user must complete a fresh FYERS authentication on their next sign-in; the FYERS token does not carry across the rebind. All notifications and Telegram link associations remain attached to the recovered account; no re-linking of Telegram is required.

## Part 3 — Universe and Market Data

*Implemented by .NET background worker services (DataSync, HistoricDataSeed, Universe Sync) and the ASP.NET Core API layer for provider routing. Must be operational before any Signal runs or charting can work.*

### Universe Management and Symbol Master

*Governs how the Nifty 500 symbol list is maintained in MongoDB and how symbols are kept in sync with NSE changes.*

- `REQ-UNIV-001` The platform universe is managed from the Nifty 500 CSV uploaded by the admin.
- `REQ-UNIV-002` CSV import must require the columns `Company Name`, `Industry`, `Symbol`, `Series`, and `ISIN Code`. The symbol master document must also carry a `lot_size` field (positive integer, default 1) representing the NSE minimum lot size for equity CNC orders for that symbol. The CSV does not currently include this field; the admin must manually edit the `lot_size` value through the symbol master management UI for the rare symbols with non-1 lot sizes. The `lot_size` value must be used by REQ-SIZING-010 and REQ-EXEC-004 when rounding position quantities to NSE and FYERS minimum quantity constraints. All symbols initialised by CSV import must receive `lot_size = 1` as the default; the admin is responsible for maintaining non-default values when NSE changes or introduces non-1 lot sizes for specific equity symbols. The `Industry` field is the sole classification field imported from the CSV and is the platform's canonical grouping dimension. All references to "sector" throughout the platform — including dashboard sector breakdown, sector exposure limits, sector concentration rules, and portfolio impact assessments — mean the `Industry` value from the symbol master. No separate sector field exists; the terms are synonymous within this platform.
- `REQ-UNIV-002a` When a CSV upload changes the `Industry` value for an existing symbol, the platform must update the symbol master record in place and record the change in the audit trail, including the previous and new industry values and the upload that caused the change. The updated classification must be applied immediately to all live calculations — dashboard sector breakdown, portfolio heat sector exposure, and scan sector concentration rules — from the next sync or page load. Historical closed-position records in the trade ledger must retain the industry classification that was active at the time those positions were open; the reclassification must not retroactively alter completed trade history or closed-position portfolio impact records. Any open position in the reclassified symbol must be re-evaluated against the new sector exposure limits at the next RME portfolio heat recalculation, and the user must receive a notification of type `sector_exposure_breach` as defined in REQ-NOTIFY-006 if the reclassification causes their sector exposure to breach a configured threshold.
- `REQ-UNIV-003` CSV import must compare uploaded rows against the existing MongoDB symbol master.
- `REQ-UNIV-004` CSV import must import only rows where `Series = EQ`.
- `REQ-UNIV-005` CSV import must skip rows where `Series != EQ` and report them in the upload summary.
- `REQ-UNIV-006` Symbols removed from a newly uploaded CSV must be marked archived instead of deleted.
- `REQ-UNIV-007` Archived symbols must remain queryable so prior charts, signals, trades, and audit trails continue to work.
- `REQ-UNIV-008` Archived symbols must continue to receive EOD historical sync into SQL Server.
- `REQ-UNIV-009` Admin must be able to temporarily exclude active symbols from scans without archiving them.
- `REQ-UNIV-010` Symbol master must persist both archive state and scan-exclusion state with audit trail.
- `REQ-UNIV-011` Admin upload summary must show how many new symbols were added.
- `REQ-UNIV-012` Admin upload summary must show which symbols are no longer part of the uploaded index list.
- `REQ-UNIV-013` Admin upload summary must show which symbols were skipped because `Series != EQ`.
- `REQ-UNIV-014` When a CSV upload results in net-new symbols being added to the symbol master, the platform must automatically trigger the HistoricDataSeed job scoped to those new symbols only. The job must fetch the full available historical OHLCV data for each new symbol, working backward from the current date as far as the market data provider API supports. The auto-triggered run must be recorded in `job_runs` with `triggered_by: universe_upload` and must reference the upload record from `universe_upload_results`. New symbols must not be eligible for backtesting or EOD Signal Runner evaluation until their HistoricDataSeed run completes successfully.
- `REQ-UNIV-015a` The admin CSV upload page must display the full current symbol master as a list alongside the upload interface. For each symbol the list must show: trading symbol, company name, current status (active or archived), scan-exclusion state, and data sync health. Data sync health is determined by comparing the most recent daily candle date in the symbol's SQL Server `D_` table against the most recent completed trading session from the internal trading calendar. A symbol is considered out of sync if its most recent candle date is earlier than the most recent completed trading session.
- `REQ-UNIV-015b` The CSV upload page must display a count of out-of-sync symbols and provide a single action button to trigger a targeted reseed for all out-of-sync symbols simultaneously. This reseed must invoke the HistoricDataSeed job scoped to the out-of-sync symbols only, using the standard gap-fill behaviour: for each symbol the job fetches only from its most recent successfully written date forward, filling the gap up to the current date without overwriting existing rows. The job must be recorded in `job_runs` with `triggered_by: manual_reseed` and must list the symbols included in the run.
- `REQ-UNIV-015c` While a HistoricDataSeed job triggered from the CSV upload page is in progress, the upload page must show a progress indicator and must prevent a duplicate reseed trigger for the same symbols. On completion, the symbol list must refresh its data sync health indicators automatically.
- `REQ-UNIV-015` When a CSV upload archives a symbol (transitions it from active to archived state), the platform must check whether any user has an open position in that symbol. For each user with an open position in an archived symbol, the platform must generate a notification of type `symbol_archived_with_open_position` alerting the user that the symbol has been removed from the Nifty 500 universe and that their position will no longer receive new entry signal advisories but will continue to be monitored by the RME for stop updates, add and reduce level triggers, and exit conditions until they close the position. The RME must not suspend or auto-close open positions solely because the symbol was archived; the full position lifecycle continues unchanged. The chart page must continue to show the red archived indicator (REQ-CHART-005) for the symbol. The `symbol_archived_with_open_position` type must be added to the supported notification types alongside those in REQ-NOTIFY-006.
- `REQ-UNIV-016` The CSV upload page must display an age indicator for the current symbol master derived from the most recent successful upload recorded in `universe_upload_results`. When the age exceeds a configurable threshold, the indicator must surface a warning banner prompting the admin to refresh the universe against the latest NSE Nifty 500 composition. The threshold must be seeded in `sys_config` under the key `operations.universe.stale_after_days` with a default of 180 days, reflecting the NSE semi-annual rebalance cadence. The warning is advisory and must not block other platform functions.
- `REQ-UNIV-017` Every CSV upload must present a pre-commit diff preview before any state changes are applied. The preview must list: symbols to be added (net-new rows absent from the current master); symbols to be archived (present in the current master, absent in the uploaded CSV); symbols whose `Industry` classification would change, with before and after values; and rows that would be skipped because `Series != EQ`. The admin must explicitly confirm the diff before the upload commits. An upload submitted without traversing this confirmation step must be rejected by the server even if the client attempts to bypass it.
- `REQ-UNIV-018` When the diff preview indicates that the upload would archive more than a configured percentage of the currently active symbols, the commit control must require a typed confirmation phrase matching a server-generated prompt, plus a written justification, before the upload is accepted. The threshold percentage must be seeded in `sys_config` under the key `operations.universe.archive_confirm_threshold_pct` with a default of 5 (five percent), calibrated slightly above the typical NSE semi-annual rebalance replacement rate. The typed confirmation phrase and justification must be recorded in `audit_events` alongside the upload record. This control protects against operator error from an inadvertent small or incorrect CSV file.
- `REQ-UNIV-019` Every CSV upload must retain a complete pre-upload snapshot of the symbol master for rollback purposes. Snapshots must be retained for a configurable window, seeded in `sys_config` under the key `operations.universe.rollback_retention_days` with a default of 30 days. The admin portal must provide a one-click rollback control for any upload within the retention window; a rollback reverses the symbol-master changes atomically — symbols added by that upload are removed, symbols archived by it are reactivated, and industry-classification changes introduced by it are reverted — while preserving any downstream data created in the interim (open positions, notifications, trade ledger entries, Signal runs). Rollback must be recorded in `audit_events` with the upload identifier being reversed and the actor. Rollback of an upload earlier than the most recent one must be prevented; if the admin needs to revert multiple uploads they must roll back sequentially from the most recent.
- `REQ-UNIV-020` During the Universe Sync diff preview (REQ-UNIV-017), when a CSV row introduces a new `Symbol` value whose `ISIN Code` matches the `ISIN Code` of a currently active symbol whose `Symbol` value is absent from the uploaded CSV, the diff must classify this pair as a candidate rename rather than as separate add and archive events. The preview must display the pair explicitly (old symbol → new symbol, shared ISIN) and require the admin to resolve it before commit. Two resolutions are permitted: (a) "approve rename" updates the existing symbol master record's `Symbol` in place, preserves the existing `sql_table_name_suffix` and the associated `D_`, `W_`, and `M_` tables, and preserves all historical references (trade ledger entries, closed positions, audit records); (b) "reject rename" treats the pair as a standard archive-and-add — the new symbol receives a fresh suffix and fresh `D_`, `W_`, `M_` tables materialised through the scoped HDS path per REQ-HIST-009a, and the old symbol is archived per REQ-UNIV-006. The rename decision and actor must be recorded in `audit_events` alongside the upload record and retained for the rollback window (REQ-UNIV-019). Rollback of a rename resolution must revert the symbol master value to the prior `Symbol` while leaving the suffix and tables unchanged.
- `REQ-UNIV-021` Symbol Validity Probe. On each date that has a trading session per the internal trading calendar, immediately after the admin FYERS token is successfully generated for the first time that day, the worker must run a Symbol Validity Probe covering every active symbol in the current Nifty 500 universe, including symbols with `scan_excluded = true`. The probe fetches FYERS LTP (last traded price) in batches sized by `operations.universe.symbol_probe_batch_size` (default 50), respecting the FYERS rate limits configured in REQ-RATE-003. A probe run is recorded in `job_runs` with `triggered_by: fyers_token_refresh`. The probe may be disabled for incident response via `operations.universe.symbol_probe_enabled` (default true); when disabled, the admin portal must display a visible banner noting that symbol-change detection is paused.
- `REQ-UNIV-021a` The Symbol Validity Probe must classify each per-symbol response into one of three outcomes. (a) **Success**: a valid LTP response. The `symbol_health` record for that symbol is updated with `last_successful_probe_at` set to the probe run's start timestamp and `consecutive_failure_count` reset to zero. (b) **Transient failure**: network failures, rate-limit responses, and 5xx status codes. These are retried with exponential back-off within the run per REQ-RATE-004; the final outcome after retries is recorded, but if any retry succeeds the outcome is classified as Success. A transient failure that persists after all retries is recorded as a transient-failure event on the `symbol_health` record without incrementing `consecutive_failure_count`. (c) **Unknown-symbol failure**: the specific FYERS error code indicating the symbol is not recognised by FYERS (the concrete error code is resolved by the active provider adapter and documented in the adapter contract). `consecutive_failure_count` is incremented by one and `last_unknown_symbol_at` is set to the probe run's start timestamp. `last_successful_probe_at` is not modified. Any provider error not covered by the transient or unknown-symbol classifications must be recorded with its raw error code and treated as transient for the purposes of `consecutive_failure_count`, with an operator alert raised so the adapter contract can be updated.
- `REQ-UNIV-021b` When a symbol's `consecutive_failure_count` reaches the value of `operations.universe.symbol_probe_flag_threshold_days` (default 2), the platform must add it to the admin work queue as a rename-or-delisting candidate and must surface it in the admin portal with the full recent failure history attached. The admin must resolve the flag with one of three actions: (a) **Approve rename** — admin supplies the new symbol value; the platform invokes the same in-place update path as REQ-UNIV-020 (preserves `sql_table_name_suffix` and the `D_`, `W_`, and `M_` tables); `consecutive_failure_count` is reset; the resolution is recorded in `audit_events`. (b) **Mark delisting** — the symbol is archived per REQ-UNIV-006 and REQ-UNIV-015; any open user positions receive the `symbol_archived_with_open_position` notification per REQ-UNIV-015. (c) **Dismiss** — records an audit note with an operator-supplied reason; `consecutive_failure_count` is not reset, so the probe will re-flag the symbol on the next run. Probe flags and their resolutions feed the same admin work queue as rename candidates detected by REQ-UNIV-020; when both detection paths fire for the same symbol the queue entry must be tagged `high_confidence`.

### Historical Storage and Symbol-to-Table Mapping

*Governs the SQL Server market data database layout: three tables per symbol, stable naming, and how DataSync populates weekly and monthly candles from daily data.*

- `REQ-HIST-001` SQL Server historical storage uses three tables per symbol in the market data database: one for daily candles (`D_` prefix), one for pre-computed weekly candles (`W_` prefix), and one for pre-computed monthly candles (`M_` prefix).
- `REQ-HIST-002` Each OHLCV table contains `Date`, `Open`, `High`, `Low`, `Close`, and `Volume`. This schema applies identically to the daily, weekly, and monthly tables.
- `REQ-HIST-003` MongoDB symbol master must store a stable `sql_table_name_suffix` for each symbol. Full table names are constructed at runtime by prepending the timeframe prefix: `D_{suffix}`, `W_{suffix}`, `M_{suffix}`.
- `REQ-HIST-004` SQL Server historical tables must be referenced using `sql_table_name_suffix`, not raw symbol text and not ISIN code.
- `REQ-HIST-005` `sql_table_name_suffix` must be generated deterministically from `Symbol`.
- `REQ-HIST-006` The `sql_table_name_suffix` generation algorithm must be deterministic and exhaustive: (a) uppercase the `Symbol` value; (b) replace any character not in `[A-Z0-9]` with `_`; (c) collapse consecutive underscores into a single `_`; (d) strip leading and trailing underscores; (e) truncate to 100 characters. If the cleansed result is empty, the import must reject the symbol with a clear operator error. Rule (b) applies to all non-alphanumeric characters, not only `&` and `-`.
- `REQ-HIST-007` If the sanitised name starts with a digit, it must be prefixed with `SYM_`.
- `REQ-HIST-008` Once assigned, `sql_table_name_suffix` must remain stable even if symbol metadata changes later.
- `REQ-HIST-008a` The symbol master seed process and every CSV upload that adds new symbols must validate that no two symbols in the symbol master produce the same `sql_table_name_suffix` after applying the sanitisation rules in REQ-HIST-006 and REQ-HIST-007. If a collision is detected — either at seed time or when a new symbol is imported — the import must fail loudly with a clear error identifying the colliding symbols and their generated suffixes; it must not silently assign a modified suffix or overwrite an existing table. The CSV upload summary (REQ-UNIV-003) must include a collision-check result row. Additionally, the Worker Service startup sequence must assert at boot that no duplicate suffixes exist in the current symbol master and must refuse to start if any are found, logging the colliding symbols as a fatal startup error; this guards against any collision that might have been introduced through a direct database edit or a pre-validation data import.
- `REQ-HIST-009` DataSync and HistoricDataSeed must write to all three table variants (`D_`, `W_`, `M_`) for each symbol on each sync run.
- `REQ-HIST-009a` Before writing candles to the three per-symbol tables for a symbol whose tables have not yet been materialised — specifically a symbol just added to the symbol master via a CSV upload (REQ-UNIV-014) or created as a fresh entry by a rename-reject resolution (REQ-UNIV-020(b)) — HistoricDataSeed must ensure the `D_{suffix}`, `W_{suffix}`, and `M_{suffix}` tables exist by creating any that are missing, using the shared schema defined in REQ-HIST-002 and the standard indexes defined in the shared schema template. Table creation must satisfy four constraints. **(a) Idempotency:** the creation step must use `IF NOT EXISTS` semantics so repeated invocation and retry after partial failure are safe; a second HDS run for the same symbol must succeed without error when tables already exist. **(b) Per-symbol atomicity:** the creation of the three tables for a single symbol must execute inside one database transaction so a mid-creation failure cannot leave the symbol with one or two of the three tables present; partial state of this kind is treated as a correctness defect. Atomicity applies per symbol, not across symbols — a scoped HDS run for multiple new symbols may create tables for symbol A and fail on symbol B without rolling back A's tables. **(c) Single shared schema template:** the column definitions and index specifications for the three per-symbol tables must be held as a single shared DDL template — either as a FluentMigrator migration that renders the DDL at runtime, or as a parameterised DDL helper keyed by the timeframe prefix — so that a future change to the per-symbol table shape is a single edit that flows through REQ-MIGRATION-004 for existing symbols and through this requirement for newly-added symbols; divergence between the template used by this requirement and the template used by REQ-MIGRATION-004 is treated as a defect. **(d) Auditability:** each table-creation event must be written to the `job_runs` record for the HDS run with the symbol, the `sql_table_name_suffix`, and the three table names created, so that the admin job log makes every table materialisation visible. The combination of REQ-HIST-009 and REQ-HIST-009a must cover the full lifecycle: REQ-HIST-009a brings the three tables into existence when a symbol joins; REQ-HIST-009 writes candles into them on every subsequent sync run. Per-symbol table creation under this requirement is explicitly outside the scope of REQ-MIGRATION-004, which governs fleet-wide schema evolution across already-existing per-symbol tables.
- `REQ-HIST-010` Weekly candles in `W_` tables must span from the first to the last trading session of each ISO calendar week as defined by the internal NSE trading calendar. Monthly candles in `M_` tables must span from the first to the last trading session of each calendar month. DataSync is responsible for deriving and upserting these from the daily data it has ingested.
- `REQ-HIST-011` Every platform component that requires an SQL Server table name for a symbol must obtain it through a single shared mapping service (for example `ISymbolTableMapping`). Components must not construct table names by applying the REQ-HIST-006 cleansing algorithm directly in their own code. The mapping is loaded in memory from `symbol_master` at application startup and refreshed on successful completion of each Universe Sync. This rule binds the charting layer, the backtesting engine, the EOD Signal Runner, and any other consumer of SQL Server historical data; divergence between consumers is treated as a defect.
- `REQ-HIST-010a` The weekly candle boundary algorithm must handle NSE special sessions — including Muhurat trading sessions that fall on a Saturday, Sunday, or public holiday — using the following explicit rules: (a) **Week assignment:** a session's ISO calendar week is determined by the session date in `Asia/Kolkata`; sessions that fall on a Saturday or Sunday (including Muhurat sessions) are assigned to the ISO week that contains that date, consistent with the ISO 8601 definition where weeks run Monday through Sunday. (b) **Single-session weeks:** if an ISO week contains exactly one trading session (for example, a Muhurat session on a Saturday that is the only session in that ISO week because all weekdays were exchange holidays), the weekly candle for that week is built from that single session; it is a valid one-day weekly candle with equal open, high, low, and close derived from the session's daily candle. (c) **Cross-week Muhurat sessions:** if a Muhurat session falls on a Sunday that ISO 8601 assigns to the following week (noting that ISO 8601 weeks start on Monday, so Sunday belongs to the *prior* week — day 7 of the week), the session is assigned to the prior week per ISO 8601. No session is ever split across two weekly candles. (d) **Consistency requirement:** the weekly candle boundary logic must be identical across DataSync (for `W_` SQL Server tables), the charting layer (for displayed weekly candlestick charts), and the backtest engine (for weekly-timeframe backtests); any divergence between these three consumers is a defect. The single authoritative boundary implementation must reside in a shared library or service used by all three consumers, not duplicated per consumer.

### Trading Calendar and Timeframes

*The internal NSE trading calendar is the single authoritative source for all session-based calculations across the platform. All components must use it.*

- `REQ-CALENDAR-001` The platform must maintain an internal NSE trading calendar in `Asia/Kolkata`.
- `REQ-CALENDAR-002` The admin must be able to add or update all record types in the internal calendar: normal trading sessions, special sessions, Muhurat trading sessions, and explicit non-trading-day markers. Session records (the first three types) must store the session date, session type, session start time, and session end time in `Asia/Kolkata`; the platform treats them as valid trading sessions and uses their times as the authoritative market hours for that day. An explicit non-trading-day marker stores only the date and an optional holiday name; it carries no session times and unambiguously signals that the exchange is closed on that day. The distinction between a session record and a non-trading-day marker is the mechanism by which REQ-CALENDAR-007 distinguishes intentional closures from unconfigured dates.
- `REQ-CALENDAR-003` The internal trading calendar is the shared authority for chart aggregation, rolling timeframes, weekly/monthly boundaries, EOD sync timing, scans, and stop monitoring.
- `REQ-CALENDAR-004` The default EOD sync schedule must run after exchange close and post-close processing, with `17:00 IST` as the initial default unless changed operationally.
- `REQ-CALENDAR-005` All scheduled background jobs that depend on market activity — including DataSync, the EOD Signal Runner (EODSR), EOD stop-level updates, and intraday account sync — must check the internal NSE trading calendar at startup before performing any work. If the current date has no session record in the internal calendar — or has an explicit non-trading-day marker (per REQ-CALENDAR-002) — the job must exit immediately with a status of `skipped_holiday` and record this outcome in `job_runs`. A holiday skip must not be treated as a failure and must not trigger alerts or retry logic. The intraday account sync polling loop (REQ-PORT-019) and the Live Market Data Scan (LMDS, REQ-STOP-006) must additionally check the calendar before each poll cycle and cease polling for the remainder of the session if the session is detected as a holiday mid-run.
- `REQ-CALENDAR-006` Wherever the platform must determine whether it is currently within market hours — including the Live Market Data Scan (LMDS, REQ-STOP-006a), the intraday account sync polling loop (REQ-PORT-019), live quote fetching (REQ-DASH-003), and the Phase 1 order modal market-hours indicator (REQ-ORDER-018) — it must derive the session start and end times from the current day's session record in the internal trading calendar. No component may hardcode session times. If the current day has no session record, it must be treated as outside market hours.
- `REQ-CALENDAR-007` The admin portal must perform a Calendar Coverage check and display a persistent non-blocking warning whenever any weekday (Monday through Friday in `Asia/Kolkata`) within the next 30 calendar days from today has neither a session record nor an explicit non-trading-day marker in the internal trading calendar. Such a date is classified as an **unconfirmed date**: it cannot be distinguished from a forgotten entry, because REQ-CALENDAR-005 silently skips jobs on any unconfigured date. The warning must name the count of unconfirmed weekdays and the earliest such date, and must link directly to the admin Calendar page. The admin must resolve each unconfirmed date by either: (a) adding the appropriate session record if it is a trading day, or (b) adding an explicit non-trading-day marker (per REQ-CALENDAR-002) if the exchange is closed on that day. The warning must clear automatically as dates are resolved and must re-appear as the rolling 30-day window advances. The Calendar Coverage status — number of unconfirmed weekdays in the next 30 days — must also be surfaced on the Legal Posture widget (REQ-LEGAL-010) alongside other phase-readiness indicators, and must reach zero before a phase transition from A to B is permitted.
- `REQ-TIMEFRAME-001` Supported global timeframes must include daily, weekly, monthly, and rolling 3-day, 5-day, and 7-day views.
- `REQ-TIMEFRAME-002` Rolling timeframe candles must be built from trading sessions, not calendar dates.
- `REQ-TIMEFRAME-003` In a rolling 3-day candle, the opening bar is the oldest included trading session and the closing bar is the most recent trading session in the window.
- `REQ-TIMEFRAME-004` The same timeframe definitions must be used consistently in charting, Signal runs, EOD Signal Runner evaluation, and backtesting.
- `REQ-TIMEFRAME-005` Weekly and monthly candles in charting and backtesting must be sourced directly from the pre-computed `W_` and `M_` SQL tables for the relevant symbol. They must not be re-derived at query time from daily data.
- `REQ-TIMEFRAME-006` Rolling window candles (rolling 3-day, 5-day, 7-day) must be computed on demand from the daily `D_` tables. No dedicated SQL table is maintained for rolling window candles.

### Market Data Provider and EOD Sync

*Covers the provider abstraction layer design (REQ-MKTPROV) and the specific behaviour of DataSync and HistoricDataSeed jobs (REQ-MARKET). The abstraction must be implemented first; the jobs depend on it.*

#### Provider Abstraction

- `REQ-MKTPROV-001` The platform must implement a market data provider abstraction layer so that the source of shared historical OHLCV data and real-time quotes can be changed through configuration without code changes.
- `REQ-MKTPROV-002` All components that need market data must call through the provider abstraction; no component may bind directly to a specific provider's API.
- `REQ-MKTPROV-003` The initial supported providers must include FYERS (using the admin daily token) and at least one third-party provider such as TrueData or Global Data Feeds.
- `REQ-MKTPROV-004` Each provider implementation must conform to a common market data interface exposing at minimum: fetch historical daily OHLCV candles for a symbol over a date range, and fetch the latest real-time or delayed quote for a symbol.
- `REQ-MKTPROV-005` The active market data provider must be selectable through an admin-managed configuration setting. Switching providers must never require a code deployment. A rolling application restart to pick up the new provider is acceptable and must be covered by standard deployment health-check probes so that user-visible disruption is minimal; hot-swap without restart is not required.
- `REQ-MKTPROV-006` Provider credentials such as API keys for third-party providers must be stored in Azure Key Vault or equivalent secret storage and must never be placed in `sys_config` or source control.
- `REQ-MKTPROV-007` When a third-party provider is the configured market data provider, market data ingestion must operate independently of the admin FYERS token; the admin FYERS token is then required only for user account data workflows.
- `REQ-MKTPROV-008` The user's FYERS token must never be used for shared market data ingestion regardless of which market data provider is configured.
- `REQ-MKTPROV-009` FYERS must always remain the provider for user-specific account data including positions, orders, trades, and profile data; this is not configurable.
- `REQ-MKTPROV-010` The admin portal must display which market data provider is currently active and the last successful data fetch timestamp for that provider.
- `REQ-MKTPROV-011` When displaying live quotes and real-time price data in the portal, the platform must use the individual logged-in user's FYERS token to fetch that data; this distributes API load across user sessions rather than routing live portal requests through the admin market data provider.
- `REQ-MKTPROV-012` Historical OHLCV chart data served to the portal must be read from SQL Server via the API layer; live and intraday price updates displayed in the portal must be fetched at display time using the user's FYERS token.
- `REQ-MKTPROV-013` Background jobs including DataSync, HistoricDataSeed, and the EOD Signal Runner must use the admin-configured market data provider; they must never use a user's FYERS token for this purpose.

#### EOD Sync Jobs

- `REQ-MARKET-001` The platform must route all shared market data access through the configured market data provider; the provider is an abstracted, swappable integration layer.
- `REQ-MARKET-002` When FYERS is the configured market data provider, shared symbol and market-data ingestion jobs must use the admin FYERS token.
- `REQ-MARKET-002a` All backend services (the API service and all Worker Service jobs — including DataSync, HistoricDataSeed, the EOD Signal Runner, the Live Market Data Scan, and the Live Account Data Scan) must access the market data provider and the broker exclusively through REST interfaces. Backend services must never open or consume the FYERS Data WebSocket, nor any equivalent streaming channel offered by a future market data provider, for market data or account data ingestion. This rule preserves uniform rate-limit accounting, retry handling, observability, and provider-portability across adapters and keeps the Market Data Provider abstraction surface narrow.
- `REQ-MARKET-002b` The FYERS Data WebSocket may be used in the browser tier (the Next.js portal) only, connected directly to FYERS using the logged-in user's access token, for live chart and in-browser quote refresh. The backend must not proxy, relay, or multiplex this stream on behalf of the browser. This use is scoped to Portal Live Data per the Market Data Provider boundaries in `docs/system-architecture.md` and is subject to the same CSP allow-list that governs the FYERS API Connect widget origin.
- `REQ-MARKET-002c` FYERS is the initial market data provider because its market-data APIs are free of cost during the testing and evaluation phase. The platform is explicitly designed to migrate to a third-party commercial data provider (TrueData, Global Data Feeds, or equivalent) ahead of broader rollout. All FYERS-specific quirks — rate-limit accounting semantics, daily admin token renewal, bulk-quote symbol batch size, per-second and per-minute pacing — must remain encapsulated behind the Market Data Provider abstraction so that migration is a configuration and adapter change, not a domain-code change. Future documentation reviews must not treat FYERS as the long-term market data provider.
- `REQ-MARKET-002d` Before the Phase B transition, the platform must demonstrate that the Market Data Provider abstraction boundary holds under a real provider swap. A cross-provider swap integration test must be included in the Phase B test suite that: (a) sets `market_data.provider.active` in `sys_config` to a stub or canned-response TrueData adapter; (b) runs DataSync, the EODSR, and a representative chart-data fetch end-to-end against the stub adapter's canned OHLCV responses; (c) asserts that all three flows complete successfully and that no code path hard-codes any FYERS-specific constant, API pattern, or authentication flow. This test validates the abstraction's promise that migration is a configuration and adapter change, not a domain-code change. The stub adapter is a Phase B deliverable per ADR-0005; this requirement gates the Phase B transition on its existence and on the passing swap test.
- `REQ-MARKET-003` After market close, a post-market DataSync job must refresh SQL Server historical data before any end-of-day signal scan runs.
- `REQ-MARKET-004` When FYERS is the configured market data provider, the DataSync job must require a valid admin FYERS token; the existing dirty-token and re-auth rules apply. **Operational note:** FYERS access tokens are day-scoped; when FYERS is the active market data provider the admin must generate a fresh FYERS token each trading day before EOD sync runs. The persistent admin portal warning defined in REQ-SESSION-009 is the sole notification mechanism for a missing or expired admin token. No automated proactive reminder is provided — this is an operator responsibility. When the active market data provider is switched to a third-party provider such as TrueData or GDF, the admin FYERS token is no longer required for market data ingestion and this daily renewal obligation falls away entirely.
- `REQ-MARKET-005` If the market data provider is unavailable or authentication fails, the DataSync job must fail and the EOD Signal Runner must abort for that session. **Loud failure on stale admin token (S-3):** When the DataSync job or the Live Market Data Scan (LMDS) starts and detects that the admin FYERS token is absent, expired, or dirty, the failure must not be silent. The job must: (a) abort immediately with a structured log entry at Error level naming the job, the provider, and the reason (`admin_token_absent`, `admin_token_expired`, or `admin_token_dirty`); (b) immediately emit an `admin_fyers_token_expiry_warning` notification of type `admin_fyers_token_expiry_warning` (as defined in REQ-NOTIFY-022) via both Telegram and email unconditionally, regardless of whether the daily scheduled check has already fired one for this session — a job-startup stale-token detection is treated as an independent trigger that always fires, separate from the at-most-one-per-session limit that applies to the scheduled check. This ensures that if the admin fails to refresh the token before LMDS starts at market open, the failure produces an immediate dual-channel admin alert rather than silent LMDS degradation throughout the trading day.
- `REQ-MARKET-005a` DataSync must re-check admin token validity at every batch boundary during a 10-session recovery run. If the token has expired mid-run (i.e., was valid at job startup but a batch fails with a token-expired error), DataSync must exit immediately with outcome `partial_completion_token_expired`, recording in `job_runs` how many sessions and symbols completed successfully before the expiry, and emitting the same dual-channel `admin_fyers_token_expiry_warning` notification defined in REQ-MARKET-005. This prevents DataSync from failing randomly mid-batch on transient HTTP errors that would otherwise be indistinguishable from token expiry, and gives the admin a clear audit trail of how much recovery was completed before the token expired.

- `REQ-MARKET-006` If today's daily data is unavailable for a specific symbol, that symbol may be skipped from the scan for that session while the rest of the eligible universe continues.
- `REQ-MARKET-007` The DataSync job must write an explicit success marker for the trading session so the EOD Signal Runner knows when it is safe to start.
- `REQ-MARKET-008` The admin portal must provide a way to trigger or retry DataSync and the EOD Signal Runner manually when scheduled execution fails or needs operator intervention. If an admin attempts to manually trigger a job that is already in a running state, the platform must reject the request and display a clear message stating that the job is currently running, along with its start time. A duplicate manual trigger must never spawn a second concurrent instance of the same job.
- `REQ-MARKET-009` The post-market DataSync job must fetch daily candles from the current trading session minus 10 sessions through the current session to automatically recover from missed sync days or missed admin token generation.
- `REQ-MARKET-010` A separate HistoricDataSeed job must be available for operator-triggered execution to seed SQL Server with historical daily candles for all active symbols. The default behaviour in all invocations is gap-fill: the job identifies the most recent successfully written date per symbol and fetches only from that date forward, leaving existing rows untouched. For operator-triggered manual runs from the admin portal, an optional from-date parameter may be provided; when supplied, the job overwrites rows from that date forward for the targeted symbols, providing a corrective path for known bad data. A full-wipe of all historical data is not exposed through the platform UI and must only be performed as a direct database operation by an operator. The job fetches backward from the current date as far as the market data provider API supports when no existing data is present for a symbol.
- `REQ-MARKET-011` HistoricDataSeed API calls must be batched to respect the market data provider's per-call data point limits and any applicable rate limits; the job must be resumable if interrupted.
- `REQ-MARKET-012` HistoricDataSeed must not run automatically as part of the regular post-market schedule. It may only be triggered in two ways: by an operator explicitly invoking it from the admin portal (full-universe seed or targeted reseed), or automatically as a scoped event-driven invocation when net-new symbols are added via a CSV upload per REQ-UNIV-014.
- `REQ-MARKET-013` DataSync and HistoricDataSeed must validate each OHLCV candle before writing to SQL Server. A candle is invalid if: High is less than Low, any of Open, High, Low, or Close is zero or negative, or Volume is negative. Invalid candles must be rejected and logged with the symbol, date, and failing rule; they must never be written to SQL Server.
- `REQ-MARKET-014` If a candle for a specific symbol and session fails data quality validation, that symbol must be skipped from that session's scans in the same way as a missing candle per REQ-MARKET-006. The failure must be recorded in the job run log.
- `REQ-MARKET-015` If the proportion of invalid candles across all symbols in a single DataSync run exceeds a configurable threshold, the job must abort with a clear error rather than continuing to write, to prevent a bad data batch from silently corrupting the dataset. The threshold must be seeded in `sys_config`.
- `REQ-MARKET-016` On any failure of the shared-ingestion admin FYERS token — including a failed daily token generation, a mid-session token expiry, or a failed token refresh attempt — the platform must enter an asymmetric degraded state with the following precise scope: (a) **LMDS (Live Market Data Scan)** must suspend immediately for the current and all subsequent poll cycles until the shared-ingestion token is successfully re-established; all open positions must display the "Level monitoring suspended" indicator per REQ-STOP-006b; (b) **DataSync** must suspend and the EOD Signal Runner must skip its next entry-signal evaluation per REQ-MARKET-005 if the token is not restored before the EODSR window opens; (c) **EODSR** (EOD Signal Runner) must not emit any entry signals for the session in which the shared-ingestion token is unavailable; it must record the run as `skipped_token_unavailable` in `job_runs`; (d) **LADS** (Live Account Data Scan) is unaffected — it uses individual user tokens and must continue running; (e) **per-user live PLD quotes and charts** are unaffected — they use individual user tokens and must continue rendering; (f) **RME exit advisories, position monitoring flags, and Notification Delivery Job** are all unaffected and must continue; (g) **admin dashboard banner** must appear immediately on token failure with the message "Shared-ingestion suspended: admin FYERS token refresh failed — LMDS and DataSync are halted. Last successful token at [timestamp]. Re-authenticate to restore." The banner must remain visible until the token is successfully restored. A **Telegram message must also be sent to the configured admin Telegram chat** with the same information at the moment of first failure; it must not be re-sent on every subsequent poll cycle to avoid alert fatigue. Resume is automatic on the next successful admin FYERS token fetch; LMDS and DataSync resume their next scheduled cycle without requiring an explicit admin action beyond re-authenticating. The asymmetric degraded state — users can see their own live data and exit positions, but inbound entry-signal generation and shared stop monitoring are suspended — must be documented in `docs/system-architecture.md` under the MDP failure modes section.
- `REQ-MARKET-017` **Historical OHLCV gap-repair procedure (U-3).** The DataSync job auto-recovers from missed sessions within a rolling 10-session lookback window (REQ-MARKET-009). For gaps larger than 10 sessions — caused by extended provider outages, a prolonged admin token outage, or other multi-day data-loss events — the operator must follow the explicit gap-repair procedure below. (a) **Detection:** the admin CSV upload page's out-of-sync symbol list (REQ-UNIV-015a) identifies symbols whose most-recent daily candle pre-dates the most-recent completed trading session. Symbols whose gap exceeds the configurable threshold seeded in `sys_config` under `operations.universe.gap_repair_threshold_sessions` (default 10 sessions) must be highlighted as requiring gap-repair rather than standard reseed; (b) **Initiation:** the admin triggers a targeted HistoricDataSeed run from the admin portal (REQ-MARKET-010) scoped to the affected symbols, supplying an explicit `from_date` parameter set to the day after the last successfully written candle; (c) **Execution:** the HistoricDataSeed job fills the gap using the gap-fill mode defined in REQ-MARKET-010 — fetching from the supplied `from_date` forward, leaving existing rows untouched, and re-deriving `W_` and `M_` candles per REQ-HIST-010; (d) **Completion and verification:** on completion the job records each symbol and the date range repaired in the `job_runs` entry; the admin must verify the out-of-sync indicator in REQ-UNIV-015a clears for all targeted symbols before triggering any EODSR run that covers those symbols; any symbol for which the configured market data provider cannot supply the full gap range (provider historical lookback shorter than the gap) must be logged as `gap_unrecoverable` in `job_runs` and surfaced in the admin portal — the admin must manually decide whether to archive that symbol or accept a permanent data gap and annotate it in the job log; the platform must not silently accept a partial gap repair as a full gap repair. The full step-by-step procedure, including recovery from provider-API-limit exhaustion mid-repair and from partial failures, must be documented in the DataSync failure recovery runbook at `docs/operations/runbooks/datasync-failure-recovery.md`.

### API Rate Management

*Implemented by a centralised throttling layer in the .NET application layer. Every call to FYERS or any third-party market data provider from any component must pass through this layer.*

- `REQ-RATE-001` The platform must implement a centralised API request throttling layer that all components use when calling FYERS or any configured third-party market data provider; no component may call these APIs directly bypassing this layer.
- `REQ-RATE-002` The throttling layer must enforce configurable per-second, per-minute, and per-day call limits stored in `sys_config` so limits can be updated by the admin without a code deployment.
- `REQ-RATE-003` The default FYERS rate limit values must be seeded in `sys_config` as: 10 calls per second, 200 calls per minute, and 100,000 calls per day. **The 100,000 calls/day figure is an unverified estimate and must be confirmed against FYERS's current published API documentation for the algo trading app tier before Phase 2 (market data) implementation begins.** FYERS has historically offered 10,000–50,000 calls/day on some app tiers; if the verified limit is lower than 100,000, the seed value must be updated and the FYERS API budget model (REQ-RATE-011, `docs/operations/fyers-api-budget.md`) must be recalculated before any Phase 2 code that depends on the budget model is written. The verification must be performed against the FYERS API documentation current at the time of implementation, not the documentation current at the time this requirement was written; the verified limit and its source URL must be recorded as a comment in the `sys_config` seed file alongside the key.
- `REQ-RATE-004` The throttling layer must use a request queue with exponential back-off when a rate limit response is received; rate limit errors must be treated as transient and retried automatically.
- `REQ-RATE-005` If a background job is significantly delayed due to rate limiting, the delay duration must be logged and surfaced as a warning through the standard observability model.
- `REQ-RATE-006` If rate limiting prevents a job from completing before its next scheduled run window, the job must fail with a clear error and the failure must be observable and alertable.
- `REQ-RATE-007` Live scan polling intervals and post-market sync batch sizes must be configured to keep total daily FYERS API calls within the configured daily limit across all concurrent consumers.
- `REQ-RATE-008` The admin portal must display current FYERS API call consumption for the day alongside the configured daily limit so the operator can monitor headroom.
- `REQ-RATE-009` The throttling layer must enforce separate, independently configurable rate limits for each third-party market data provider (TrueData, Global Data Feeds, and any future providers). Default rate limits for each supported provider must be seeded in `sys_config` under the `integrations` category. A rate limit response from one provider must not affect calls to any other provider or to FYERS.
- `REQ-RATE-010` Observable daily call consumption metrics must be maintained per provider so the operator can monitor API headroom for each integration independently.
- `REQ-RATE-011` The platform must maintain a documented FYERS API daily call budget model covering the expected consumption from DataSync (DS), HistoricDataSeed (HDS), the EOD Signal Runner (EODSR) market-data reads, the Live Market Data Scan (LMDS), and admin operations, evaluated at the currently configured values of `jobs.live_market_scan.poll_interval_seconds`, `jobs.account_sync.intraday_interval_minutes`, approved user count, and typical open-position count per user. The model must be stored as a reviewable artefact in operational docs and must be refreshed whenever any input changes. The admin portal must surface the currently modelled daily consumption against the configured daily limit (`integrations.fyers.rate_limit.per_day`), alongside the actual previous-day consumption, so the admin can compare projection to reality.
- `REQ-RATE-012` When the admin edits any sys_config value that affects the FYERS daily budget — specifically `jobs.live_market_scan.poll_interval_seconds`, `jobs.account_sync.intraday_interval_minutes`, `integrations.fyers.rate_limit.per_day`, `risk.default.max_concurrent_positions`, or `operations.phase_a.tester_ceiling` — the admin portal must recalculate the modelled daily consumption in real time and display a warning when projected consumption would exceed 80% of the configured daily limit. The projection method is: **already-consumed calls in the current UTC calendar day** (read from the rate-management telemetry store) **plus projected calls for the remainder of the day under the new settings** (computed from the new config values against the remaining market-hours window, using the budget model in `docs/operations/fyers-api-budget.md`). This projection method is chosen over a "full day at new settings" projection because it avoids penalising mid-session admin saves for consumption that has already occurred and cannot be undone. The daily budget counter resets at UTC midnight; this reset boundary is used consistently by the rate-management layer and must be recorded in `docs/operations/fyers-api-budget.md` alongside the calculation method. A `sys_config` key `integrations.fyers.rate_limit.reset_boundary` with default value `utc_midnight` must be seeded to allow future providers (TrueData, GDF) to declare a different reset boundary if their accounting differs. Saving a value that would breach the 80% threshold under this projection requires the admin to enter a justification, which is recorded in `audit_events` alongside the config change.

### Market-Wide Halt Detection

*Auto-detects NSE index-level circuit breakers (10% / 15% / 20% halts) via the Live Market Data Scan (LMDS) rather than relying on admin-initiated flags. Governs platform behaviour during a halt across LMDS, the order modal, account sync, and notifications.*

- `REQ-HALT-001` The platform must auto-detect market-wide trading halts during NSE market hours using a heuristic implemented in the Live Market Data Scan (LMDS). The heuristic enters halt state when, across N consecutive LMDS poll cycles, price and last-trade fields for at least P% of the polled symbols remain identical to the previous poll with no new trade prints. The thresholds must be configured in `sys_config` under the `market_data` category: `market_data.halt.consecutive_stale_polls` (default 3) and `market_data.halt.stale_symbol_pct` (default 80). The heuristic must evaluate only during market hours as defined by the internal trading calendar; outside market hours no halt state is inferred.
- `REQ-HALT-002` The admin may force-set or force-clear the market halt state through the admin portal as a safety valve for cases where auto-detection misfires or lags the real exchange behaviour. Manual overrides must be recorded in `audit_events` with actor, timestamp, and justification, and supersede the heuristic's inferred state until either the admin clears the override or the next session starts. The admin portal must visibly distinguish an auto-detected halt from an admin-override halt.
- `REQ-HALT-003` On entry into halt state the platform must: record a halt-start event in `audit_events` with detected time, inferred or overridden source, and the triggering metric values; write a `market_halt_active` notification to every user with at least one position in PendingEntry or Open state, delivered through the standard notification pipeline; flag every such position with a visible "market halted" indicator on the positions summary page and on the chart page; and suspend generation of stop-breach, add-advisory, and reduce-advisory notifications for the duration of the halt. LMDS must continue polling throughout the halt so the platform can detect halt end and so restored price movement is captured immediately on resumption.
- `REQ-HALT-004` On exit from halt state the platform must record a halt-clear event in `audit_events` and write a `market_halt_cleared` notification to every user previously alerted. Suspended advisory generation resumes on halt clear. Any stop breach that would have fired during the halt window must be re-evaluated against the first post-clear LMDS poll and emitted as a standard stop-breach notification if it is still valid; this ensures users are not left with undetected breaches accrued during the halt.
- `REQ-HALT-005` During an active market halt the Phase 1 order confirmation modal must display a prominent non-blocking warning above the confirm button stating that the market is halted and that FYERS is likely to reject the order. The user may still submit; exchange-window enforcement remains FYERS's responsibility in Phase 2 per REQ-ORDER-018. The halt warning must be visually distinct from the out-of-hours indicator defined in REQ-ORDER-018 so that the two states are never confused. **In-progress modal halt detection (U-10):** If a market halt is detected via WebSocket per REQ-NFR-013 while the Phase 1 modal is already open, the modal must auto-display the halt warning without requiring the user to close and reopen it (the server pushes the halt event; the portal receives it and updates the open modal). The signed payload and any filled-in order parameters must remain intact so the user can review their intent against the halt context and decide whether to proceed or close the modal. The modal must not close automatically on halt detection — auto-closing would surprise the user and lose their parameter choices. The user retains full discretion to submit despite the halt warning or to dismiss the modal.
- `REQ-HALT-006` During an active market halt the intraday Live Account Data Scan (LADS) must skip polling cycles until the halt clears. Skipped cycles must be logged in `job_runs` with outcome `skipped_market_halt` and must not be treated as failures. The first cycle after halt clear must run immediately to re-establish current broker state per REQ-PORT-019.
- `REQ-HALT-007` The market halt state must be treated as a `catastrophic gap or circuit stop` condition for the purposes of the exit priority order defined in REQ-STOP-012. When the halt clears and stop breaches are re-evaluated under REQ-HALT-004, the re-evaluation must honour this priority.
- `REQ-HALT-008` The `market_halt_active` and `market_halt_cleared` notification types must be added to the list of supported user-facing notification types alongside those enumerated in REQ-NOTIFY-006. Each notification's content must include the detected halt time (or halt-clear time), the inferred or overridden source, and — for `market_halt_active` only — a clear statement that no new stop, add, or reduce advisory notifications will fire for the duration of the halt.

## Part 4 — Signals and Research

*Implemented by a .NET Signal service (Signal types, backtest runner) and the SQL Server backtest database. Depends on Part 3 (market data) being operational.*

> **Naming note:** All requirement IDs in this part use the `REQ-STRAT-` prefix, which was assigned before the component was renamed from "Strategy" to "Signal." The prefix is stable and will not change. Whenever you see `REQ-STRAT-`, read it as a Signal requirement. The canonical names — Signal, Signal Subscription, entry signal, Signal Builder, EOD Signal Runner — are defined in `docs/terminology.md` and must be used in all code, logs, and documentation going forward.

### Signal Types and Backtesting

*Signal types are post-market opportunity scanners that emit entry signals only. Everything after signal emission is owned by the RME (Part 5).*

- `REQ-STRAT-001` The platform must support multiple named Signal types, each with a defined purpose, configurable parameters, and a configured timeframe.
- `REQ-STRAT-001a` Signal types are defined and deployed by developers as coded implementations. Users subscribe to available Signal types and configure their parameters within the bounds each Signal type exposes. The Signal Builder is a subscription configurator, not a Signal logic authoring tool. Adding a new Signal type requires a developer code change and deployment. Removing a Signal type from the codebase is prohibited without first disabling it via the admin portal (REQ-ADMIN-011); a Signal type must remain in a disabled state for at least one full release cycle before its code is removed to ensure no active subscriptions or open positions reference it. Each Signal type implementation must carry a stable string identifier that is persisted on Signal Subscription records, entry signal records, and backtest run records; this identifier must never be reused for a different Signal type.
- `REQ-STRAT-002` Examples of Signal types include Price Volatility Signal, Volume Spike Signal, and similar post-market opportunity scanners; the platform must be extensible to add new Signal types without structural changes to the surrounding Signal engine, subscription model, or notification pipeline.
- `REQ-STRAT-003` Each Signal type must have a human-readable name that is included in all alerts and notifications generated by that Signal type.
- `REQ-STRAT-004` Each Signal type must record the timeframe it ran on and include that timeframe in all alerts and notifications it generates.
- `REQ-STRAT-005` Users must be able to subscribe to one or more developer-defined Signal types and configure their parameters per Signal Subscription.
- `REQ-STRAT-006` Signal parameters must be user-configurable and persisted per Signal Subscription.
- `REQ-STRAT-007` Users must be able to choose timeframes and indicator parameters as part of their Signal Subscription configuration.
- `REQ-STRAT-007a` Users must be able to pause a Signal Subscription without deleting it. While paused, the Signal Subscription must not be evaluated by the EOD Signal Runner and must not generate entry signals. Open positions (in Open state) opened under the Signal Subscription are not affected; the RME continues monitoring them regardless of subscription pause state, including all advisory types — stop level updates, add advisories, reduce advisories, trailing stop updates, and exit advisories all continue to fire normally. All advisory notifications and portal alerts generated for Open positions under a paused Signal Subscription must include a visible note stating that the parent Signal Subscription is currently paused; this applies to both Telegram notifications and the portal notification feed. Any PendingEntry position associated with the paused Signal Subscription must be immediately transitioned to Suspended state with reason `subscription_paused` at the moment of pause. On subscription resume, those suspended PendingEntry positions must not be automatically reinstated; they remain Suspended until superseded by a fresh EOD Signal Runner entry signal per REQ-PLC-009 or until they expire per REQ-PLC-008.
- `REQ-STRAT-007b` A paused Signal Subscription must be clearly labelled as inactive in the Signal list. Users must be able to resume a paused Signal Subscription at any time, after which it participates in the next eligible EOD Signal Runner run. **Pause/resume during in-flight EODSR (EC-6):** If a user pauses or resumes a Signal Subscription while an EODSR run is in progress, the pause or resume state change must not affect the in-flight run. The EODSR always completes under the subscription state it read at the start of the run; state changes applied during the run take effect from the next eligible EOD run. This ensures atomic-run semantics (REQ-STRAT-027) are not broken by concurrent user state changes. The new state (paused or active) is persisted to MongoDB immediately on user action; the EODSR reads subscription state once at job start and does not re-read it per-symbol or per-cycle during the run.
- `REQ-STRAT-008` Scan logic must support long-entry opportunity identification only in the current platform.
- `REQ-STRAT-009` Backtests must run against SQL Server historical data.
- `REQ-STRAT-010` Backtest runs must be reproducible against a defined historical data slice.
- `REQ-STRAT-011` Standard backtests must use the current active Nifty 500 universe.
- `REQ-STRAT-011a` Backtests using the current active universe introduce survivorship bias: symbols removed from the Nifty 500 before the backtest is run are not included, which may make historical results appear better than they would have been in live trading. The backtest result record and result UI must display a prominent caveat stating that the universe is current-state and that results are subject to survivorship bias. Point-in-time universe tracking is deferred to a later phase per REQ-NEXT-009.
- `REQ-STRAT-011b` To make the survivorship bias caveat operational rather than cosmetic, the platform must apply a configurable survivorship bias discount to the headline expectancy figure displayed in the backtest result UI. The discount is expressed as a percentage reduction applied to the raw expectancy value before display; the discounted value must be labelled clearly as "Survivorship-Bias-Adjusted Expectancy" and the raw (unadjusted) value must also be shown alongside it so the user can see both figures. The discount percentage must be seeded in `sys_config` under the key `strategies.backtest.survivorship_bias_discount_pct` with a default of 15 (representing a 15% reduction in expectancy). The admin may adjust this value based on calibration against historical Nifty 500 reconstitution data; every change must be recorded in `audit_events`. When the discount is set to zero, only the raw expectancy is shown and the adjustment label is suppressed. The discount applies only to the result display; underlying per-trade data, equity curves, and all other backtest metrics are stored and displayed at their raw computed values. This discount does not replace the textual caveat required in REQ-STRAT-011a; both the discounted figure and the caveat text must appear together on every backtest result screen.
- `REQ-STRAT-011c` Every backtest result must include a computed **universe coverage percentage** — the proportion of symbols in the active Nifty 500 universe for which at least one valid price candle existed across the entire backtest date range — stored on the backtest result record. The backtest result screen must display this figure as an informational annotation: "Historical universe coverage: X% — results may be optimistic (symbols that were delisted or excluded before this run are not represented)." This annotation is the primary mechanism for helping users interpret survivorship-bias risk and must always appear regardless of the discount setting in REQ-STRAT-011b. When universe coverage falls below a configurable threshold seeded in `sys_config` under the key `strategies.backtest.low_confidence_skip_threshold_pct` (default 5 — meaning a backtest is flagged only when more than 5% of the universe had no coverage), the annotation must additionally render in a highlighted warning style. A contract test must assert that this annotation is present on every backtest result record and that the highlighted warning state triggers correctly when coverage is below the configured threshold.
- `REQ-STRAT-012` Standard backtests must exclude archived symbols unless a future broader research mode is introduced.
- `REQ-STRAT-013` The EOD Signal Runner must read SQL Server data and evaluate user-subscribed Signal types for next-trading-day entry signals.
- `REQ-STRAT-013a` EOD Signal Runner execution is user-scoped. For each EOD run, the Signal engine must evaluate every active (non-paused) Signal Subscription independently per user. Signal generation, deduplication, suppression, and the combined-signal merging rule in REQ-STRAT-015a all apply within a single user's context for that run; one user's subscriptions do not affect another user's signal output. **Single-pass market data read (required implementation pattern, A-13):** The EODSR must read SQL Server OHLCV data using a single shared pass: all required candle ranges for the active universe (up to 500 symbols) are fetched once per EOD run and held in Worker process memory for the duration of that run. Each Signal Subscription for each user is then evaluated against this in-memory data cache. This pattern is mandatory — implementations that fetch symbol data once per (user, Subscription) combination produce O(users × subscriptions × symbols) SQL Server reads, which at Phase A scale (30 users × 5 subscriptions × 500 symbols = 75,000 reads) will cause EODSR to run for 20+ minutes and degrade the overall EOD pipeline timing. The single-pass requirement applies only to the shared market data read; signal records, portfolio impact assessments, and Telegram notifications must remain isolated per user as stated above.
- `REQ-STRAT-014` The Live Market Data Scan (LMDS), EOD Signal Runner, and backtesting must honour admin-configured scan exclusions.
- `REQ-STRAT-015` The EOD Signal Runner must persist generated entry signals, failures, and delivery attempts.
- `REQ-STRAT-015a` When multiple user-subscribed Signal types qualify the same symbol in the same EOD run, the platform must generate a single combined entry signal record for that symbol for that session. The entry signal record must list all qualifying Signal types and their names. The Telegram notification and portal signal entry must clearly name every Signal type that contributed to the entry signal.
- `REQ-STRAT-015b` When a combined entry signal is generated from multiple qualifying Signal types, the RME profile used for sizing and advisory calculations must be taken from the Signal Subscription with the highest user-defined priority among the qualifying subscriptions. The contributing Signal type names are carried in the entry signal record for transparency.
- `REQ-STRAT-016` Each Signal Subscription must declare its RME configuration including the position sizing model, stop loss type, add and reduce rules, and position lifecycle parameters.
- `REQ-STRAT-017` A Signal Subscription's RME configuration must be versioned and persisted with the Signal Subscription definition so that backtests and Signal runs always use the same risk rules that were active when the Signal Subscription was defined.
- `REQ-STRAT-017a` A Signal Subscription may not be archived or deleted while any active position (PendingEntry, Open, or Suspended) references a version of that subscription. The archive/delete UI must list which active positions are preventing the action. Positions transitioned to Suspended state as a direct result of a system-level action — specifically kill switch activation per REQ-ADMIN-007, admin signal suspension per REQ-ADMIN-010, account deactivation per REQ-ADMIN-001a, or platform-wide Signal type disable per REQ-ADMIN-013 — must not contribute to this archive/delete lock. Only positions that entered Suspended state due to market events, risk breaches, or user-initiated Signal Subscription pause per REQ-STRAT-007a must hold the lock. The UI must distinguish between these suspension reasons when displaying which positions are preventing the action. RME configuration edits are governed by the versioned copy-on-write model in REQ-STRAT-017b and do not require blocking active positions.
- `REQ-STRAT-017b` Saving any change to a Signal Subscription's RME configuration must use a versioned copy-on-write model: the save creates a new Signal Subscription version record with a monotonically increasing version number; it does not mutate the existing version. The new version carries an `effective_from` value set to the start of the next scheduled EOD Signal Runner execution so that the existing EOD run in progress (if any) always completes under the version it started with. The previous version remains the governing version for all positions currently in PendingEntry, Open, or Suspended states — those positions reference the version under which they were created (stored as `signal_subscription_version_id` on the position record per REQ-RME-016) and continue under that version for their entire lifecycle; no in-flight RME profile is ever silently replaced. The new version becomes the governing version for positions created by future EOD runs. Because every save creates a new version unconditionally, no check against active positions is required before saving; this eliminates the TOCTOU window that the check-then-save pattern produces. The portal edit UI must show: (a) the current live version, its effective date, and the count of positions currently governed by it; (b) any pending version scheduled for the next EOD run and an option to discard it before it takes effect; (c) a version history list with the ability to view (but not restore) past configuration snapshots. Discarding a pending version before its `effective_from` time reverts future EOD runs to the previous live version; it does not affect any positions already created under the pending version (there should be none, since it had not yet become live).
- `REQ-STRAT-018` Backtest results must never be reported without the configured slippage and commission assumptions applied.
- `REQ-STRAT-019` The minimum number of historical trading sessions required before a backtest may run must be calculated dynamically: minimum sessions = indicator length × sessions per candle for the configured timeframe.
- `REQ-STRAT-020` Sessions per candle for each timeframe must be: daily = 1, rolling 3-day = 3, rolling 5-day = 5, rolling 7-day = 7, weekly = 5, monthly = 22. These values are the standard trading-day counts used by the REQ-STRAT-019 minimum-sessions pre-check. Actual weekly and monthly candles in charting and backtesting are derived from the real trading-calendar boundaries (REQ-HIST-010), which means individual candles may span fewer or more sessions than the standard (for example, a week truncated by a holiday). Such variance does not change the pre-check value and does not invalidate the backtest; short-session or long-session candles are still one candle each and contribute to the low-confidence flag in REQ-STRAT-023 only if the overall skipped-session ratio crosses its threshold.
- `REQ-STRAT-021` A backtest must be refused with a clear reason if the symbol's available historical data in SQL Server falls below the dynamically calculated minimum session count.
- `REQ-STRAT-022` If individual sessions are missing within an otherwise valid historical data range, those sessions must be skipped and the count of skipped sessions must be recorded in the backtest result metadata.
- `REQ-STRAT-023` Backtest runs with a skipped session count exceeding a configurable percentage of total sessions in the evaluated date range must be flagged as low-confidence results. The threshold must be seeded in `sys_config` under the key `strategies.backtest.low_confidence_skip_threshold_pct` with a default of 5%.
- `REQ-STRAT-024` Entry signal deduplication is governed by the one-PendingEntry-per-symbol rule (REQ-PLC-007) and the supersede-on-new-signal rule (REQ-PLC-009). Within a single EOD run, the combined-signal rule (REQ-STRAT-015a) merges multiple qualifying Signal types into one entry signal record per symbol. Across EOD runs, a fresh entry signal for a symbol with an existing PendingEntry supersedes the old PendingEntry rather than generating a duplicate advisory. The EOD Signal Runner must not emit a second entry signal record for the same user and symbol within the same EOD run under any circumstances; entry signals from different Signal types within the same run are merged per REQ-STRAT-015a, not emitted separately. An entry signal is suppressed entirely for a given user and symbol if that user already has an Open position in that symbol, since no new PendingEntry can coexist with an active Open position for the same symbol.
- `REQ-STRAT-025` Each deployed Signal type implementation must carry a stable `code_version` identifier that is bumped whenever the Signal type's logic changes in a way that affects entry-signal output. The `code_version` is distinct from the stable Signal type identifier defined in REQ-STRAT-001a and does not change when the type is renamed, reconfigured through parameters, or temporarily disabled by the admin. The current `code_version` of each deployed Signal type must be readable at runtime and published in the admin portal Signal management view.
- `REQ-STRAT-026` Every backtest run record (REQ-BTSTORE-003) and every RME profile optimisation run (REQ-RME-021) must persist the `code_version` of each contributing Signal type at run time. When a stored backtest result or profile recommendation is surfaced in the portal, the portal must compare the stored `code_version` against the currently-deployed `code_version` for the relevant Signal types. When they differ, the portal must display a visible "results may be outdated — Signal logic has changed" indicator alongside the existing data/param staleness indicators from REQ-BTSTORE-007 and REQ-RME-021, with a prompt to re-run.
- `REQ-STRAT-027` The EOD Signal Runner (EODSR) must implement atomic-run semantics for SQL Server read failures: either the full Nifty 500 universe is evaluated for a session or no entry signals are emitted for that session. Partial evaluation — where some symbols are processed and others are skipped due to a SQL Server error — produces a half-universe of signals that misrepresents the scan and must not occur. To implement this: (a) EODSR must retry transient SQL Server read errors with exponential back-off for up to `sys_config.eodsr.db_retry.max_seconds` (default 120 seconds; seed key required); (b) if retries are exhausted before the full universe is evaluated, the EODSR run must be marked `failed_for_review` in `job_runs`, must not emit any entry signals for that day, and must fire an admin Telegram message and dashboard alert identifying the run, the failure reason, and the last symbol successfully evaluated before failure; (c) the EODSR must exit non-zero so the process supervisor logs a visible failure. An admin-triggered manual retry (REQ-MARKET-008) is the recovery path; no automatic EODSR retry occurs within the same session window. **Operator expectation:** A manual retry is a full re-run of the EODSR for the session — it does not resume from the symbol where the failed run stopped. The admin should expect the retry to process the full Nifty 500 universe from scratch. This behaviour and its implications (multiple full re-runs on sustained contention) must be documented in the EOD Signal Runner failure runbook (catalog entry #4).
- `REQ-STRAT-028` **Entry signal provenance (U-6).** Every record written to the `entry_signals` collection must carry the following provenance fields at write time, and these fields must never be mutated after the record is created: (a) `signal_subscription_version_ids` — a map of Signal Subscription identifier to the specific `version_id` (per REQ-STRAT-017b's copy-on-write model) that was active at EODSR run time for each contributing subscription; (b) `signal_code_versions` — a map of Signal type identifier to the `code_version` value (per REQ-STRAT-025) for each Signal type that contributed to the entry signal. The dashboard and portal notification feed display for an entry signal must surface version context as follows: (i) if the current live version of every contributing Signal Subscription matches the recorded `signal_subscription_version_ids`, no indicator is shown; (ii) if any contributing Signal Subscription has been updated since the signal was generated — i.e., the current live `version_id` differs from the one recorded in the entry signal — the portal must display a non-blocking indicator reading "(generated under an earlier configuration)" next to the signal entry, with a tooltip or expandable note showing the version at generation time and the current live version. This indicator must appear on: the dashboard entry signal list, the position origin section of the Position Detail page for any PendingEntry or Open position created from this signal, and the portal notification feed entry for the signal. The Telegram notification content for an entry signal (REQ-NOTIFY-024) must append a "Config version: {signal_subscription_version_id}" footer field so operators can trace which configuration version produced the signal from Telegram message history alone. A contract test must assert that both provenance fields are present and non-null on every `entry_signals` document written by the EODSR test harness.

### Backtest Storage

*All backtest output is persisted to the SQL Server backtest database. Stored results must be retrievable at any time without re-running Signal or RME logic.*

- `REQ-BTSTORE-001` All backtest output must be persisted to the SQL Server backtest database so results can be retrieved and analysed at any time without re-running the Signal or RME logic.
- `REQ-BTSTORE-002` Backtest database tables must use a `BT_` prefix to distinguish them clearly from market data tables.
- `REQ-BTSTORE-003` Each backtest run record must capture: a unique run ID, Signal type, snapshot of the Signal parameter set used, snapshot of the RME profile used, timeframe, execution model assumptions (slippage and commission), symbol universe evaluated, date range covered, run timestamp, and the `signal_subscription_version_id` of the Signal Subscription version used for the run (see REQ-STRAT-017b). When a backtest is launched from the Signal Builder for an already-deployed Signal Subscription, the backtest must default to the **current live version** of that Subscription's RME configuration and make that version ID explicit in the run header. The backtest-launch UI must additionally offer a "Backtest against historical version" toggle that allows the user to select a prior version for reproducibility testing; the chosen version ID is persisted on the run record. This requirement closes the ambiguity of whether a backtest uses the live or historical version — the answer is always the live version by default, with an explicit override path for version-specific testing.
- `REQ-BTSTORE-004` Each trade generated by a backtest must be persisted linked to its run: symbol, entry date and price, stop level at entry, exit date and price, exit reason, R multiple achieved, position size in units and value, gross PnL, and net PnL after execution model assumptions.
- `REQ-BTSTORE-005` Each backtest position lifecycle must be persisted linked to its run: symbol, all add and reduce events with dates and prices, final exit event, peak R multiple, and the RME lifecycle state at each transition.
- `REQ-BTSTORE-006` Portfolio-level performance per backtest run must be persisted: total trades, win rate, expectancy, maximum drawdown, Sharpe ratio, profit factor, XIRR, peak equity, starting and ending equity, and a point-in-time equity curve as a time-series of dated equity values.
- `REQ-BTSTORE-006a` Each backtest run must require an explicit starting equity value provided by the user at the time of initiating the run. The backtest UI must present a starting equity input field pre-populated with the platform default notional starting equity — a fixed nominal value seeded in `sys_config` under the key `strategies.backtest.default_starting_equity_inr` (default ₹10,00,000 / ₹10 lakh). The field must be clearly labelled as **"Notional starting equity (for comparison purposes)"** so the user understands this is a normalisation denominator, not a projection of their real account performance. The user may override this value before launching the run. The starting equity value used must be persisted in the backtest run header record alongside the other run parameters, and must be displayed prominently in the backtest result summary so that return percentages and equity curve figures are always interpretable in context. The backtest result header and the equity-curve chart must carry a persistent caveat: "Portfolio-level figures (equity curve, drawdown %, XIRR) are scaled to the notional starting equity. They are meaningful for comparing configurations against each other but do not project real outcomes on your account." A backtest must be refused if no starting equity value is provided or if the provided value is zero or negative. **Rationale:** pre-populating with the user's current equity distorts historical backtests — a backtest from 2022–2023 using today's equity as starting capital produces a synthetic equity curve that never corresponds to anything the user would have experienced. A fixed notional starting equity makes cross-run comparisons internally consistent while being honest that the figures are scaled, not real-account projections.
- `REQ-BTSTORE-007` The RME profile optimisation workflow must read from stored backtest results rather than re-executing backtests when ranking profiles and generating recommendations, unless the scan parameters, RME profile, or underlying historical data have changed since the last stored run.
- `REQ-BTSTORE-008` The backtest database must be kept in a separate SQL Server database instance or logical database from the market data database so that backtest write load does not affect market data read performance.
- `REQ-BTSTORE-009` Users must be able to cancel a running backtest from the backtest progress screen. Cancellation is cooperative: the backtest engine must check a cancel flag between symbol batches or between date-range chunks, whichever the engine uses as its unit of work. On cancellation the run header must be marked with outcome `cancelled`; by default, partial per-trade, per-position, and portfolio-performance records written to that point are retained in a **draft** state (outcome `cancelled_draft`) rather than discarded, so that the user does not lose hours of computation on a long run. The cancel event must be recorded with the actor, timestamp, and elapsed processing time at the moment of cancellation.
- `REQ-BTSTORE-009a` A backtest run with outcome `cancelled_draft` must be treated as follows: (a) It must be visibly distinguished from a completed run everywhere results are displayed — a persistent "Incomplete result — cancelled at X% completion" banner must appear at the top of the draft result screen with the percentage of symbols processed at cancellation time. (b) Draft results must never be surfaced to the RME profile-optimisation workflow (REQ-BTSTORE-007) and must not appear in ranking views or profile suggestions; they are for manual user inspection only. (c) The user may explicitly promote a draft result to `finalized_draft` (acknowledging it is incomplete) so it is retained indefinitely alongside completed runs, or may discard it at any time; unacknowledged draft results expire and are purged after a configurable retention period seeded in `sys_config` under `strategies.backtest.draft_expiry_days` with a default of 7 days. (d) The user may also re-run the backtest from the start using the same parameters directly from the draft result screen; the new run starts fresh and does not extend from the cancellation point. This behaviour is opt-in infrastructure: if the backtest engine cannot guarantee that retained partial records represent a consistent slice of the universe (for example, because portfolio heat calculations depend on the full symbol set), the engine must discard partial records on cancellation instead and set outcome to `cancelled`; the choice between `cancelled` and `cancelled_draft` is a per-run-type engine decision documented in the backtest engine implementation, not a user preference.

## Part 5 — Risk Management Engine

*Implemented as a dedicated .NET RME service. The RME is Signal-independent: Signal types emit entry signals; the RME manages everything from initial sizing through the full position lifecycle. The same RME logic runs in both live and backtest modes.*

### RME Core Architecture

*Core design principles, inputs, outputs, and plugin architecture. All other RME sections depend on this foundation.*

- `REQ-RME-001` The platform must implement a dedicated Risk Management Engine (RME) as a Signal-independent, pluggable module responsible for all risk calculations across trade, position, portfolio, and account levels.
- `REQ-RME-002` The RME must operate consistently across backtesting and live signal workflows; the same risk logic and rules must apply in both modes.
- `REQ-RME-003` The RME must be deterministic: identical inputs must always produce identical outputs.
- `REQ-RME-004` The RME must be event-driven and respond to trade signals, price updates, stop events, portfolio state changes, and market events.
- `REQ-RME-005` The RME must not calculate trading indicators internally; Signal-produced outputs such as entry signals, ATR values, and indicator readings are provided to the RME as inputs.
- `REQ-RME-006` All risk calculations must be based on current account equity, not fixed capital amounts.
- `REQ-RME-006a` When a user's equity curve has no records yet — specifically during the period between their first FYERS account sync completing and the end of their first completed trading session — the RME must derive current account equity from the initial FYERS account sync. Equity for this purpose is defined as the market value of all holdings present in the platform's symbol master at last known prices plus the FYERS-reported available cash balance. Holdings in symbols not present in the symbol master are excluded from the equity base, consistent with REQ-PORT-005a. This derived value must be used for all RME sizing and heat calculations until the first equity curve record is written at EOD. If the FYERS sync returns zero holdings in the symbol master and zero cash balance, the RME must treat equity as zero and block all position sizing recommendations until a valid equity value is available, surfacing a clear message to the user that their account balance could not be determined. Note: users with significant holdings outside the Nifty 500 universe will have a smaller equity base visible to the RME than their total FYERS account value; this is a known and intentional consequence of the platform's Nifty 500 scope boundary.
- `REQ-RME-006b` After a user's first successful FYERS account sync, the portfolio dashboard must display a persistent equity-base disclosure panel showing three labelled figures: (1) **FYERS total account value** — the aggregate market value of all FYERS holdings at last known prices plus FYERS-reported available cash; (2) **Platform-visible equity base** — the market value of holdings in platform-tracked Nifty 500 symbols at last known prices plus FYERS-reported available cash; this is the figure the RME uses for all risk calculations unless overridden per REQ-RME-006c; (3) **External holdings (excluded)** — the arithmetic difference between (1) and (2), labelled explicitly as "holdings in symbols outside the Nifty 500 universe — excluded from RME calculations." The panel must include a brief inline explanation that the platform's risk engine is scoped to the Nifty 500 universe only, and that positions in other instruments are not visible to or managed by the platform. If the external holdings figure is zero, the panel may display a simplified view without the exclusion line but must still show the equity base in use. The panel must refresh after every account sync. A compact summary of the equity base figure in use must also appear in the Phase 1 order confirmation modal for every sizing recommendation, so the user can see the denominator driving the recommended position size at the moment of decision.
- `REQ-RME-006c` A user may optionally configure a manual equity base override from their profile settings page. When an override is active, the RME uses the override figure as the equity base for all position sizing and portfolio heat calculations instead of the auto-derived platform-visible equity base. The override and its metadata must be stored on the user's MongoDB profile document as `equity_base_override` (decimal, in INR) and `equity_base_override_updated_at` (UTC timestamp). Whenever an override is active: (a) A non-blocking but prominent warning must appear in the Phase 1 order modal and on the portfolio dashboard stating that a manually configured equity figure is in use, displaying both the override value and the current auto-derived platform-visible equity for comparison. (b) The override value and its last-updated timestamp must be visible on the profile settings page alongside a clear action to clear the override and revert to auto-derived equity. (c) If the override has not been refreshed within a configurable number of days (`sys_config` key `risk.equity_override_stale_days`, default 30 days), the platform must surface a non-blocking warning on the portfolio dashboard prompting the user to review, update, or clear the override, and must generate an admin-only notification of type `user_equity_override_stale` so the admin is aware of users running on potentially outdated equity figures. The `equity_curve` collection (REQ-PORT-022) and all drawdown tracking must always use the auto-derived platform-visible equity base regardless of any override; the override affects only the input equity supplied to the RME sizing and heat calculation path, not portfolio performance accounting. **Override cap (S-10):** To prevent the override from inflating the RME's sizing denominator far beyond the user's real capital, the override value must be capped at `min(FYERS_total_account_value × 1.5, FYERS_total_account_value + ₹10,00,000)` where `FYERS_total_account_value` is the most recently synced FYERS total. The platform must enforce this cap at save time; if the user attempts to set a value exceeding the cap, the save must be rejected with a message showing the maximum permitted value and the current FYERS total. Additionally, if any user's active override exceeds their FYERS total account value by more than 50%, the platform must emit an admin-only notification of type `user_equity_override_unusual` so the admin is aware; this notification fires at most once per user per 24-hour window.
- `REQ-RME-006d` Every RME cross-position computation that depends on ledger-derived state — position sizing (REQ-SIZING-004), portfolio heat (REQ-HEAT family), drawdown-adjusted sizing (REQ-DRDN-003 and REQ-DRDN-006), the pre-trade portfolio impact assessment (REQ-RME-017), and the Phase 1 order signing endpoint (REQ-ORDER-009b) — must implement a snapshot-consistent read contract against the per-user ledger snapshot version defined in REQ-PORT-031a. The contract is: (a) read the user's `ledger_snapshot_version` as `V1` before any dependent read; (b) perform all dependent reads across `trades`, `holdings`, `positions`, `equity_curve`, and `portfolio_snapshots`; (c) read `ledger_snapshot_version` again as `V2`; (d) if `V1 == V2` the read is snapshot-consistent and the RME proceeds to produce the advisory; (e) if `V1 != V2` a writer committed during the read window and the read is treated as torn — the RME must retry the full sequence up to `sys_config.rme.equity_read.snapshot_retry_max_attempts` (default 3) with a back-off of `sys_config.rme.equity_read.snapshot_retry_backoff_ms` (default 50 ms) between attempts; (f) on retry exhaustion the RME must **not** emit an advisory from a torn snapshot — it must defer the specific advisory being computed with a structured state (`snapshot_contention_deferred`), emit a `rme.equity_read.snapshot_retry_total{outcome="exhausted"}` OpenTelemetry counter increment, and the caller surface (chart page, Phase 1 modal, LMDS-driven advisory path, EOD Signal Runner) must present a clear "portfolio state is updating — please retry shortly" message rather than a possibly-wrong recommendation. The RME must additionally emit `rme.equity_read.snapshot_retry_total` tagged by `outcome="consistent_on_first_read"` and `outcome="consistent_after_retry"` so snapshot contention is observable on the admin System Health widget (REQ-ADMIN-014); a sustained `exhausted` rate above an operationally-tuned threshold must raise an admin advisory. Backtest paths are out of scope for this requirement: backtests read historical data with no concurrent writers and do not participate in the snapshot-version protocol. When a user's manual equity override per REQ-RME-006c is active, the override value is substituted for the ledger-derived equity at sizing time per REQ-SIZING-004, but the snapshot-consistent read is still required for all other ledger-derived inputs to the same computation (current portfolio heat, open quantities, holdings composition) so the sized recommendation is internally consistent. **Override-active retry-exhaustion UX (RME-R1):** When snapshot retry is exhausted and an override is active, the user-facing message must be differentiated: instead of the generic "portfolio state is updating — please retry shortly," the surface must show "Your equity override is in effect — retrying with current portfolio state" so the user understands their sizing denominator (the override) is not in question and the delay relates only to concurrent portfolio state reads. This prevents trader confusion where the override-active warning and the snapshot-contention message appear simultaneously and seem contradictory.
- `REQ-RME-006e` The platform must detect and surface an advisory when a user's FYERS total account value diverges materially from the platform-visible equity base. After every account sync that produces both a FYERS-total-account-value and a platform-visible-equity-base reading, the platform must compute the absolute divergence ratio: `(FYERS_total − platform_visible) / platform_visible`. If this ratio exceeds the threshold configured in `sys_config` under the key `risk.equity_base.external_divergence_warn_pct` (default 15%), the platform must: (a) display a non-blocking, non-dismissible advisory card on the portfolio dashboard below the equity-base disclosure panel (REQ-RME-006b) stating the current FYERS total, the current platform-visible equity base, the percentage difference, and one of three suggested user actions — enable the manual equity override (REQ-RME-006c) if the user wants the RME to size against their full FYERS capital, accept the silent exclusion if the external holdings are intentional, or contact the admin for assistance; (b) emit a one-time Telegram notification of type `equity_base_divergence_advisory` to the user the first time the divergence threshold is breached per account-sync cycle (i.e., once per sync that crosses the threshold, not on every sync); the notification must include the same three data points (FYERS total, platform-visible equity base, percentage gap) and a portal deep link to the profile settings page for the manual override control. The advisory clears automatically once the ratio falls back below the threshold. This requirement exists because a user who deposits capital, buys non-Nifty 500 holdings, or sells external holdings will silently have their RME sizing denominator misaligned from their real capital without this advisory; the resulting sizing errors are a slow-burn trust problem that only surface when a user questions a position size. The threshold is editable by the user in profile settings (as a user override of the sys_config default) so users who deliberately maintain external positions can raise or disable the advisory for their account.

- `REQ-RME-007` The RME must operate using Risk Units (R) where 1R equals the cash amount lost if the stop loss is hit at the entry price. The stop price must be strictly less than the entry price; a stop at or above the entry price is an invalid configuration. The RME must reject any position entry where this condition is not met, recording the rejection reason as `invalid_stop_distance` on the position record and surfacing a clear error to the user in the Phase 1 order modal. This rule applies in both live and backtest modes.
- `REQ-RME-008` All trade and portfolio performance metrics must be tracked in R multiples including average R, expectancy in R, and drawdown in R.
- `REQ-RME-009` Averaging down (adding to a losing position below the entry price) must be disabled by default and require explicit per-Signal Subscription configuration to enable.
- `REQ-RME-010` Total portfolio open risk must be continuously known and current.
- `REQ-RME-011` All RME outputs are advisory: position size recommendations, stop levels, add and reduce level advisories, and exit recommendations all require explicit user-initiated action; the platform must never place orders autonomously.
- `REQ-RME-012` The RME must be configurable through the platform's runtime configuration model, with defaults managed via `sys_config` and per-Signal Subscription overrides persisted with the Signal Subscription definition.
- `REQ-RME-013` The RME must use an abstract plugin architecture for stop loss determination, trailing stop updates, and position level generation so that concrete implementations can be swapped without changing surrounding RME logic.
- `REQ-RME-014` Each pluggable mechanism type must implement a common interface accepting standard inputs and producing consistent outputs, enabling mechanisms to be tested and compared independently.
- `REQ-RME-015` The RME configuration for a position is set as a unified profile at the time of entry and governs the entire position lifecycle until the position is fully closed; the profile must not be changed mid-lifecycle.
- `REQ-RME-016` The RME profile selected at entry must be persisted with the position record and remain immutable for audit and reproducibility purposes. The position record must additionally store the `signal_subscription_version_id` — the identifier of the specific Signal Subscription version in effect when the position was created — so that the governing configuration can be retrieved from the version history at any time. Both the full profile snapshot and the version ID are written atomically with the PendingEntry position document and must never be modified after creation.
- `REQ-RME-017` Before surfacing an entry advisory, the RME must generate a portfolio impact assessment including: projected portfolio heat after entry, projected sector exposure after entry, cash reserve remaining, number of positions from the same sector, sector concentration relative to existing positions (the V1 proxy for correlation risk), and the maximum portfolio loss scenario if all current open stops were hit simultaneously. Statistical cross-position correlation modelling is deferred to a later phase per REQ-NEXT-006.
- `REQ-RME-018` Portfolio impact insights must be delivered as a brief summary in the Telegram entry signal notification and as a full breakdown on the portal chart and position entry page.
- `REQ-RME-019` Portfolio impact insights must also be available when the user browses positions manually, reflecting the current live portfolio state at the time of viewing.
- `REQ-RME-020` The platform must support automated RME profile optimisation backtests that run a symbol's historical entry signals through multiple RME profile configurations and compare outcomes to recommend the best-performing profile for that symbol. **Optimisation run concurrency cap (U-9):** Optimisation runs share the REQ-SLO-007 concurrency cap of 5 platform-wide and 1 per user. An optimisation run triggered while the user already has one active must be rejected with a clear "optimisation run already in progress" message; the user must wait for the active run to complete before triggering another. Platform-wide, additional optimisation runs beyond 5 simultaneous are queued with a visible queue position shown to the user. This cap applies independently of and in addition to the backtest cap; a user with one active backtest and one active optimisation run has consumed both their per-user slots. The set of profile configurations to compare is a developer-defined grid of stop type, trailing stop type, and sizing model combinations; users do not define the grid. The optimisation run is triggered manually by the user from the Signal configuration screen for a specific Signal Subscription and symbol; it is not triggered automatically. The UI must display a progress indicator while the run is in progress and must prevent duplicate triggers for the same symbol and subscription while a run is active. On completion, the results screen must rank all evaluated profile configurations by expectancy in R, show the key metrics for each (win rate, average R, max drawdown, profit factor), and highlight the top-ranked configuration as the suggested profile.
- `REQ-RME-021` RME profile optimisation backtest results must be stored per symbol and surfaced as the suggested default profile when the user next configures an entry for that symbol. Results must carry a staleness indicator: if the underlying historical data or scan parameters have changed since the stored result was generated, the suggested profile must be shown with a visible "results may be outdated" warning and a prompt to re-run the optimisation. **Staleness check implementation (O-6):** The staleness check must be implemented as a single computed field evaluated at result-read time, not as a watcher across three independent change streams. Concretely: at the time an optimisation result is read (for display or for profile suggestion), the platform evaluates a single `is_stale` boolean by checking: (a) whether the most recent daily candle date in SQL Server for any symbol in the run is later than `optimisation_run.completed_at`; (b) whether the current live `signal_subscription_version_id` differs from the version recorded on the run; (c) whether the current `code_version` of the contributing Signal type differs from the `signal_code_versions` recorded on the run. If any condition is true, `is_stale = true` and the warning is shown. This read-time computation avoids the complexity and fragility of maintaining three separate staleness watchers and is consistent with REQ-STRAT-026's staleness indicator approach.
- `REQ-RME-020a` The RME profile optimisation scoring must rank configurations using a **Composite Score** rather than a single metric. The Composite Score is defined as follows, applied to each evaluated configuration's backtest result over the optimisation window:

  ```
  Composite Score =
    (0.20 × Normalised CAGR)
  + (0.15 × Sharpe Ratio)
  + (0.15 × Expectancy in R)
  + (0.10 × Profit Factor)
  + (0.10 × Stability Score)
  + (0.10 × Regime Consistency Score)
  + (0.10 × Capital Efficiency)
  + (0.10 × Trade Quality Score)
  − (0.10 × Drawdown Penalty)
  ```

  Component definitions: **Normalised CAGR** — annualised return normalised across all configurations in the run (min-max, 0–1). **Sharpe Ratio** — risk-adjusted return; computed over daily equity changes in the backtest; annualised. **Expectancy in R** — `(Win% × Avg Win in R) − (Loss% × Avg Loss in R)`. **Profit Factor** — gross profit divided by gross loss. **Stability Score** — `1 − (StdDev(returns across rolling sub-windows) / Mean return)`; measures consistency of returns over time; rolling window is the backtest period divided by 4. **Regime Consistency Score** — average of normalised performance across market regimes (bull, bear, sideways) as labelled by the signal's historical data; equal-weighted across present regimes. **Capital Efficiency** — total return divided by average capital deployed during the backtest. **Trade Quality Score** — composite of average R per trade, profit factor, and win/loss symmetry (equal-weighted). **Drawdown Penalty** — `MaxDrawdown% / DrawdownPenaltyThreshold` where `DrawdownPenaltyThreshold` is seeded in `sys_config` under `rme.optimisation.drawdown_penalty_threshold_pct` with a default of 25%; the penalty is capped at 1.0. The final score used for ranking is `Composite Score × Robustness Factor` (see REQ-RME-020b). When a backtest has too few trades (fewer than `sys_config.rme.optimisation.min_trades_for_valid_result`, default 10), the configuration must be marked as low-confidence and excluded from the top-ranked suggestion regardless of its score. All component values and the final Composite Score must be displayed in the results screen alongside the existing per-configuration metrics.

- `REQ-RME-020b` Each configuration's Composite Score (REQ-RME-020a) must be multiplied by a **Robustness Factor** before ranking. The Robustness Factor is the product of three sub-scores, each normalised to the range [0, 1] across all configurations in the same run:
  - **Parameter Sensitivity Score** — `1 − (variance of Composite Scores across immediate neighbouring parameter sets in the developer-defined grid)`. A configuration whose performance changes sharply when its parameters change by one grid step is penalised; a configuration that is stable across neighbours is rewarded. "Immediate neighbours" are configurations that differ from the evaluated configuration by exactly one parameter dimension at the smallest grid step.
  - **Cross-Symbol Consistency Score** — the coefficient of variation (CV = `StdDev / Mean`) of Expectancy in R across all symbols run in the same optimisation session, normalised inversely (lower CV → higher score). A configuration that works well on one symbol but poorly on others is penalised relative to one that is consistently positive across symbols.
  - **Walk-Forward Stability Score** — the correlation between in-sample Composite Score and out-of-sample Composite Score across walk-forward folds (divide the backtest window into `sys_config.rme.optimisation.walk_forward_folds` folds, default 4). A configuration that over-fits to the training window and degrades on the hold-out period is penalised. The Robustness Factor must be stored per configuration result and displayed on the optimisation results screen alongside the Composite Score, so users can see both the raw performance and the robustness adjustment.

- `REQ-RME-020c` The RME profile optimisation engine must evaluate each configuration across multiple timeframes. Required evaluation timeframes are: Daily, Weekly, Monthly, and Rolling N-day windows where N is drawn from the set {3, 5, 7, 10, 15}. In addition, the engine must evaluate the following multi-timeframe combinations: (a) Weekly trend filter with Daily execution — entry signals from the Daily timeframe are only included if the Weekly signal agrees with the direction; (b) Rolling 5-day + Daily combination — entry signals must align on both the Rolling 5-day and Daily timeframes. The timeframe dimension is added to the developer-defined parameter grid; each timeframe or combination is treated as a separate configuration dimension alongside stop type and sizing model. The Composite Score and Robustness Factor are computed per timeframe configuration. The optimisation results screen must allow filtering and sorting by timeframe so users can compare performance of the same stop/sizing profile across different timeframe choices.

### RME Concurrency and Serialisation

*Derived from ADR-0003. These requirements govern how the Worker Service serialises concurrent RME events for the same position. They must be implemented before any Phase 6 RME code is written; retrofitting is prohibitively expensive and correctness bugs in this area cause direct financial harm.*

- `REQ-RME-CONC-001` All RME event processing for a given position must be serialised through a per-position in-process channel queue inside the Worker Service. No event producer (LMDS handler, LADS handler, EOD stop-update job, admin action handler) may invoke RME business logic directly. Every producer must enqueue a typed `RmeEvent` record to the position's channel via a `PositionChannelRegistry` singleton service. The channel registry must be initialised synchronously from MongoDB at worker startup — loading all non-terminal positions and creating one channel per position — before the LMDS and LADS poll loops start. This guarantees no event can arrive for a position whose channel does not yet exist.
- `REQ-RME-CONC-002` Every position document in MongoDB must carry a `_version` field (long integer, initialised to 1 on document creation, incremented by 1 on every successful write). Every RME write to the `positions` collection must use a MongoDB filter that includes `{ _id: <positionId>, _version: <readVersion> }` and must verify that `UpdateResult.MatchedCount == 1` after the operation. If `MatchedCount == 0` (version conflict — a concurrent writer modified the document between the processor's read and write), the processor must re-read the current document, recompute the RME output from fresh state, and retry the write. Maximum retry attempts per event: 3. After a 4th consecutive version-conflict failure on the same event, the processor must log the conflict as an error in the structured log, write an incident record to `rme_incidents` (not `rme_events` — `rme_events` is the immutable event-sourced audit log; `rme_incidents` is the operator-actionable flag collection, per `docs/data-management.md`) with `incident_type: concurrency_conflict_unresolved` and the full event context (position ID, event type, retry count, last conflicting version), write an admin-only `position_concurrency_alert` notification, and cease further retry for that event instance. The OCC mechanism serves as a write-level safety net for crash-recovery paths and future multi-instance deployments where the channel-based serialisation cannot apply.
- `REQ-RME-CONC-003` The core RME event processor must be implemented as a deterministic pure function with the signature `(PositionDocument, RmeEvent) → (UpdatedPositionDocument, IReadOnlyList<RmeOutput>)`. The function must have no observable side effects other than its return value; it must not perform I/O, write to any collection, or enqueue notifications internally. All I/O — writing the updated position document, appending to `rme_events`, writing notification records — is performed exclusively by the channel consumer loop after receiving and validating the output list. This shape enforces the determinism requirement of `REQ-RME-003` at the architectural level and makes the RME processor trivially unit-testable without a database or message bus.
- `REQ-RME-CONC-004` The backlog depth of each active position's channel — the count of enqueued but not yet processed events — must be exposed as an OpenTelemetry gauge metric tagged with `position_id`. A platform-wide aggregate metric — the maximum channel depth across all currently active positions — must be emitted as a separate gauge under the name `rme.channel.max_backlog_depth`. The admin System Health widget required by `REQ-ADMIN-014` must surface this aggregate alongside the LMDS and LADS health indicators. A warning state must be triggered when the aggregate exceeds a configurable threshold seeded in `sys_config` under the key `rme.channel.backlog_warn_depth` with a default of 20 events.
- `REQ-RME-CONC-005` Position channel lifecycle must be managed as follows: (a) a channel is created lazily — on the first `RmeEvent` enqueued for the position — rather than eagerly at PendingEntry document creation time; this avoids creating a channel for positions that are rejected synchronously during pre-trade validation (e.g., heat breach, drawdown gate fail, equity-base unavailable) before any event is ever produced, which would result in channels created and destroyed with no events ever processed; channel allocation must only occur after the position's PendingEntry document has successfully committed to MongoDB and the partial unique index check in REQ-PLC-007a has passed; (b) a channel is completed — writer side closed — immediately when the position transitions to Closed or Rejected; the consumer task must drain any remaining enqueued events to completion before the channel object is removed from the registry; (c) channels for positions that are in Open or Suspended state but have no enqueued events must remain live in the registry until those positions close; they must not be garbage-collected based on idle time alone; (d) on worker restart, the registry is rebuilt synchronously from MongoDB before any poll loop starts, as specified in REQ-RME-CONC-001; channels are again created lazily — a position loaded at startup that has no pending events will have its channel created on first enqueue after restart. A contract test must cover the "rejected on first pre-trade validation" path and assert that no channel is registered for the rejected position. **Suspended-channel leak observability (RME-L1):** The total count of channels in the registry that correspond to positions in `Suspended` state with no enqueued events must be exposed as an OpenTelemetry gauge metric named `rme.channel.idle_suspended_count`. A sys_config key `channel.lifecycle.phase_a_max_active_channels` (default 200, no enforcement, observability only) defines the Phase A channel ceiling. The admin System Health widget (REQ-ADMIN-014) must surface a non-blocking warning when `idle_suspended_count` exceeds 80% of this ceiling, prompting the admin to review and resolve stale Suspended positions before a worker restart exposes the accumulated idle channels as a resource leak.
- `REQ-RME-CONC-007` When OCC retries exhaust on a position event (REQ-RME-CONC-002 — 4th consecutive version-conflict failure), the affected position must adopt **frozen-with-visibility** semantics as follows: (a) the position transitions to `Suspended` lifecycle state with reason `concurrency_conflict_unresolved`; (b) the `PositionChannelRegistry` continues to accept new events enqueued for this position — no evidence is discarded and the channel remains live; (c) the RME channel consumer skips processing of all enqueued events for this position until admin resolution occurs — it must not attempt to process, drop, or re-order events in the frozen queue; (d) the admin is notified via the `rme_incidents` incident record written by REQ-RME-CONC-002 and via a `position_concurrency_alert` admin notification; (e) admin resolution consists of the admin reviewing the incident, confirming the position document state is consistent, and clearing the incident via the admin portal; on clearance the position is returned to its prior lifecycle state (Open or PendingEntry), and the RME channel consumer resumes processing enqueued events in FIFO order. A runbook entry must document the admin resolution procedure, including how to verify position document consistency before clearing the incident. A contract test must cover the frozen state — assert that events enqueued during the frozen window are neither processed nor dropped, and that they are processed in order on resume.
- `REQ-RME-CONC-006` The Worker Service must be deployed as exactly one running instance at any time until the Phase C multi-instance partitioning extension specified in ADR-0003 § Phase C Scaling Extension is delivered and accepted in a new ADR. Multi-instance deployment without the partitioning extension silently breaks the per-position channel invariant defined in REQ-RME-CONC-001 and produces undetectable concurrent writes on the same position document; the defect cannot be caught by unit tests. The API service is not subject to this constraint and may scale horizontally. The single-instance invariant on the Worker Service must be enforced at three independent layers: **(a) Infrastructure as code.** The Worker Service's Azure App Service plan template (Bicep or Terraform) must set `workerCount = 1` and must not declare an auto-scale rule; the deployment workflow must include a preflight check that fails the release if the target plan's current instance count is not 1 or if any auto-scale rule is attached. **(b) Pipeline gate.** The GitHub Actions deployment workflow must assert the absence of auto-scale configuration against the Worker's App Service plan before promoting a build; a detected violation must fail the release. **(c) Runtime self-election.** At Worker startup the process must attempt to acquire a Redis-backed singleton lease under the key `rme:worker:singleton` with a TTL read from `sys_config.operations.worker.singleton_lease_ttl_seconds` (default 60 seconds), and must refresh the lease every 20 seconds while running. If a Worker instance boots and finds the lease held by another active holder, it must log a `singleton_violation` structured error at Error level naming the detected holder's instance identifier, write a `position_concurrency_alert` admin advisory, and exit with a non-zero status code so Azure App Service restarts the process and produces a visible crash-loop signal. If Redis is unreachable at startup the Worker must proceed with normal startup — consistent with ADR-0003's stance that Redis is not a correctness dependency at runtime — but must log a `singleton_lease_unavailable` warning at Warning level so the missing enforcement layer is visible in the admin System Health widget required by REQ-ADMIN-014. Relaxation of layers (a) and (b) is gated on the acceptance of the Phase C partitioning ADR.

### Position Sizing

*Pluggable sizing models conforming to a common interface. The default is Fixed Percentage Risk Per Trade.*

- `REQ-SIZING-001` The RME must support multiple pluggable position sizing models that share a common interface so models can be swapped per Signal Subscription without changing the surrounding system.
- `REQ-SIZING-002` Supported sizing models must include at minimum: Fixed Percentage Risk Per Trade, ATR and Volatility-Based Sizing, Portfolio Heat-Based Sizing, and Drawdown-Adjusted Sizing.
- `REQ-SIZING-003` Additional sizing models should be supportable as configurable options including: Fixed Percentage Risk with Pyramiding, Equal Risk Contribution, Trend Following Pyramiding, and Breakout Add-on.
- `REQ-SIZING-004` Each sizing model must accept the same standard inputs (entry price, stop price, account equity, available capital, current portfolio state) and produce a recommended position size. For the purposes of this requirement, "account equity" is the platform-visible equity base as defined in REQ-RME-006a — the market value of Nifty 500 holdings at last known prices plus FYERS-reported available cash — unless the user has configured a manual equity override per REQ-RME-006c, in which case the override value is substituted.
- `REQ-SIZING-005` The default sizing model is Fixed Percentage Risk Per Trade. The default risk per trade is configurable within a band defined by a minimum and maximum percentage of current account equity, seeded at 0.5% minimum and 1.0% maximum. The RME must use the minimum value as the default risk per trade unless the user has explicitly configured a different value within the band for their Signal Subscription. The band bounds must be seeded in `sys_config` under the `position_sizing` category and are editable by the admin to adjust platform-wide defaults.
- `REQ-SIZING-005a` Portfolio Heat-Based Sizing requires a positive, non-zero platform-visible equity base (as defined in REQ-RME-006a) to function. If the equity base is zero, unavailable, or the `equity_curve` collection contains no completed-session records for the user (i.e., the user has not yet completed their first full trading session on the platform), the RME must fall back to Fixed Percentage Risk Per Trade for that sizing computation and surface a non-blocking advisory to the user explaining that Heat-Based Sizing is temporarily unavailable because their portfolio equity baseline has not yet been established. The fallback must be recorded in the sizing computation audit output required by REQ-SIZING-009. Once a valid equity base is available, Heat-Based Sizing operates normally without requiring any user action.
- `REQ-SIZING-006` Z-score deviation-based advisory overlays must remain supported as an additional signal layer on top of the primary sizing model for add-more and reduce-size suggestions.
- `REQ-SIZING-007` The default z-score timeframe is rolling 5-day trading-session candles; the default add-more threshold is `+3` and the default reduce-size threshold is `-3`.
- `REQ-SIZING-008` The system must determine the price levels that would produce the configured z-score thresholds and surface those levels as advisory add-more and reduce-size targets.
- `REQ-SIZING-009` All sizing suggestions must be explainable and expose the model used, its inputs, the thresholds applied, and the derived price or quantity levels.
- `REQ-SIZING-010` Position quantities must be rounded to comply with NSE and FYERS minimum quantity constraints; fractional quantities are not supported.
- `REQ-SIZING-011` The RME must reject or downsize any proposed position that would breach maximum notional, maximum quantity, or configurable liquidity thresholds.
- `REQ-SIZING-012` Single stock exposure must default to a maximum of 10% of portfolio equity.
- `REQ-SIZING-013` Total open risk across all positions must default to a maximum of 5% of portfolio equity.
- `REQ-SIZING-014` Sector or correlated-basket exposure must default to a maximum of 20% of portfolio equity.
- `REQ-SIZING-014a` The RME must support a configurable correlated-industry grouping map that treats specified industry pairs or sets as a single combined sector for concentration-limit purposes under REQ-SIZING-014 and REQ-RME-017. The map must be stored in `sys_config` under the key `risk.correlated_industry_groups` as an array of group objects, each containing a `group_name` and an array of `industry_names` that must match the `Industry` field values in the symbol master. The RME must merge positions across all industries within a group when computing sector exposure: if a user holds positions in both "Banking" and "Finance" (a default group), the combined exposure counts against the single 20% cap, not two separate 20% caps. Default seed groups must include at minimum: `{group_name: "Banking & Finance", industry_names: ["Banking", "Finance"]}`, `{group_name: "Metals", industry_names: ["Metals", "Metal Products"]}`, and `{group_name: "Oil & Gas", industry_names: ["Oil", "Gas"]}`. The admin may update the map via the `sys_config` management UI at any time; changes take effect on the next RME computation cycle. The pre-trade portfolio impact assessment (REQ-RME-017) must use the merged group view for sector exposure reporting. Statistical correlation modelling remains deferred per REQ-NEXT-006.

### Portfolio Heat and Exposure Controls

*Real-time portfolio heat governs whether new positions or adds are permitted. Blocks are hard stops enforced by the RME.*

- `REQ-HEAT-001` The platform must calculate and maintain Portfolio Heat defined as Total Open Risk divided by Current Account Equity, expressed as a percentage.
- `REQ-HEAT-002` Maximum portfolio heat must be configurable with a conservative default managed via `sys_config`.
- `REQ-HEAT-003` New trade signals must be blocked by the RME when adding the proposed position would push portfolio heat above the configured maximum.
- `REQ-HEAT-004` Portfolio heat at or approaching the configured maximum must trigger position reduction advisories surfaced to the user.
- `REQ-HEAT-005` Maximum number of concurrent open positions must be configurable.
- `REQ-HEAT-006` Concentration rules must prevent new add-on entry recommendations in a sector when both portfolio heat is at or above a configurable elevated-heat threshold and that sector's current exposure is at or above a configurable sector concentration threshold. Both thresholds must be seeded in `sys_config` under the `risk` category with defaults of 4% for the elevated-heat trigger and 15% for the sector concentration block.
- `REQ-HEAT-007` Minimum cash reserve as a percentage of account equity must be configurable and enforced before approving new position sizing recommendations.
- `REQ-HEAT-008` Positions in `Suspended` lifecycle state must continue to contribute to portfolio heat calculations as though they were in `Open` state, using their last-known risk amount (`initial_risk_amount` × remaining quantity) as the heat contribution. The RME must not release a position's heat contribution when it transitions to `Suspended`; heat is only released when the position transitions to `Closed` or `Rejected`. To ensure users are not silently constrained by invisible risk budget consumption, the `Suspended` status must be prominently surfaced on: (a) the Portfolio Dashboard — with a count of suspended positions and their aggregate heat contribution shown as a distinct line in the heat breakdown; (b) the Positions Summary page — with a visual indicator (e.g., status badge) on each suspended position row; (c) the Position Detail page — with a banner explaining that the position is suspended and still consuming portfolio risk budget. Users must be able to identify and act on suspended positions without having to discover them through missing heat capacity.

### Drawdown Control

*Graduated account-level drawdown response. Thresholds are configurable; the defaults below are the safe starting values.*

- `REQ-DRDN-001` The platform must track account-level drawdown from the equity high-water mark on a continuous basis. Drawdown must be derived from the append-only `equity_curve` collection (REQ-PORT-022), which records the equity high-water mark and drawdown percentage at the end of each completed trading session.
- `REQ-DRDN-002` Daily, weekly, and monthly loss limits must be configurable and monitored. Breaching any limit must surface an advisory to the user via the portal notification feed and dashboard. Breach of a loss limit is advisory only and does not block trading automatically; the graduated drawdown response rules in REQ-DRDN-003 govern hard restrictions. Default values must be seeded in `sys_config` under the `risk` category: daily loss limit 2% of account equity, weekly loss limit 4%, and monthly loss limit 6%.
- `REQ-DRDN-003` The platform must implement graduated drawdown response rules that progressively restrict trading activity as drawdown deepens, with the following default thresholds: at 5% drawdown, reduce recommended new position size proportionally; at 10% drawdown, suspend add-on entry recommendations; at 15% drawdown, surface advisory to reduce all open positions; at 20% drawdown, suppress new entry signal recommendations from the RME and reject new entry order attempts in the Phase 1 modal (the user remains free to trade directly in FYERS); at 25% drawdown, surface advisory to close the weakest open positions; at 30% drawdown, surface advisory to stop all trading activity. The six threshold responses fall into two distinct enforcement categories that must not be conflated in code or code review: (a) *Platform-enforced restrictions on RME output* — the 5% threshold causes the RME to reduce computed position sizes algorithmically (REQ-DRDN-005); the 10% threshold causes the RME to suppress add-on entry recommendations entirely; the 20% threshold causes the RME to suppress new entry signal recommendations and the Phase 1 order confirmation modal to reject new entry order attempts per REQ-ORDER-004 — this is a platform-advisory suppression, not an order-level block; the user is still free to trade directly in FYERS. These three are applied automatically by the platform when the threshold is breached — no user acknowledgement is required or solicited. (b) *User-advisory notifications* — the 15%, 25%, and 30% thresholds cause the platform to surface a highly visible advisory to the user via the portal notification feed, the dashboard health strip, and a Telegram notification; the user retains full discretion to act or not. None of the six responses, including the category (a) restrictions, involve autonomous order placement or autonomous position closure — they restrict only the platform's own advisory output and confirmation flow, consistent with REQ-BOUNDARY-004. The THRESHOLD VALUES for all six levels are configurable via `sys_config` per REQ-DRDN-004; the ENFORCEMENT CATEGORY (a vs b) of each level is fixed and cannot be changed by configuration.
- `REQ-DRDN-004` All drawdown thresholds must be configurable through `sys_config` with the values in REQ-DRDN-003 as safe defaults. **sys_config key naming convention for drawdown (L-8):** To prevent admin confusion between advisory-only settings and platform-enforcement settings, the seed keys must use distinct sub-namespaces: advisory loss-limit keys (REQ-DRDN-002) must be seeded under `risk.drawdown_advisory.*` (e.g., `risk.drawdown_advisory.daily_loss_limit_pct`, `risk.drawdown_advisory.weekly_loss_limit_pct`, `risk.drawdown_advisory.monthly_loss_limit_pct`); enforcement-category threshold keys (REQ-DRDN-003 — the six graduated thresholds) must be seeded under `risk.drawdown_enforcement.*` (e.g., `risk.drawdown_enforcement.size_reduction_pct`, `risk.drawdown_enforcement.suppress_addon_pct`, `risk.drawdown_enforcement.suppress_entry_pct`, and corresponding advisory-notification thresholds). The admin `sys_config` management UI must surface the `category_subgroup` distinction visually so the admin can tell at a glance whether changing a key adjusts an advisory or an enforcement behaviour.
- `REQ-DRDN-005` Position sizing must be dynamically scaled down in proportion to current drawdown depth when drawdown mode is active.
- `REQ-DRDN-006` The platform must support equity-curve-based sizing adjustments as a configurable option, reading the historical equity series from the `equity_curve` collection (REQ-PORT-022). When enabled, the RME must reduce recommended position sizes when the equity curve is in a declining trend, as determined by a configurable lookback window stored in `sys_config`.
- `REQ-DRDN-007` An admin-controlled global kill switch must be available to suspend all Signal generation and recommendation output platform-wide.

### Pyramiding and Scaling

*Add-on and scale-out advisory rules. All actions are advisory — user-initiated execution is required.*

- `REQ-PYR-001` The RME must support adding to an open winning position (pyramiding) at configurable price levels as an advisory action.
- `REQ-PYR-002` Supported add triggers must include: fixed percentage move from entry, R multiples from entry, ATR multiples from entry, breakout above a resistance level, and pullback to a support level.
- `REQ-PYR-003` Maximum number of add-on entries per position must be configurable with a safe default.
- `REQ-PYR-004` Add-on quantity must reduce progressively with each successive add; add size must never increase on subsequent entries.
- `REQ-PYR-005` Total position risk including all add-on entries must never exceed the configured maximum single-position risk limit.
- `REQ-PYR-006` Add-on recommendations must be blocked when portfolio heat would exceed the configured maximum after the add.
- `REQ-PYR-007` The RME must support reducing an open position (scaling out) at configurable levels as an advisory action.
- `REQ-PYR-008` Supported reduce triggers must include: configured profit targets, volatility increase beyond a threshold, portfolio heat exceeding maximum, and time-based reduction rules. In backtest mode only, trend weakening may additionally be detected by re-evaluating the Signal type's entry conditions against subsequent candles; if the entry condition is no longer met at a later candle, this constitutes a trend weakening signal for reduce advisory purposes. In live signal workflows, Signal types are post-market scanners that emit entry signals once and do not produce ongoing trend readings; the trend weakening trigger therefore does not apply in live mode and must be excluded from live position advisory logic.
- `REQ-PYR-009` All add and reduce actions are advisory and require explicit user-initiated execution.
- `REQ-PYR-010` After each confirmed add or reduce, the platform must recalculate the position's average entry price, active stop level, current R multiple, and portfolio heat contribution.
- `REQ-PYR-011` When a new pyramid tranche is added to an open position, the RME must recalculate the effective combined stop for the entire position using the updated average entry price and ATR. The resulting effective combined stop must never be set below the highest individual tranche stop that was in effect immediately before the new tranche was added. Stated plainly: **a new tranche must never lower the effective combined stop of the position.** If the combined stop formula produces a value lower than the prior highest tranche stop, the prior highest tranche stop must be used as the floor and the position's `active_stop_level` must be set to that floor value. This invariant must be enforced in the RME processor and must be covered by a unit test asserting that adding a tranche at a higher average price does not reduce the active stop level.
- `REQ-PYR-012` The Position Detail page must surface a per-tranche breakdown for any position that has had more than one confirmed add fill (i.e., a position with two or more `intent_ledger` records in `matched` status for the same `position_id`). The breakdown must show: (a) each confirmed tranche listed in fill-date order with its fill date, filled quantity, average fill price for that tranche, and the initial stop level assigned to that tranche at the time of fill; (b) the combined average entry price and total combined quantity derived from all tranches, computed by the standard weighted average formula; (c) the effective combined stop level — which must be the floor-adjusted value required by REQ-PYR-011 — displayed prominently in the RME advisory panel alongside the per-tranche detail. The per-tranche breakdown must be visible for all non-terminal positions (PendingEntry, Open, Suspended) and must persist on closed position records so users can review the full entry history after a position is resolved. Positions with only one tranche (no adds yet) must not show the per-tranche section; a single consolidated view is sufficient.

### Dynamic Trigger Recalibration

*After any trigger execution the RME must recalculate all active price levels for the position. This requirement applies to both live signal workflows and backtesting.*

- `REQ-RME-022` The RME is a stateful, iterative engine. After any trigger is executed — meaning any event that changes the position's quantity, average entry price, or stop level, including: a stop-loss exit, a trailing stop update, an add-on fill, a reduce fill, or a break-even stop activation — the RME must immediately recompute **all** of the following price levels for the position using the updated position state (new quantity, new average entry price, current ATR at that point): (a) active stop loss level; (b) active trailing stop level if a trailing stop is configured; (c) all remaining configured add-on levels and their corresponding quantities; (d) all remaining configured reduce levels and their corresponding quantities; (e) any exit trigger levels derived from the RME configuration (e.g., profit-target exit price). This full recalibration must complete before the next event can be processed for that position — it is not deferred or batched. The recalibrated levels must be persisted on the position document atomically with the trigger execution write, so the position document always reflects a self-consistent set of levels derived from the same underlying state. Partial recalibration — where some levels are updated but others retain stale values from a prior state — is a contract violation. Both live and backtest modes must use the same recalibration logic, consistent with REQ-RME-002 and REQ-RME-003.

- `REQ-PLC-004` Each position must persist: symbol, entry date and price, current size, average entry price, active stop level, trailing stop level, initial risk amount (1R), current R multiple, unrealised and realised PnL, number of adds completed, configured add and reduce levels and quantities, maximum allowed position size, last add price, last reduce price, locked profit amount, distance to stop, ATR at entry, holding period, time stop date if applicable, portfolio heat contribution, the four advisory flags (add advisory active, reduce advisory active, trailing stop active, exit advisory active) with timestamps of when each was last set or cleared, and two circuit-limit fields: `circuit_limit_active` (boolean, default false) and `circuit_limit_direction` (enum: `upper`, `lower`, or null when inactive) with a timestamp of when the flag was last set or cleared. Specifically: the RME must re-evaluate the current stop level, all add levels, and all reduce levels against the post-clear price and queue the appropriate advisory or exit events on the position's channel. The position's `circuit_limit_active` flag must be cleared atomically with this re-evaluation. This ensures that a position suspended during a circuit event is not left in stale advisory state after the market resumes for that symbol.

Admin suspension and RME-forced suspension share the `Suspended` state but have distinct `source` values and distinct resolution paths: `ADMIN`-sourced suspensions require resolution per the per-reason path listed above; `RME_OCC`-sourced suspensions require admin incident resolution per REQ-RME-CONC-007; `CORPORATE_ACTION`-sourced suspensions require user adjustment per REQ-PORT-029; `LMDS`-sourced suspensions may self-resolve. **REQ-ADMIN-016 must surface the correct resolution action for each `reason` code** so the admin UI does not present a blanket "Release suspension" button for reason codes whose resolution is a different action (e.g., `account_deactivated` requires reactivation, not a suspension release).
- `REQ-PLC-006` Position lifecycle events that must be handled include: entry signal received, entry fill confirmed via sync, add level reached, reduce level reached, stop level updated, stop breached, portfolio heat limit exceeded, drawdown threshold breached, time stop reached, gap event, and circuit limit event.
- `REQ-PLC-007` Only one PendingEntry position may exist per symbol per user at any time, regardless of how many Signal Subscriptions contributed to the underlying entry signal. This is consistent with the combined-signal rule in REQ-STRAT-015a, which merges multiple qualifying Signal types into a single entry signal record per EOD run.
- `REQ-PLC-007a` The uniqueness invariant in REQ-PLC-007 — at most one non-terminal position per `(user_id, symbol)` tuple — must be enforced at the database layer, not only at the application layer. The `positions` collection must carry a partial unique index on the fields `{ user_id: 1, symbol: 1 }` with a partial filter expression restricting the index to documents whose `lifecycle_state` field is one of `PendingEntry`, `Open`, or `Suspended`. Any position creation attempt that would violate this uniqueness constraint — including a concurrent duplicate write that passes application-level checks before the first write commits — must be rejected by MongoDB with a duplicate-key error. The position creation handler must catch this error and return a structured failure with reason `duplicate_active_position_attempt`, log it as a warning (not an error, because this is an expected concurrent-safety rejection, not a system fault), and surface a user-visible message indicating that an active position for this symbol already exists. Channel allocation in the `PositionChannelRegistry` (REQ-RME-CONC-005) must only occur after the MongoDB write has successfully committed, ensuring that no channel is created for a position that was rejected by the uniqueness check. A contract test must cover the concurrent-creation race: two simultaneous position creation requests for the same `(user_id, symbol)` tuple must result in exactly one committed position document and exactly one `duplicate_active_position_attempt` rejection. **Partial-fill coalescing rule (CG-4 invariant).** NSE CNC orders may fill in multiple partial tranches within the same session, each producing a separate FYERS fill event for the same `order_id`. When LADS detects subsequent fill events for a FYERS `order_id` that has already been matched to an existing `Open` position document (via the intent-ledger reconciliation path in REQ-ORDER-015c or the REQ-ORDER-015a partial-fill path), LADS must apply those additional fills as updates — incrementing `quantity`, recalculating `average_entry_price`, and re-running the REQ-ORDER-015a advisory recalculation — on the **same** existing position document. LADS must never create a second position document for a subsequent fill of the same `order_id`; doing so would produce a `duplicate_active_position_attempt` rejection at the database layer and lose the fill. The single-position-per-intent rule is: one FYERS `order_id` maps to exactly one `intent_ledger` record and therefore to exactly one `positions` document for its lifecycle; all fills against that `order_id` accumulate into that one document. A contract test must cover the two-fill case: a partial fill followed by a completing fill against the same `order_id` must produce one `Open` position with combined quantity and a correctly weighted average entry price, not two separate position documents.
- `REQ-PLC-008` A PendingEntry position must auto-expire and transition to Rejected state if no entry fill is confirmed within a configurable number of trading sessions from the date the signal was generated. The expiry window must be stored in `sys_config` under the key `risk.pending_entry.expiry_sessions` with a default of 1 trading session. On expiry, the Rejected record must carry the reason `pending_entry_expired` and the expiry event must be logged in `rme_events`.
- `REQ-PLC-009` If the EOD Signal Runner for a new trading session generates a fresh entry signal for a symbol that already has a PendingEntry position for the same user, the existing PendingEntry must be automatically superseded: it must be transitioned to Rejected with reason `superseded_by_new_signal`, and a new PendingEntry must be created from the fresh signal with updated entry parameters, ATR, and RME advisory values. The user must receive a notification indicating the advisory has been refreshed. This ensures that PendingEntry positions always reflect the most current signal data.
- `REQ-PLC-011` When a position transitions to Closed or Rejected, the terminal position document must record an `exit_reason` field capturing both the machine-readable exit cause and its numeric exit priority rank per the priority order in REQ-STOP-012 and `docs/portfolio-risk-guidelines.md`. Required machine-readable reason codes and their priority ranks are: `gap_circuit_breach` (rank 1), `stop_loss_hit` (rank 2), `trailing_stop_hit` (rank 3), `portfolio_risk_reduction` (rank 4), `time_stop` (rank 5), `strategy_exit_signal` (rank 6), `rebalancing_exit` (rank 7), `profit_target` (rank 8). Two out-of-band codes carry priority rank 0 because they are user- or admin-driven rather than RME-driven: `manual_exit` (user-initiated discretionary exit via the Phase 1 modal without an active exit advisory) and `admin_forced_close` (admin-triggered state override). When multiple conditions fired simultaneously the exit reason recorded must be the highest-priority condition (lowest rank number) per REQ-STOP-012. The `exit_reason` code and priority rank must be surfaced on the Position Detail page for all Closed and Rejected positions, allowing users and operators to review the causal chain of exits over time. Backtest position records (REQ-BTSTORE-005) must also carry the same `exit_reason` code and priority rank so that exit-cause analysis is consistent between live and backtest views.
- `REQ-PLC-010` When the corporate action detection logic in REQ-PORT-016 flags a non-terminal position (i.e., a position in PendingEntry, Open, or Suspended state), the RME must suspend RME monitoring for that position by transitioning it to Suspended state with reason `corporate_action_detected`. The following actions must be taken atomically with the suspension: (a) write an incident record to `rme_incidents` with `incident_type: corporate_action_suspension`, including the position ID, symbol, the detected discontinuity details (FYERS-reported quantity/value vs. FIFO-derived values), and the detection timestamp — this triggers the admin-actionable incident workflow; (b) block new size additions to the position while it is in `Suspended` state with this reason; (c) emit a user notification of type `corporate_action_warning` per REQ-NOTIFY-006. While the position is in `Suspended (corporate_action_detected)` state, LMDS continues to emit price-level breach notifications to the user (so the user is not blind to price moves against their position), but the RME must not act on those events or attempt to modify the position record until the suspension is resolved. Resolution requires an admin or automated re-anchor pass that applies the corporate action adjustment ratio to the original entry, stop, and all level prices, and writes the adjustment and the new values to the position's audit history. After re-anchoring, the position may be returned to its prior lifecycle state (Open or PendingEntry) by admin action. A contract test must cover the detection-to-suspension path and verify that the position is not modified by RME events while suspended for this reason.
- `REQ-PLC-010a` **Interim corporate action handling during Phase A and Phase B (U-1).** Until full corporate action ingestion and automated processing is available (Phase 9, REQ-NEXT-010), any corporate action that cannot be automatically processed by the platform must follow the interim manual-intervention procedure documented in `docs/operations/runbooks/corporate-action-interim.md`. Three triggering scenarios are covered. (a) **Detected actions:** CA events identified by the REQ-PORT-016 discontinuity check already suspend the position per REQ-PLC-010 and write an `rme_incidents` record; the admin resolves these through the CORPORATE_ACTION path in REQ-ADMIN-016(c). (b) **Undetected actions:** CA events missed by the ADR-0004 threshold — including 3:2 bonus issues whose cost delta falls below 50%, and rights issues — may still be caught by REQ-PORT-016's quantity-mismatch condition (a); however, if FYERS's quantity reporting lags by one session, the mismatch condition may also miss the event for that session. When the admin is aware of a CA from NSE announcements or broker communications before any platform detection fires, the admin must manually suspend the affected position using the `ADMIN` source path in REQ-ADMIN-016(d) before any re-anchoring work is performed, to freeze RME monitoring and prevent erroneous level updates during the lag window. (c) **Operator-reported actions:** CAs learned from any external source for any reason must be handled identically to scenario (b). In all three cases the final resolution path is the re-anchor flow governed by REQ-ADMIN-016(c) (for CORPORATE_ACTION-sourced suspensions) or REQ-ADMIN-016(d) (for ADMIN-sourced manual freezes applied before detection). The interim runbook at `docs/operations/runbooks/corporate-action-interim.md` is a required Phase 5 deliverable and must exist in the repository before Phase 5 (portfolio analytics) implementation begins. A non-blocking advisory banner must be displayed in the admin portal's System Health section during Phase A and Phase B noting that CA detection and resolution is best-effort and requires operator attention, consistent with the Phase A disclaimer in ADR-0004.

### Stop Losses and Exit Alerts

*Stop loss calculation and trailing stop updates are pluggable RME mechanisms. Exit priority ordering is fixed and must not be overridden.*

- `REQ-STOP-001` Each position must have a defined initial stop loss set at the time of entry based on the Signal Subscription's configured stop type.
- `REQ-STOP-002` The platform must support multiple stop loss types, configurable per Signal Subscription.
- `REQ-STOP-003` Supported stop types must include: Fixed Stop Loss, ATR-based Stop, Trailing Stop (percentage-based), Trailing Stop (ATR-based), Swing Low Stop, Break-Even Stop, and Time Stop. Time Stop exits a position after a configurable number of trading sessions from the entry date, as counted by the internal NSE trading calendar. The session count must be configurable per Signal Subscription; the default session count for new Signal Subscriptions is `sys_config.risk.time_stop.default_sessions` (default 10). The `time_stop_date` field required by REQ-PLC-004 is populated at entry by adding the configured session count to the entry date using the trading calendar. **Swing Low Stop default lookback:** The Swing Low Stop must use a configurable lookback window to identify the reference swing low, seeded in `sys_config` under the key `risk.swing_low_stop.default_lookback_bars` with a default of 20 bars measured on the Signal Subscription's configured chart timeframe. When two or more equal-price swing lows exist within the lookback window, the most recent one must be used as the stop reference. The lookback is overridable per Signal Subscription. **Time Stop session-counting semantics:** The Time Stop session count is measured in NSE trading sessions as defined by the internal trading calendar (REQ-CALENDAR-001); calendar days, weekends, exchange holidays, and market-wide circuit-halt days do not count as trading sessions. Partial-day or shortened trading sessions (such as Muhurat trading half-days) are counted as full trading sessions for Time Stop purposes, because the NSE trading calendar records them as scheduled trading sessions.
- `REQ-STOP-003a` When the admin edits the internal NSE trading calendar (adding a session, adding a non-trading-day marker, or removing or modifying an existing record per REQ-CALENDAR-002), the platform must recompute `time_stop_date` for every non-terminal position (PendingEntry, Open, Suspended) that carries a Time Stop. The recompute must be triggered as a post-commit background job immediately after the calendar edit is saved. The recompute rule is: recalculate the `time_stop_date` from the position's entry date using the updated calendar; if the newly computed date lands on a day that is now a non-trading-day or has no session record, roll forward to the next trading session as determined by the updated calendar. For each affected position: (a) write the updated `time_stop_date` to the position document with an audit entry on the document recording the previous date, the new date, and the triggering calendar-edit event; (b) append an `rme_events` record with `event_type: time_stop_recomputed_on_calendar_edit` and the before/after dates. After the recompute completes, the platform must emit a single admin notification (dashboard alert and Telegram admin message) summarising the scope: how many positions were recomputed, how many dates changed, and the date range affected. The recompute is idempotent — re-running it on the same calendar state produces the same result. A contract test must cover the specific edge case where a time-stop date lands on a newly-introduced holiday and must assert it is rolled forward to the next trading session, not left on the holiday.
- `REQ-STOP-004` Additional stop types should be supportable including: Volatility Stop, Portfolio Stop, Equity Curve Stop, Gap Risk Stop, and Circuit Limit Stop.
- `REQ-STOP-005` An EOD job must update trailing stop and break-even stop levels for all active positions based on each Signal Subscription's configured stop rules.
- `REQ-STOP-006` A Live Market Data Scan job must run during NSE market hours and monitor all price levels — stop loss, add levels, and reduce levels — for every open position across all users. The job must fetch live prices using the configured shared market data provider (admin token when FYERS is the configured provider); it must never use individual users' FYERS tokens for this purpose. When a price level is breached, the job must write an alert record to the `notifications` collection and notify the RME so it can update the affected position's state and advisory flags. The scan interval must be configurable via `sys_config`. If the shared market data provider token is unavailable or dirty, the Live Market Data Scan must suspend and a high-visibility warning must appear in the admin portal; this is distinct from and does not affect the per-user Live Account Data Scan.
- `REQ-STOP-006a` The Live Market Data Scan must only run during NSE market hours as defined by the internal trading calendar; it must not poll outside market sessions.
- `REQ-STOP-006c` When the configured shared market data provider delivers delayed quotes (i.e., quotes that are not real-time), the Live Market Data Scan must surface a persistent per-position indicator on the positions summary page and on the individual chart page stating that level monitoring is based on delayed data and showing the known delay duration. The delay duration for each provider must be configured in `sys_config` under the `integrations` category. When FYERS is the configured provider, quotes are treated as real-time and no delay indicator is shown. When any other provider is active, the delay duration seeded in `sys_config` for that provider must be displayed. The indicator must not prevent stop monitoring from running; it is informational only.
- `REQ-STOP-006b` If the shared market data provider is unavailable for a polling cycle, all positions must be skipped for that cycle and the skip must be recorded in the job log. Positions must not be moved to Suspended state solely due to a temporarily unavailable provider. Each open position must display a visible "Level monitoring suspended" indicator on the positions summary page and on the individual chart page while the provider is unavailable. The indicator must clear automatically once the provider is reachable and monitoring resumes.
- `REQ-STOP-007` Exit alerts must deep-link the user to the chart page for the affected symbol.
- `REQ-STOP-008` When the RME has set the exit advisory flag on an open position, the chart page must offer a user-initiated exit action through the standard two-phase execution flow defined in REQ-ORDER-006. The exit action must be available for both full exit and partial exit quantities. When no exit advisory is active, the exit action must still be accessible from the chart page so the user can exit a position at their own discretion at any time. The FYERS API Connect widget handles final submission in Phase 2 as with all other action types. **Positions-summary fast exit affordance (T-8):** The positions summary page must include a persistent "Exit position" action button on every open position row. Clicking the button must open the Phase 1 modal pre-populated with full-exit quantity and market order type. This reduces the click count to initiate a discretionary or emergency exit to one from the positions summary page, while preserving the full modal-and-widget advisory chain (the advisory-only invariant is unchanged). The Phase 1 modal opened from this button must behave identically to one opened from the chart page, including all RME context, warnings, and the FYERS widget Phase 2 flow.
- `REQ-STOP-009` A break-even stop must be capable of moving the stop to the entry price once the position reaches a configurable profit level, defaulting to 1R gain.
- `REQ-STOP-010` Gap risk stop handling must detect when a session opens with price gapping past the active stop level and surface an advisory alert treating the gap open as the effective exit price.
- `REQ-STOP-011` Circuit limit stop handling must detect when a held stock hits an NSE upper or lower circuit limit and surface an advisory alert for the user.
- `REQ-STOP-012` When multiple exit conditions are triggered simultaneously, the platform must apply the following exit priority order: catastrophic gap or circuit stop first — including market-wide halts per REQ-HALT-007 — then hard stop loss, trailing stop, portfolio risk reduction, drawdown control exit, time stop, strategy exit signal, rebalancing exit, and profit target exit last.

## Part 6 — Portfolio and Accounting

*Implemented by a .NET portfolio service that syncs from FYERS and maintains the internal trade ledger. Depends on Part 2 (auth) and Part 3 (market data) being operational.*

### Portfolio Analytics and Accounting

*The platform maintains its own trade ledger and computes FIFO-based PnL independently of broker-provided figures.*

- `REQ-PORT-001` The platform must sync user trades, holdings, positions, and orders from FYERS into MongoDB.
- `REQ-PORT-002` The platform must maintain an internal immutable trade ledger in MongoDB for each user.
- `REQ-PORT-003` When a user first connects FYERS, the platform must fetch their available trade history using the FYERS Trade History API going as far back as the API permits, and their current-day trades using the FYERS transaction endpoint, to initialise the internal trade ledger and FIFO state for current holdings and positions. If the API returns zero trades (a new FYERS account with no prior activity), the platform must silently initialise an empty trade ledger for the user and proceed normally; an empty history is not an error and must not trigger the incomplete-history warning defined in REQ-PORT-013.
- `REQ-PORT-004` Ongoing FYERS sync must ingest new trades, orders, holdings, and positions incrementally and idempotently.
- `REQ-PORT-005` The platform must tolerate users placing orders outside this portal directly through the broker.
- `REQ-PORT-005a` When FYERS sync returns trades or holdings for symbols not present in the platform's symbol master, those records must be silently ignored and must not be ingested into the trade ledger, displayed in the portal, or considered in any RME calculation including portfolio heat, position sizing, drawdown tracking, and scan eligibility. All trades in symbols that are present in the symbol master — regardless of whether the order was placed via the platform or directly through the FYERS app — must be ingested and tracked. The platform does not display or account for activity in symbols outside the Nifty 500 symbol master. When a symbol is newly added to the symbol master via a CSV upload (REQ-UNIV-014), the platform's go-forward sync will begin ingesting trades in that symbol from that point on, but historical trades that occurred while the symbol was outside the universe are not retroactively backfilled by automatic sync; the user-opt-in retroactive backfill flow defined in REQ-PORT-030 is the explicit mechanism for capturing such history.
- `REQ-PORT-030` When a CSV upload adds one or more net-new symbols to the symbol master, the platform must identify users whose current FYERS holdings include any of those symbols and notify each affected user with a one-time prompt offering to run a retroactive single-symbol trade-ledger backfill for the newly-added symbol. The backfill, if accepted, executes the same logic as the per-user "Rebuild trade ledger from broker" operation in REQ-PORT-027 but scoped to a single symbol and the user's available FYERS Trade History window. Single-symbol scope keeps FYERS API consumption modest and predictable. Backfill is opt-in only; declining or ignoring the prompt leaves the trade ledger as go-forward-only for that symbol, with the holding marked as having incomplete trade history per REQ-PORT-013, prompting the standard manual-opening-adjustment flow if the user later wants accurate FIFO. Each backfill invocation must be recorded in `audit_events` with the user, the symbol, the time window replayed, and the outcome.
- `REQ-PORT-006` The platform must tolerate arbitrary user trade sequences including add, partial sell, full exit, and re-entry.
- `REQ-PORT-007` The platform must compute average buy, realised PnL, and unrealised PnL for holdings using synced trade history because broker-provided position PnL is limited.
- `REQ-PORT-008` Average buy must be derived from the remaining open lots under FIFO after partial exits.
- `REQ-PORT-009` FIFO calculations must use the platform's internal trade ledger as the source of truth, with broker positions and holdings used as reference and reconciliation inputs.
- `REQ-PORT-010` Platform-calculated realised and unrealised PnL are gross and exclude brokerage, taxes, and statutory charges.
- `REQ-PORT-011` Portfolio analytics must cover holdings that span multiple days, months, or years.
- `REQ-PORT-012` The platform must reconcile computed holdings against broker-reported holdings and surface mismatches for investigation.
- `REQ-PORT-013` For any holding where FIFO state cannot be fully initialised because trade history predates the earliest date available from the FYERS Trade History API, the holding must be flagged as having incomplete trade history.
- `REQ-PORT-014` Holdings flagged as having incomplete trade history must prompt the user to enter a manual opening adjustment to seed the FIFO state, providing quantity, average buy price, and an approximate date; this uses the same audited adjustment flow as the reconciliation adjustment mechanism.
- `REQ-PORT-015` A manual opening adjustment used to seed an incomplete-history holding must be recorded as a seeded opening balance entry in the trade ledger, clearly distinguished from broker-synced trade records, and must carry an audit trail including who entered it and when.
- `REQ-PORT-016` Until corporate actions handling is available (Phase 9), the platform must detect potential corporate action events by monitoring for discontinuities between FYERS-reported holding quantities or prices and the internal trade ledger state that cannot be explained by known trades. A discontinuity must be flagged if either of the following conditions is true: (a) the FYERS-reported quantity for a holding differs from the platform's FIFO-computed quantity by any non-zero amount; or (b) the implied average cost per unit derived from the FYERS-reported holding value differs from the platform's FIFO-derived average buy price by more than a configurable threshold, seeded in `sys_config` under the key `risk.corporate_action.avg_cost_delta_threshold_pct` with a default of 50 (representing a 50% deviation). The threshold is configurable because the 50% default is a first-principles estimate: a 2:1 stock split produces exactly a 50% cost-per-unit change (potentially triggering the flag at the boundary), while a 3:2 bonus issue produces a 33% change (falling below the threshold and not triggering it). Before Phase 5 (portfolio) implementation the threshold must be calibrated against a sample of actual NSE corporate actions as documented in `docs/adr/0004-corporate-action-detection-threshold.md`; the calibration outcome must update the `sys_config` seed value if it differs from 50. When a discontinuity meeting either condition is detected on sync, the affected holding must be flagged with a prominent warning that a corporate action may have occurred and that portfolio figures for that holding may be inaccurate. No automatic price or quantity adjustment must be made.
- `REQ-PORT-017` A holding flagged under REQ-PORT-016 must remain visibly marked until the user explicitly dismisses the warning or raises a manual adjustment. The user must be prompted to review the holding and use the standard audited manual adjustment flow if a correction is needed.
- `REQ-PORT-018` An initial FYERS account sync must be triggered automatically when a user logs in and their FYERS token is valid, and again each time a user successfully completes FYERS re-authentication. This ensures portfolio data is refreshed at the start of every session without requiring manual action.
- `REQ-PORT-019` During NSE market hours as defined by the internal trading calendar, the platform must run FYERS account sync for each user with a valid FYERS token on a configurable recurring interval. The interval must be stored in `sys_config` under the key `jobs.account_sync.intraday_interval_minutes` and must support values of 5, 10, 15, 30, and 60 minutes. Sync must not run outside market hours under this schedule; it must respect the trading calendar and not poll during exchange holidays or after market close.
- `REQ-PORT-020` An EOD account sync must run automatically after market close for all users with valid FYERS tokens, after the market data DataSync job has completed for the session. This final sync must capture settled trades, updated positions, and end-of-day holdings before the next trading session begins. The EOD account sync must write an explicit per-user success or failure marker so the dashboard can show data freshness accurately. EOD account sync must proceed independently of DataSync outcome: if DataSync fails for the session, EOD account sync must still run to capture settled trades and updated positions from FYERS. However, when DataSync has failed for the session, the portfolio snapshot written after EOD account sync must carry a visible data quality warning indicating that market prices in the snapshot may be stale because EOD market data sync did not complete successfully for that session. This warning must be surfaced on the dashboard data freshness indicator required by REQ-DASH-013 until a successful DataSync run updates the SQL Server data for that session.
- `REQ-PORT-021` Users must be able to trigger a manual account sync at any time from the dashboard or holdings page regardless of market hours. Manual sync must be rate-limited per user to prevent abuse; the minimum interval between manual sync requests must be configurable via `sys_config` (default 2 minutes). The portal must show sync status (in progress, last successful sync timestamp, or last error) so the user knows when data was last refreshed.
- `REQ-PORT-021a` The LADS (Live Account Data Scan) intraday polling loop must instrument cycle-level failure visibility and apply graduated suspension on repeated MongoDB write failures. Specifically: (a) every LADS cycle that aborts due to a MongoDB connection error or write failure (including replica-set failover windows, which typically produce 10–30 second outages) must increment an OpenTelemetry counter `lads.cycle.aborted.total` with a `reason` label (e.g., `mongo_write_error`, `mongo_connection_lost`); (b) if two consecutive LADS cycles abort for MongoDB reasons, the admin System Health widget (REQ-ADMIN-014) must surface a warning showing the consecutive abort count and the reason; (c) if three or more consecutive LADS cycles abort for MongoDB reasons, the platform must: suspend new entry intent creation for all users (applying the same block as REQ-ORDER-005 but at platform level, not per-user); emit an admin Telegram alert and dashboard alert identifying the sustained LADS failure, the consecutive abort count, and the elapsed time since the last successful cycle; and record a `lads_sustained_failure` incident in `rme_incidents`. The suspension is released automatically on the next successful LADS cycle completion. A successful LADS cycle resets the consecutive-abort counter to zero. The expected MongoDB replica-set failover behaviour (brief abort followed by automatic recovery) must be documented in the MongoDB operational runbook. **Worker-side MongoDB write retry semantics (A-12):** All Worker Service MongoDB writes — including intent-ledger updates, RME channel consumer writes, notification writes, equity-curve writes, and portfolio-snapshot writes — must use the MongoDB driver's built-in retry semantics (`retryWrites: true` in the connection string, which is the driver default for replica-set connections). The RME channel consumer must additionally treat driver-level retry exhaustion (i.e., a `MongoException` thrown after the driver has exhausted its internal retries) as a third-consecutive-abort equivalent for the LADS event that triggered the write, triggering the same admin advisory path as the three-consecutive-abort threshold above. This ensures that transient MongoDB failovers during non-LADS Worker writes are handled gracefully and do not produce silent data loss.
- `REQ-PORT-022` The platform must maintain a separate append-only equity curve time series for each user in the `equity_curve` MongoDB collection. One record must be written per completed trading session (after EOD account sync completes per REQ-PORT-020), storing: user ID, session date, total portfolio market value, cumulative realised PnL to date, unrealised PnL, equity high-water mark at that point, and drawdown from the high-water mark as a percentage. The equity curve is the authoritative source for drawdown tracking (REQ-DRDN-001), equity-curve-based sizing adjustments (REQ-DRDN-006), and historical portfolio performance visualisation. It is entirely separate from the `portfolio_snapshots` collection, which serves only as a display cache for the current-state dashboard view. An equity curve record must be written even when the user has no open positions and zero unrealised PnL, so that the time series remains unbroken for drawdown and XIRR calculations; in this case, total portfolio market value equals zero and all PnL fields are zero. If a user's initial FYERS sync completes mid-session rather than at EOD, no partial-day equity curve record is written; the first equity curve entry for that user is written at the end of the first completed trading session after onboarding, following the normal EOD sync flow.
- `REQ-PORT-023` The trade ledger dedup key is the FYERS `trade_id`, which is globally unique within the user's FYERS account. Trade ingestion must reject any attempt to insert a trade record whose `trade_id` already exists for that user; the incoming record is discarded as a duplicate and the event logged at debug level with the `trade_id`. This rule makes every sync path — initial bootstrap, intraday, EOD, and admin-triggered rebuild — idempotent by design.
- `REQ-PORT-024` Broker order records in `broker_orders` are keyed per user by FYERS `order_id`. Each incoming order record overwrites the existing record with the same `order_id` if present; this is point-in-time snapshot behaviour and is consistent with the short-lived cache lifecycle described in `docs/data-management.md`. No historical order-state time series is maintained; only the latest status per order is retained, aged out by the existing TTL rule.
- `REQ-PORT-025` All FYERS-provided timestamps must be converted to UTC on ingest and stored as UTC throughout MongoDB per engineering standards. Conversion must tolerate up to 5 seconds of clock skew between the platform and FYERS without triggering spurious duplicate-detection mismatches or out-of-order events that are within the skew tolerance.
- `REQ-PORT-026` Out-of-order trade ingestion — where a newly-synced trade carries a `trade_at` earlier than the most recently applied trade for the same user and symbol — must be handled correctly. The trade is inserted at its correct chronological position in the ledger, and FIFO-derived state (average buy price, realised PnL, open lots, and portfolio heat contribution) is recomputed from the earliest affected date forward for the affected symbol. The recomputation must be logged with scope, earliest affected date, and duration. Downstream records dependent on the recomputed state — open position records, equity curve entries beyond the affected date — must also be refreshed as part of the same recomputation. The FIFO recomputation is a sub-operation of the sync that detected the out-of-order trade; it executes under the trade-ledger write lock already held by that sync call per REQ-PORT-031 and must not acquire a separate lock. No recomputation may begin outside of a held lock.
- `REQ-PORT-027` The admin portal must expose a per-user "Rebuild trade ledger from broker" operation that replays the FYERS Trade History API over the user's available history window and re-applies dedup and ordering rules per REQ-PORT-023 through REQ-PORT-026. This operation is intended for corruption recovery, upstream API behaviour changes, or post-incident reconciliation. It must require admin step-up re-authentication per REQ-SEC-011 and must be recorded in `audit_events` with the affected user, the history window replayed, and the outcome. During a rebuild, the affected user's write path to the trade ledger must be paused so new live-sync writes do not interleave with the replay. This pause is implemented by acquiring the trade-ledger write lock for the affected user per REQ-PORT-031 with blocking-wait semantics before any replay work begins, and holding it for the full duration of the rebuild. The admin portal must surface the lock-acquisition wait as a loading state so the operator knows the rebuild is queued behind an active sync. Lock renewal must be active throughout the rebuild duration per REQ-PORT-031.
- `REQ-PORT-028` When a corporate action discontinuity is flagged on a holding per REQ-PORT-016, the RME must immediately suspend stop-level updates and stop-breach alert generation for any Open position in that symbol. The "Level monitoring suspended" indicator defined in REQ-STOP-006b must be applied to the position with a distinct reason code `corporate_action_discontinuity_detected` that differentiates it from the provider-unavailable case. No position state transition occurs; the position remains Open. The Live Market Data Scan continues polling the symbol so price movement is not lost, but breach evaluation is paused until the user resolves the discontinuity.
- `REQ-PORT-029` When the user resolves a corporate action discontinuity by raising a manual adjustment per REQ-PORT-014 and REQ-PORT-017, the RME must re-initialise the affected Open position's 1R risk amount, active stop level, trailing stop level, add and reduce levels, and portfolio heat contribution using the adjusted average buy price from the adjustment entry. The user must explicitly confirm the re-initialised stop level through a dedicated acknowledgement screen before stop monitoring resumes; the position continues to show the `corporate_action_discontinuity_detected` indicator until this confirmation is complete. The entire before and after state of the position — quantity, average buy price, stop level, initial risk, advisory levels — must be captured in `rme_events` and in `audit_events`.

### Trade-Ledger Write Serialisation

*Every write path that touches the trade ledger, triggers a FIFO recomputation, or refreshes the portfolio snapshot must acquire a per-user distributed lock before beginning. This prevents concurrent sync paths — intraday polling, on-login sync, manual sync, EOD sync, and admin rebuild — from interleaving writes on the same user's ledger, which would corrupt FIFO-derived average buy prices, realised PnL, equity curve entries, and all downstream RME risk calculations that depend on them.*

- `REQ-PORT-031` The platform must implement a per-user trade-ledger write lock using Redis (available per `REQ-DATA-006`). The lock key format is `ledger:write:lock:{userId}`. Every write path that modifies the trade ledger, triggers FIFO recomputation, or writes a portfolio snapshot for a given user must acquire this lock before beginning any work and must hold it for the full duration of the operation, including any downstream FIFO recomputation and equity-curve refresh triggered as a consequence. The lock must use a unique per-acquisition token (UUID) as its value so that only the holder can release it; releasing a lock whose stored value does not match the acquisition token must be a no-op. Lock TTL must be set at acquisition time to a value that covers the worst-case operation duration — seeded in `sys_config` under the key `jobs.ledger_lock.ttl_seconds` with a default of 600 seconds (10 minutes). For operations expected to run longer than half the TTL (specifically the admin "Rebuild trade ledger from broker" per REQ-PORT-027 and the single-symbol backfill per REQ-PORT-030), the holder must renew the lock by resetting its TTL at a configurable interval seeded in `sys_config` under the key `jobs.ledger_lock.renewal_interval_seconds` with a default of 60 seconds; renewal must only succeed if the lock value still matches the holder's token. A failed renewal (value mismatch) means another process has taken the lock; the current operation must abort immediately with a structured error log entry and an `audit_events` record noting the interrupted operation, the user, and the elapsed time at abort. Lock acquisition behaviour must differ by caller as follows. Every write path listed here is an authorised lock acquirer; no other path may modify the trade ledger without first acquiring this lock. Authorised acquirers: LADS intraday polling (REQ-PORT-019), on-login sync (REQ-PORT-018), EOD sync (REQ-PORT-020), user-triggered manual sync (REQ-PORT-021), admin "Rebuild trade ledger from broker" (REQ-PORT-027), single-symbol backfill (REQ-PORT-030), and **manual adjustment write paths (REQ-PORT-014/015, REQ-RECON-003/004)** — manual adjustments modify FIFO-derived state and the trade ledger, and must be lock-protected with blocking-wait semantics identical to admin rebuild. This omission was an oversight; manual adjustments applied concurrently with a sync path would corrupt FIFO-derived average buy prices. Acquisition semantics per caller: (a) background sync jobs (LADS intraday polling per REQ-PORT-019, on-login sync per REQ-PORT-018, EOD sync per REQ-PORT-020) must use a non-blocking try-acquire with a timeout of 0 — if the lock is held, the job must skip the affected user for that cycle, log the skip at warning level with the user ID and the current lock holder's operation type if determinable, and move to the next user; skips must not be treated as errors and must not trigger alerts unless the same user is skipped for more than a configurable consecutive-skip threshold seeded in `sys_config` under `jobs.ledger_lock.skip_warn_threshold` with a default of 3; (b) user-initiated manual sync (REQ-PORT-021) must use a try-acquire with a timeout of 5 seconds — if the lock is not acquired within 5 seconds, the portal must surface a clear message stating that a sync is already in progress for this account and the user should try again shortly; (c) admin "Rebuild trade ledger from broker" (REQ-PORT-027) and single-symbol backfill (REQ-PORT-030) must use a blocking wait with a timeout of 30 seconds — if not acquired within 30 seconds the admin portal must surface an error stating that another operation is active on this user's ledger and show its expected completion time if available. The current lock holder and approximate lock age must be surfaced in the admin portal System Health widget (REQ-ADMIN-014) per-user when a ledger lock is active, so the admin can diagnose a stuck lock without resorting to direct Redis inspection. The lock only provides mutual exclusion between writers; readers that need a consistent view of the ledger-derived state must use the snapshot-version protocol defined in REQ-PORT-031a and consumed by the RME per REQ-RME-006d. Nothing in REQ-PORT-031 permits readers to proceed against a partially-applied write.
- `REQ-PORT-031a` Every user document in MongoDB must carry a `ledger_snapshot_version` field (long integer, initialised to 1 on user creation, monotonically non-decreasing, never reset or recycled). The value must be incremented by 1 as the final durable step of every write path covered by REQ-PORT-031, before the REQ-PORT-031 lock is released. The increment must be covered by the same MongoDB transaction or unit of work as the trade-ledger write, FIFO recomputation, and portfolio-snapshot refresh that the lock protects, so that either the write commits and the version advances atomically together or both roll back together — a partial commit where the ledger advances but the version does not (or vice versa) is a contract violation and must be treated as an abort. This version is the sole coordination point for readers that require a consistent view of ledger-derived state under the reader contract defined in REQ-RME-006d; consumers must never attempt to infer consistency from timestamps, lock-held signals, or collection-level modification counts. The version is write-only from the REQ-PORT-031 path: no other code path may increment it, and no code path may decrement or reset it. **Invariants that must be upheld without exception:** (i) `ledger_snapshot_version` is incremented only *after* all writes in the protected unit of work have durably committed — it must never be incremented at the start of a write attempt or during an OCC retry loop; premature increments would allow readers to observe a "consistent" version while the underlying write is still in-flight or may yet be retried and rolled back. (ii) `ledger_snapshot_version` gates the consistency of trade-ledger-derived state only — specifically: `trade_ledger`, `holdings`, `portfolio_snapshots`, and `equity_curve` records written under the REQ-PORT-031 lock. It does **not** gate the consistency of RME-managed position fields (such as `trailing_stop_level`, `exit_advisory_active`, `_version`) which are written by the RME via the OCC path defined in REQ-RME-CONC-002, outside the trade-ledger write lock. Readers that require a fully consistent view of **both** ledger-derived state and the current RME state of a specific position must independently check the position document's `_version` field after completing the `ledger_snapshot_version` protocol defined in REQ-RME-006d; the two version fields together provide a complete consistency guarantee; neither alone is sufficient when both trade-ledger state and RME position state are being read in the same computation. (iii) During the OCC retry loop in REQ-RME-CONC-002, if the RME's OCC write fails and the event is retried from a freshly-read position document, the `ledger_snapshot_version` value the RME observed before starting the computation must be re-read from the user document before each retry — using a stale `ledger_snapshot_version` from the first attempt with a freshly-read position document from a later version would produce a torn cross-document view. The RME's snapshot-consistent read protocol (REQ-RME-006d) must therefore be re-executed in full at the start of each OCC retry, not just the position document re-read.
- `REQ-PORT-031b` The trade-ledger write lock defined in REQ-PORT-031 must be implemented with Redlock semantics plus a fencing token to guard against Redis key eviction invalidating a held lock. Specifically: (a) **Redlock acquisition:** the lock must be acquired using the Redlock algorithm (quorum-based acquisition across at least three independent Redis nodes or, in a single-node deployment, across the single node with the explicit acceptance that single-node Redlock degrades to a simple SET NX with TTL — document the trade-off in `docs/system-architecture.md`); (b) **Fencing token:** every successful lock acquisition must obtain a monotonically increasing fencing token — implemented as an atomic Redis INCR on a per-user counter key `ledger:write:fence:{userId}` — and include this token in every MongoDB filter for trade-ledger writes under that lock acquisition, in the form `{ "ledger_fence_token": { "$lte": <acquired_token> } }`; a MongoDB write that matches zero documents because the stored fence token has advanced past the holder's token must be treated as a stale-write abort, not a version conflict — the holder must release the lock, log the eviction-induced conflict at Error level, and surface an `audit_events` record noting the interrupted operation; (c) **noeviction on lock keyspace:** the Redis deployment (REQ-DATA-006a) must configure a dedicated logical database index (the `LOCK_DB_INDEX` referenced in Redis connection strings) for lock keys (`ledger:write:lock:*`, `ledger:write:fence:*`, `rme:worker:singleton`) with `maxmemory-policy noeviction`; cache keys that may be evicted must live in a separate logical database index with an eviction-friendly policy; the separation must be documented in `docs/system-architecture.md` and enforced in the Azure Cache for Redis configuration managed by infrastructure-as-code; (d) **Position document writes under the RME are out of scope for REQ-PORT-031b** — they are governed by the OCC version check in REQ-RME-CONC-002 and the per-position channel serialisation in REQ-RME-CONC-001, not by the trade-ledger write lock. (e) **Fencing-token abort must not advance ledger_snapshot_version (A-11):** A fencing-token abort as described in (b) — where a MongoDB write is rejected because the stored fence token has advanced past the holder's token — must neither increment nor have previously incremented the `ledger_snapshot_version` field on the user document. The abort means no trade-ledger write was durably committed; incrementing the version would allow readers to observe a "consistent" snapshot version while the underlying write state is in fact unmodified or partially torn. The implementation must ensure that `ledger_snapshot_version` is incremented only as the final step of a confirmed durable commit — which, for the fencing-token abort path, never occurs. A contract test must assert that a simulated fencing-token abort (fence token advanced before write) leaves `ledger_snapshot_version` unchanged from its pre-operation value.

### User Dashboard

*The default home page after sign-in. Shows portfolio health, performance, sector breakdown, and RME advisory state at a glance.*

- `REQ-DASH-001` The platform must provide a user dashboard as the default home page after sign-in.
- `REQ-DASH-002` The dashboard must display a portfolio summary section showing: total invested amount (cost basis of all open positions), current market value, absolute return in both cash value and percentage, and XIRR return.
- `REQ-DASH-003` XIRR must be calculated from the internal trade ledger using actual buy dates and invested amounts as cash flow inputs and current market value as the terminal value. Current market value must be derived from the most recently available closing price from SQL Server. During NSE market hours, if a live FYERS quote fetched via the user's token is available and more recent than the last SQL Server close, the live quote may be used as the current price instead. The pricing source and its timestamp must be reflected in the data freshness indicator required by REQ-DASH-013.
- `REQ-DASH-003a` The XIRR cash flow construction algorithm must be specified as follows to ensure correctness across partial exits and re-entries. Each row in the trade ledger maps to a dated cash flow: a buy (or add) trade produces a **negative** cash flow equal to `quantity × price` (capital deployed); a sell (reduce or full exit) trade produces a **positive** cash flow equal to `quantity × price` (capital returned). The terminal value — the current market value of all remaining open holdings — is appended as a **positive** cash flow dated today. All cash flows across all holdings are combined into a single chronological series (not one series per holding) before passing to the XIRR solver. Re-entries after a full exit produce additional negative cash flows at the re-entry dates; there is no netting or pairing of buy and sell flows — every trade generates its own dated entry in the series. The XIRR solver must use the Newton-Raphson iterative method with a maximum of 200 iterations and a convergence tolerance of 0.000001; if the solver fails to converge (typically because all cash flows are positive or the rate is not meaningful), the XIRR field must be displayed as "N/A" with a tooltip explaining the condition rather than showing an incorrect or placeholder value. Brokerage, taxes, and statutory charges are excluded from cash flows per REQ-PORT-010; XIRR therefore reflects gross returns. This algorithm must also be applied to XIRR computation in backtest result reporting (REQ-BTSTORE-006).
- `REQ-DASH-003b` XIRR computation must define explicit behaviour for positions in Suspended state. A Suspended position must contribute to the terminal cash-flow value used by the XIRR solver at its last-known mark-to-market price: the most recently available daily closing price from SQL Server, or, if an intraday FYERS live quote was fetched via the user's token more recently than the last SQL Server close, that live quote. The Suspended position's cost basis (buy cash flows) continues to appear in the XIRR cash-flow series unchanged. The XIRR display on the dashboard must include a visible disclosure footnote whenever one or more Suspended positions are contributing to the calculation, stating the number of suspended positions and a note that their market value is based on last-known price and may not reflect current market conditions. The same marked-to-last-known-price rule applies to Suspended positions in backtest XIRR calculations per REQ-BTSTORE-006, and to any XIRR computation driven by the portfolio analytics layer.
- `REQ-DASH-004` The dashboard must display portfolio performance for the following periods: today, rolling last 5 trading sessions, rolling last 15 trading sessions, rolling last 30 trading sessions, week to date (WTD), and month to date (MTD).
- `REQ-DASH-005` All rolling period calculations must use trading sessions from the internal NSE trading calendar, not calendar days.
- `REQ-DASH-006` When the current day is a trading holiday or before market open, the today period must reflect the last completed trading session.
- `REQ-DASH-007` Period performance is the net change in portfolio market value during that period, comprising unrealised PnL movement plus realised PnL from any positions closed within the period.
- `REQ-DASH-008` The dashboard must display a sector breakdown section showing portfolio exposure and performance grouped by the Industry classification from the symbol master.
- `REQ-DASH-009` The sector breakdown must show per sector: number of open positions, total invested, current market value, absolute return value and percentage, and sector weight as a percentage of total portfolio value.
- `REQ-DASH-010` The dashboard must display a positions summary section showing all open positions with per-position data: symbol, quantity, average buy price, current price, current market value, absolute PnL, percentage PnL, current R multiple, holding period, and active RME advisory state.
- `REQ-DASH-011` Active RME advisory flags that must be visible per position on the dashboard include: add advisory active, reduce advisory active, exit advisory active, and whether the position is in Suspended state.
- `REQ-DASH-012` The dashboard must display a persistent RME portfolio health strip showing: current portfolio heat as a percentage, current drawdown from equity high-water mark, active drawdown mode level if any, total number of open positions, and a **portfolio-level freshness indicator** showing the age of the oldest position-data component currently visible in the portfolio. The freshness indicator is a single roll-up timestamp displayed as "Data as of: {timestamp}" where the timestamp is the minimum of the last successful LADS cycle completion time, the last successful LMDS price update for any open position, and the equity-base last-synced timestamp. This gives the trader a single at-a-glance signal for the overall currency of their portfolio view — relevant during LADS-sustained-failure or provider-unavailable windows where multiple per-position stale indicators would otherwise provide a confusing and fragmented picture.
- `REQ-DASH-013` Market value and performance figures on the dashboard must display the most recently available price data and must show a data freshness timestamp so the user knows when prices were last updated.
- `REQ-DASH-014` The dashboard must be responsive to the NSE trading calendar; performance period labels and calculations must automatically shift at the start of each new trading session.
- `REQ-DASH-015` Dashboard portfolio figures must be served from the user's latest portfolio snapshot (stored in the `portfolio_snapshots` MongoDB collection) on every normal page load. This avoids a live FYERS API call on every visit and reduces load on the trade ledger query layer. A snapshot is written to the collection — overwriting the previous one in place — after each account sync completion (intraday polling sync per REQ-PORT-019, on-login sync per REQ-PORT-018, and EOD sync per REQ-PORT-020) and after each user-triggered manual refresh per REQ-DASH-016. If no snapshot yet exists for a user (first login after FYERS connection), the dashboard must compute portfolio figures on demand from the trade ledger and SQL Server closing prices, write the result as the initial snapshot, and then display it. Period performance calculations (REQ-DASH-004/007) reconstruct the portfolio's historical market value at each period boundary by replaying the FIFO trade ledger to derive holdings as of that date and applying the corresponding session closing prices from SQL Server; these computed period values are also stored in the snapshot so they are not recomputed on every page load.
- `REQ-DASH-016` The dashboard must provide a manual refresh button that forces a full recomputation of all portfolio figures using the latest available market data, regardless of when the last snapshot was written. On refresh: the platform fetches fresh live quotes from FYERS using the user's token for all open positions, replays the trade ledger for current holdings, recomputes all dashboard figures including period performance and sector breakdown, writes the result as the new snapshot, and renders the updated figures. The data freshness timestamp required by REQ-DASH-013 must reflect the moment the refresh completed. The refresh button must be visibly disabled while a refresh is in progress to prevent concurrent requests. The refresh must be subject to the per-user rate limit governed by `sys_config` key `jobs.account_sync.manual_sync_min_interval_seconds` to prevent abuse.
- `REQ-DASH-017` The admin portal must include a platform portfolio overview page that reads the latest snapshot from each user's `portfolio_snapshots` record and displays an aggregate view of all active user portfolios. The view must show per-user: last snapshot timestamp, total market value, total unrealised PnL, portfolio heat, and active position count. This page is read-only and intended for the admin to monitor portfolio health and risk concentration across the platform without triggering live FYERS API calls. For users who have completed FYERS authentication but have no snapshot yet (first sync has not completed), the row must still appear in the overview with all metric columns showing a "No data yet" placeholder and the last snapshot timestamp shown as "Never".
- `REQ-DASH-018` The `portfolio_snapshots` cache must define explicit invalidation triggers and a bounded TTL ceiling so that a stale snapshot is never displayed indefinitely. Invalidation triggers — each of which causes the affected user's snapshot to be recomputed and overwritten on the next dashboard read or background sync — are: (a) any LADS cycle that writes one or more new trade records to the `trade_ledger` for the user; (b) any manual admin adjustment recorded via REQ-RECON-005 that affects the user's ledger or FIFO state; (c) EOD account sync completion for the user per REQ-PORT-020. In addition to event-driven invalidation, a TTL ceiling must be enforced: the dashboard API must treat a snapshot as stale if its `written_at` timestamp is older than `sys_config.dashboard.portfolio_snapshot.ttl_seconds` (default 900 seconds). When a stale snapshot is detected on a dashboard read, the API must trigger a background recomputation and serve the stale snapshot with a visible data-freshness indicator per REQ-DASH-013 disclosing the snapshot age, rather than blocking the page render. The dashboard cache key used by the API layer must incorporate the user's `ledger_snapshot_version` from REQ-PORT-031a, so that any cached snapshot computed against a prior ledger version is automatically treated as stale as soon as the ledger version advances — making stale snapshots unreachable by construction on ledger writes, regardless of TTL.

At most one rotation-due notification may fire per 7-day window to prevent reminder spam; the admin may acknowledge-and-defer via the portal, which resets the 7-day window without changing the rotation threshold. (c) **Token replacement triggers disable-and-re-enable cycle.** When the admin replaces the bot token via REQ-NOTIFY-015, the platform must: (1) automatically set `global_disable = true` for the duration of the token validation call; (2) on successful validation and Key Vault write, immediately set `global_disable = false` and record `last_token_replaced_at` on the bot token metadata; (3) if validation or Key Vault write fails, leave `global_disable = true` and require the admin to retry or clear the flag manually. This ensures no delivery occurs against a stale or potentially compromised token during the replacement window.
- `REQ-NOTIFY-022b` In addition to the 15:00 IST DataSync-window check in REQ-NOTIFY-022, a second admin FYERS token validity check must run each NSE trading day before market open. The pre-market check must not run on weekends or exchange holidays per the same calendar used in REQ-NOTIFY-022. The pre-market check specifically targets the case where the admin forgets to generate a daily FYERS token before LMDS starts for the day, which would cause intraday market data ingestion to fail silently without the reactive job-startup guard (REQ-MARKET-005) being present.
- `REQ-NOTIFY-023` The Notification Delivery Job must implement idempotent delivery to prevent double-sending on retry after a crash between HTTP send and MongoDB acknowledgement. The idempotency mechanism works as follows: (a) before dispatching to Telegram, the Notification Delivery Job must generate a deterministic `client_message_id` derived from the notification's `_id` field (for example, using the `_id` as the base-62 encoded Telegram `parse_mode`-compatible message identifier field, or — if Telegram's bot API supports it for the account type — as a parameter on the `sendMessage` call); (b) after a successful Telegram API response the job must persist Telegram's returned `message_id` on the notification record in MongoDB as `telegram_message_id`, then set `delivery_status` to `delivered`; the persistence of the Telegram `message_id` is the durable acknowledgement — the delivery is considered complete only after this write succeeds; (c) on retry after a crash, the job must check whether `telegram_message_id` is already set; if it is, the notification was already delivered and must be skipped (no re-send); if it is not, the crash occurred before the Telegram response was persisted and the message must be re-sent; (d) for notification types where Telegram does not return a usable `message_id` (for example, some bot-API edge cases), the job must fall back to writing a deterministic per-notification sent-at timestamp as the idempotency anchor, with the same pre-send check semantics. The `telegram_message_id` field must be added to the notification record schema per REQ-NOTIFY-005.

For partial fills per REQ-ORDER-015a the notification must additionally state the filled and unfilled quantities separately (e.g., "Filled: 50 of 100 units requested"). The Telegram message text and the portal notification feed entry may differ in formatting (the portal entry is richer; Telegram is constrained by message length), but both must include all eight fields above. The field set and the naming conventions defined here are locked to prevent Phase 4 (EODSR signal generation) and Phase 6 (RME advisory) from shipping divergent notification formats; any addition or removal of a required field requires a REQ update and must be treated as a breaking change to the notification contract. **Dispatch ordering invariant (L-3).** For all LADS-initiated fill notifications — including the fill-before-callback case where LADS processes the fill before the widget `finished` callback has arrived (REQ-ORDER-015g matrix row 4) — the notification writer must durably commit all required MongoDB writes before dispatching any Telegram message or portal feed entry. The required write sequence, in order, is: (1) update the `intent_ledger` record — for fill-before-callback, LADS must transition the intent_ledger from `pending` to `matched` with `match_source = "lads_reconciliation"` before the notification is dispatched; the callback, when it eventually arrives, then stamps `callback_received_at` on the already-`matched` record (REQ-ORDER-015); (2) update the `positions` document to `Open`; (3) dispatch the Telegram notification and portal feed entry. This ordering guarantee ensures the notification is never dispatched against an `intent_ledger` record still in `pending` state, which would present an inconsistent view to a concurrent reader or to the user inspecting their intent history. A contract test must assert that, for the fill-before-callback case, the `intent_ledger` status is `matched` and the `positions` document is `Open` at the time the Telegram notification is observed as dispatched.

- `REQ-ORDER-005` If an order for the same symbol and action type is already in flight (submitted to FYERS but not yet confirmed or rejected), duplicate submission must be prevented and the user shown a status message for the in-flight order.
- `REQ-ORDER-006` The execution flow for every action (Entry, Add, Reduce, Exit) must consist of two distinct phases. Phase 1 is platform-owned: a modal that surfaces all RME context, pre-flight checks, and warnings and allows the user to review and adjust parameters. Phase 2 is FYERS-owned: the FYERS API Connect JS widget opens as a pop-up and handles auth verification, exchange window checks, final order submission to FYERS, and success or error display. - `REQ-ORDER-007` The Phase 1 platform modal must display: action type (Entry / Add / Reduce / Exit), symbol name and trading symbol, proposed quantity, estimated fill value at the last available quoted price, the RME stop level for the position, and portfolio heat before and after the trade. This prevents the failure mode where the modal displayed one price at open but price moved materially before the user clicked confirm — the trader must see a current estimate at all times while the modal is open. For Exit actions the modal must additionally specify whether the exit is a full exit or partial exit. When an exit advisory is active, the proposed quantity must be pre-populated with the RME-recommended exit quantity, which may be a partial amount if the advisory is for a scale-out. When no exit advisory is active and the user initiates a discretionary exit, the proposed quantity must be pre-populated with the full open quantity. In both cases the user may adjust the quantity freely down to a minimum of one share, with estimated fill value and post-trade portfolio heat recalculating in real time. After a confirmed partial exit the position remains in Open state with its quantity, average buy price, and portfolio heat contribution recalculated. After a confirmed full exit the position transitions to Closed. Both cases are audited per REQ-ORDER-015a with the requested and filled quantities recorded. All labels and copy in the modal must follow the self-directed language rule in REQ-LEGAL-006, and the short-form disclaimer defined in REQ-LEGAL-007 must appear as a prominent strip above the confirm button.
- `REQ-ORDER-008` The proposed quantity in the Phase 1 modal must be derived from the RME-recommended size for the action. The user may adjust the quantity; estimated fill value and post-trade portfolio heat must recalculate in real time.
- `REQ-ORDER-009` The user must be able to select order type in the Phase 1 modal: market order or limit order. Limit order must default to the RME-suggested price for the action; the user may modify it with estimated fill value updating in real time.
- `REQ-ORDER-009b` The attribute values rendered onto the `<fyers-button>` element must originate from a single signed payload returned by the platform backend. On every Phase 1 recalculation (quantity change, order type change, price change) the frontend must request a fresh signed payload. The backend must validate every field before signing: the symbol must be in the active Nifty 500 universe and not scan-excluded; `data-product` must be `CNC` (REQ-ORDER-010); quantity must be a positive integer; price must be non-zero for LIMIT / SL orders; `data-transaction_type` must be `BUY` for Entry and Add actions and `SELL` only for Reduce and Exit against an existing long platform position or externally-opened holding; the user must not be hard-blocked per REQ-ORDER-002, REQ-ORDER-003, REQ-ORDER-004, REQ-ORDER-005. The payload must be signed with a short-lived HMAC key managed in Key Vault and must be bound to the user's session, the action type, and a single-use server-issued nonce. The backend must reject any intent-ledger write whose payload signature is invalid or whose nonce has been seen before. Any frontend mutation of the signed `data-*` values between signing and widget click invalidates the signature. **HMAC domain separation and key isolation (S-1):** Every HMAC input string must be prefixed with the literal domain-separation string `fyers.intent.v1:` before the HMAC digest is computed, so that the intent signing key can never be confused with — or exploited via — any other HMAC-signed artefact on the platform (cookies, CSRF tokens, webhook verification). The signing key must be a dedicated Azure Key Vault secret used solely for intent payload signing; it must not be shared with, derived from, or rotated in lockstep with any other key. The Key Vault secret name for the signing key must be recorded in `sys_config` under the non-secret reference key `orders.intent.hmac_key_name` (category `orders`, type `string`) so that operators can identify and rotate the correct secret without inspecting code. The key material itself must never appear in `sys_config`, source control, or logs. **Multi-intent portfolio heat gate at signing time (EC-5):** The signed-payload endpoint must include the count and aggregate portfolio heat impact of all currently `pending` `intent_ledger` records for the user in the signing decision. If the user has N pending intents for different symbols, and if adding the current proposed order to those N intents would together push portfolio heat above the configured maximum (`risk.default.max_portfolio_heat_pct`), the endpoint must refuse to sign with reason `pending_intents_would_breach_heat` and a message: "You have {N} orders submitted to FYERS awaiting confirmation. If all fill, adding this position would exceed your portfolio heat limit. Please wait for fill confirmation or cancel in-flight orders before proceeding." This closes the multi-tab gap where a user opens 10 modals for 10 different symbols, signs all 10 payloads before any LADS cycle processes fills, and ends up with a combined portfolio heat far exceeding their limit.

**LADS health gate at signing time (RME-R2):** The signed-payload endpoint must re-validate platform-wide LADS health before signing. Specifically, if a LADS-sustained-failure state is active at signing time (i.e., three or more consecutive LADS cycles have aborted per REQ-PORT-021a), the endpoint must refuse to sign with a structured error response carrying the reason `lads_sustained_failure_active` and the timestamp of the last successful LADS cycle. The Phase 1 modal must surface this as a non-blocking but prominent advisory: "Account data may be stale — the last portfolio sync encountered repeated failures. Position sizing may be based on outdated equity. Consider retrying after the sync recovers." The signing refusal is only in effect while the sustained-failure state is active; once LADS recovers and completes a successful cycle, signing is permitted again without requiring any user action. This prevents the failure mode where a user opens the modal before a LADS failure, the equity state becomes unreliable during the modal session, and the user submits a payload signed against stale portfolio state.
- `REQ-ORDER-009c` The signed-payload nonce issued by the backend per REQ-ORDER-009b is **strictly single-use and is not intended for idempotent re-submission of the same order.** Each Phase 1 recalculation (user changes quantity, order type, or price) issues a fresh nonce bound to the updated parameters; issuing the fresh nonce does not invalidate any previously issued nonce for a *different* recalculation — each signed payload is independent. The nonce becomes consumed the moment the corresponding `intent_ledger` write is accepted; any subsequent intent-write attempt carrying the same nonce must be rejected with a `nonce_already_used` error and the guard-state banner defined in REQ-ORDER-018b must be surfaced. The nonce is not a mechanism for deduplicating retries of a failed intent write; if an intent write fails (network error, server error), the user must return to the Phase 1 modal to obtain a fresh signed payload with a new nonce before attempting again. The `orders.payload_nonce_ttl_seconds` sys_config key (default 300 s) sets the expiry window after which an unused nonce is rejected even if it has never been presented; this prevents stale browser-tab re-submissions. **Tab-refocus stale-payload mitigation:** The Phase 1 modal frontend must implement a `visibilitychange` listener. When the browser tab transitions from hidden to visible while the modal is open, the frontend must request a fresh signed payload from the backend (identical to the refresh triggered by a user edit) and update the modal's estimated fill value and displayed parameters before the user can click confirm. This ensures a user who opens the modal, backgrounds the tab for several minutes, and then returns will see a current estimated value rather than a stale one — even though the nonce has not yet expired at the protocol level.

- `REQ-ORDER-014b` An `intent_ledger` document is **immutable on its order-parameter fields from the moment it is written.** The following fields must never be modified after the initial insert, by any code path — including the callback handler, LADS, the reconciliation safety net, admin tools, or migration scripts: `user_id`, `symbol`, `action_type`, `product_type`, `quantity_requested`, `order_type`, `limit_price`, `signed_payload_hash`, and `nonce`. The platform's internal trading calendar and all authoritative persisted timestamps remain in UTC internally and `Asia/Kolkata` for market-session logic; the timezone preference affects display only, never the underlying timestamps or calendar evaluation.
- `REQ-PROFILE-004` The user must be able to set a default chart timeframe used when a chart page is opened without an explicit timeframe. Valid values are the supported global timeframes defined in REQ-TIMEFRAME-001.
- `REQ-PROFILE-005` The user must be able to set a default risk-per-trade percentage, applied to new Signal Subscriptions created without an explicit override. The value must fall within the platform band defined by `position_sizing.default_risk_per_trade_pct` and `position_sizing.max_risk_per_trade_pct`. Values outside the band must be rejected at save time with a clear message showing the permitted range.
- `REQ-PROFILE-006` The user must be able to configure per-notification-type Telegram delivery preferences. For each user-facing notification type listed in REQ-NOTIFY-006, the user may toggle Telegram delivery on or off. A minimum non-suppressible set must always be delivered to Telegram regardless of preference, because suppressing them could cause the user to miss critical trading or safety information: stop breach alerts, exit alerts, gap risk alerts, circuit limit alerts, market halt active, market halt cleared, and pending entry superseded. Portal notification feed entries must be written for all types regardless of Telegram preference; preferences only govern Telegram dispatch.
- `REQ-PROFILE-007` The user must be able to configure Telegram quiet hours: a single start time and end time expressed in the user's configured timezone (REQ-PROFILE-003). During quiet hours, Telegram delivery of any notification type not in the non-suppressible set in REQ-PROFILE-006 must be held in the notification store and dispatched after the quiet window ends. Non-suppressible types must be delivered during quiet hours regardless. Multi-window quiet hours (for example, separate morning and evening windows) are out of scope for V1.
- `REQ-PROFILE-007a` The Notification Delivery Job (NDJ, REQ-NOTIFY-007) must implement separate dispatch logic for held and non-suppressible notifications to prevent a non-suppressible alert from being batched with held notifications and delayed to window-end. The dispatch rules are as follows: (a) **Non-suppressible types during quiet hours:** the NDJ must attempt delivery on its next poll cycle regardless of the quiet-hour window; it must not check the quiet-hour flag for these types. The non-suppressible set is defined in REQ-PROFILE-006. (b) **Suppressible types outside quiet hours:** delivered on the next NDJ poll cycle as normal. (c) **Suppressible types during quiet hours:** marked as `held` on the notification record; the NDJ skips them during each poll cycle until the quiet window end time is crossed, at which point all `held` records for the user are promoted to `pending` in a single batch operation and are dispatched on the following poll cycle. The quiet-window-end promotion must be triggered by the NDJ's own clock, not by the next incoming event; the NDJ must check for the window crossing once per poll cycle against the current time for each user who has an active quiet-hour window. (d) **Non-suppressible types that arrive during quiet hours and are then held alongside suppressible types in the `held` state:** this state is invalid. A notification record whose type is in the non-suppressible set must never be written with `held` status; it must always be written as `pending` so that the standard NDJ dispatch path handles it immediately. The quiet-hour check must be applied at the time the notification record is written (by the generating component) for suppressible types, and must be skipped entirely for non-suppressible types.
- `REQ-PROFILE-008` The settings page must expose the user's Telegram link management: the initial linking flow per REQ-NOTIFY-016, the current linked chat ID masked for display, and the unlink action per REQ-NOTIFY-018. The current link status (linked, not linked, or dirty per REQ-NOTIFY-019) must be visible, along with the timestamp of the last successful Telegram delivery.
- `REQ-PROFILE-009` The settings page must expose the user's linked OAuth identities per REQ-RECOVERY-001 and REQ-RECOVERY-002: the list of currently-linked identities with their providers and masked emails, which identity was used to sign in to the current session, the last successful sign-in time per identity, and actions to link or unlink identities within the two-identity limit.
- `REQ-PROFILE-010` The settings page must expose a "Download my data" action that initiates a DPDP access request per REQ-PRIVACY-004. The request enters the admin-portal ticket queue and the user receives a confirmation with an expected completion time consistent with the REQ-PRIVACY-004 SLA. Repeated requests within 24 hours must be coalesced to a single pending ticket.
- `REQ-PROFILE-011` The settings page must expose a "Request account deactivation" action that initiates a DPDP erasure request per REQ-PRIVACY-004. Deactivation is not immediate; it requires admin review through the grievance flow and respects the lawful retention carve-outs documented in the Privacy Notice. The action must display a clear summary of what erasure will and will not remove before the user submits the request.
- `REQ-PROFILE-012` Every change a user makes to their settings must be recorded with before and after values in a user-visible change log within the settings page itself, so the user can see their own change history without requiring admin assistance. The underlying events must also be recorded in `audit_events` for operational audit purposes.

## Part 8 — Admin Portal

*Admin capabilities are delivered through a privileged section of the same portal. All admin actions are audited.*

### Admin Operations

- `REQ-ADMIN-001` The admin portal must support pending-user approval workflows. During Phase A (REQ-LEGAL-001) the approval action must enforce the tester ceiling defined in REQ-LEGAL-003 — the approve control must be disabled and clearly labelled when the current count of non-deactivated approved users equals or exceeds the configured ceiling, and attempting to approve in that state must be rejected with a message naming the current count and ceiling. The admin must capture a short justification when approving a user during Phase A, which is recorded in `audit_events` alongside the approval event.
- `REQ-ADMIN-001a` The admin must be able to deactivate an already-approved user account. Deactivation must immediately invalidate all active portal sessions for that user and block them from accessing any protected platform features. The user's trade history, position records, and audit trail must be preserved intact; deactivation must not delete any data. If a deactivated user completes OAuth and attempts to access the platform, they must be shown a dedicated account-deactivated screen — consistent with the purpose-specific screen model in REQ-SESSION-013 — that clearly states their account has been deactivated and instructs them to contact their platform administrator. No protected portal content must be accessible from this screen. When a user account is deactivated, all their PendingEntry positions must be immediately transitioned to Suspended state with reason `account_deactivated`. Open positions must remain in Open state and continue to be monitored passively: the Live Market Data Scan must continue evaluating their stop, add, and reduce levels; the RME must continue updating trailing stop levels via the EOD stop update job; and stop breach alerts must continue to be written to the notifications collection. No Telegram notifications must be dispatched to a deactivated user, and no new entry signals or RME entry advisories must be generated for them. EOD account sync must not run for deactivated users. On reactivation per REQ-ADMIN-001b, Telegram delivery resumes, EOD account sync resumes, and the platform must trigger an immediate account sync to re-establish current broker state before the user can interact with their positions.
- `REQ-ADMIN-001b` The admin must be able to reactivate a previously deactivated user account, restoring their access to the platform. Reactivation must be recorded in the audit trail.
- `REQ-ADMIN-001c` **Data and token state on user deactivation (U-2).** When a user account is deactivated per REQ-ADMIN-001a, the following state transitions must occur atomically alongside the session invalidation and position suspension already required by that requirement: (a) **intent_ledger:** any record for the deactivated user in a non-terminal status (`pending` or `awaiting_confirmation`) must be immediately transitioned to the terminal status `expired_account_deactivated`, with `updated_at` set to the deactivation timestamp; no further LADS reconciliation, callback processing, or FYERS order-state polling may be applied to these records after the deactivation event; (b) **rme_incidents:** any open (non-resolved) `rme_incidents` record for the user that carries an operator-actionable incident type must be surfaced in the admin System Health widget (REQ-ADMIN-014) as a deactivation-flagged incident requiring attention; the admin must manually resolve or dismiss these incidents through the standard incident resolution flow; unresolved incidents do not block deactivation and do not prevent reactivation; (c) **fyers_tokens:** the user's `fyers_tokens` record must be marked `dirty` at deactivation time so that no automated sync or LADS cycle can attempt to use it while the account is inactive; on reactivation per REQ-ADMIN-001b, the FYERS token dirty state persists and the user must complete a fresh FYERS re-authentication before any FYERS-dependent feature is accessible. All three state transitions and any unresolved incident count must be captured in the deactivation `audit_events` record. Trade ledger records, closed and open position records (open positions continue passive monitoring per REQ-ADMIN-001a), notification history, Signal Subscriptions, `rme_events` audit log, and all other data are preserved intact.
- `REQ-ADMIN-002` The admin portal must support Nifty 500 CSV upload and synchronisation.
- `REQ-ADMIN-003` The admin portal must support internal trading-calendar management.
- `REQ-ADMIN-004` The admin portal must support job monitoring and explicit manual triggering or retry of key operational jobs.
- `REQ-ADMIN-005` All privileged actions must be attributable to a user or service identity.
- `REQ-ADMIN-006` The admin portal must support management of shared runtime system settings stored in `sys_config`, with audit trail.
- `REQ-ADMIN-007` The admin must be able to activate the global RME kill switch to suspend all Signal generation and recommendation output platform-wide, with the action recorded in the audit trail. On kill switch activation, all PendingEntry positions across all users must be immediately transitioned to Suspended state with reason `kill_switch_activated`. On kill switch deactivation, these suspended PendingEntry positions must not be automatically reinstated; they remain Suspended until superseded by a fresh EOD Signal Runner entry signal per REQ-PLC-009 or until they expire per REQ-PLC-008. The next eligible EOD Signal Runner run after deactivation is the natural recovery path for generating fresh advisories.
- `REQ-ADMIN-007a` The global kill switch (REQ-ADMIN-007) has a precisely scoped effect. The following are **halted** when the kill switch is active: EOD Signal Runner (EODSR) entry-signal emission — the EODSR must not emit new entry signals for any user in any EOD run while the switch is active; it must record the run as `skipped_kill_switch` in `job_runs`. The following **continue unaffected** regardless of kill switch state: Live Market Data Scan (LMDS) stop-level and add/reduce-level monitoring for all open positions; Live Account Data Scan (LADS) and all trade-ledger accounting; RME exit advisories, trailing stop updates, and all advisory processing for Open positions; per-user live quotes and real-time chart data (PLD); and the Notification Delivery Job dispatching any notification already in the queue. The admin portal must display the kill switch state prominently and must include a description visible to the admin operator of what the switch does and does not stop, so that the switch cannot be mistaken for a full-platform halt. The description must read at minimum: "The kill switch stops new entry-signal generation. Stop monitoring, exit advisories, live quotes, account sync, and existing notifications are unaffected." The kill switch state and the timestamp and actor of each state change must be surfaced on the System Health widget (REQ-ADMIN-014).
- `REQ-ADMIN-007b` The admin portal must provide a separate **Drain notification queue** action, distinct from the global kill switch, that allows the admin to suppress delivery of already-queued notifications. When this action is invoked: all notification records currently in `pending` status that have not yet been dispatched by the Notification Delivery Job must be transitioned to a `drained` terminal status, with an audit entry recording the actor, timestamp, and count of drained records; the Notification Delivery Job must skip `drained` records in all future processing cycles; and an `audit_events` record must be written. This action is a separate admin step — activating the kill switch does not implicitly drain the queue, and draining the queue does not deactivate the kill switch. Both the kill switch and the queue-drain action require admin step-up re-authentication per REQ-SEC-011 and must be recorded individually in `audit_events`.
- `REQ-ADMIN-008` The admin portal must display current RME-related `sys_config` values including drawdown thresholds, portfolio heat limits, and sizing defaults, and allow editing within permitted bounds.
- `REQ-ADMIN-009` The admin portal must include a read-only Data Management help page that lists every MongoDB collection, its retention mechanism (TTL, Online Archive, or permanent), the active window or expiry period, and a setup checklist for TTL indexes and Online Archive policies. Default values must match those defined in `docs/data-management.md`. This page exists to assist operators during database setup and periodic audits.
- `REQ-ADMIN-010` The admin must be able to suspend signal delivery for a specific user without deactivating their account. While signal-suspended, the user retains full read access to the platform — including charting, portfolio analytics, notification history, and Signal browsing — but the EOD Signal Runner must not generate new entry signals or RME advisories for that user and no new Telegram notifications must be dispatched to them. On suspension, all PendingEntry positions for that user must be immediately transitioned to Suspended state with reason `user_signal_suspended`. On re-enabling, suspended PendingEntry positions must not be automatically reinstated; they remain Suspended until superseded by a fresh EOD Signal Runner entry signal per REQ-PLC-009 or until they expire per REQ-PLC-008. The admin must be able to re-enable signals for the user at any time. Both actions must be recorded in the audit trail and must appear visibly in the user's record in the admin user management view.
- `REQ-ADMIN-011` The admin must be able to disable a specific Signal type platform-wide from the admin portal.
- `REQ-ADMIN-012` The admin portal must display a persistent badge indicator on the user management menu item showing the count of accounts currently pending approval. The badge must update in real time and clear automatically as approvals are processed. No Telegram notification is required for pending user registrations.
- `REQ-ADMIN-014` The admin portal must include a system health section providing a centralised, proactive view of all major platform components. The section must display a traffic-light status indicator (healthy, warning, or critical) for each component, derived from configurable staleness thresholds and error rate thresholds seeded in `sys_config`. For each component the section must show the current state and a 7-day daily breakdown of outcomes, warning counts, and error counts so the admin can identify when a degradation began. The lookback window must be configurable via `sys_config` key `operations.system_health.lookback_days` with a default of 7. Components that must be represented are: (a) each background job (DataSync (DS), HistoricDataSeed (HDS), EOD Signal Runner (EODSR), Live Market Data Scan (LMDS), Live Account Data Scan (LADS), Notification Delivery Job (NDJ)) — showing last run timestamp, last outcome, and per-day run count, success count, warning count, and error count sourced from `job_runs`; (b) admin FYERS token — current state (valid, dirty, or missing), expiry timestamp, and 7-day history of token validity events sourced from `audit_events`; (c) market data provider — active provider, last successful data fetch timestamp, current API call consumption versus daily limit, and 7-day history of provider fetch outcomes sourced from `job_runs`; (d) Telegram delivery pipeline — last successful delivery timestamp and 7-day daily breakdown of delivery attempts, successes, and failures sourced from `notifications`; (e) global kill switch — current active or inactive status and the timestamp and actor of the last state change sourced from `audit_events`; (f) market halt state — current halted or clear status per REQ-HALT-001/REQ-HALT-002, whether the current state is auto-detected or admin-overridden, the start timestamp of any active halt, and a 7-day history of halt events sourced from `audit_events`. Clicking any component row must navigate to the relevant filtered detail view or job log. All data for the health section is sourced from existing collections; no new persistence layer is required.

- `REQ-ADMIN-013` A disabled Signal type must not be evaluated by the EOD Signal Runner for any user regardless of their subscription state. Individual user Signal Subscriptions to the disabled Signal type must be preserved so they resume automatically when the Signal type is re-enabled. The disabled state must be clearly indicated in the Signal management view for both admin and users. Disabling and re-enabling a Signal type must be recorded in the audit trail. When a Signal type is disabled, all PendingEntry positions across all users that were generated under that Signal type must be immediately transitioned to Suspended state with reason `signal_type_disabled`. On re-enable, these suspended PendingEntry positions must not be automatically reinstated; they remain Suspended until superseded by a fresh EOD Signal Runner entry signal per REQ-PLC-009 or until they expire per REQ-PLC-008. The next eligible EOD Signal Runner run after re-enable is the natural recovery path for generating fresh advisories.
- `REQ-ADMIN-015` The admin portal must provide a "View as user" read-only impersonation mode. From the admin user management view the admin may select a target user and invoke "View as." The impersonation session must render the portal exactly as the target user would see it — dashboard, watchlist, chart pages, Signal Subscriptions, notification feed, settings — with no action controls active. All forms must be disabled, all state-changing controls must be visibly marked read-only (including Telegram linking, manual sync, CSV upload, the Phase 1 order modal, manual adjustment flows, and backtest launch), and any API write originating from an impersonation session must be rejected server-side even if a client-side control is bypassed. The session must display a persistent high-visibility banner at the top of every page reading "Viewing as [user display name]. Read-only." Entry into and exit from an impersonation session must be gated by admin step-up re-authentication per REQ-SEC-011, and must be recorded in `audit_events` with admin identity, target user identity, entry time, exit time, and the pages visited during the session. Impersonation sessions must auto-expire after a configurable idle timeout, seeded in `sys_config` under the key `operations.impersonation.idle_timeout_minutes` with a default of 15 minutes.

- `REQ-ADMIN-016` The admin portal's position management view must display suspended positions with their `source` value (per REQ-PLC-005a) and must offer only the resolution action appropriate for each source. A single generic "Resume Position" or "Release Suspension" action that applies uniformly to all suspended positions regardless of source is not permitted; the source determines both the UI label and the permitted action set. The required source-to-action mapping is as follows. (a) `LMDS`-sourced suspension — the admin view must display "Self-monitoring — may auto-resolve" together with the triggering event description (circuit limit or gap) and the last-known price; no manual release action is offered in the default flow because auto-resolution occurs per REQ-PLC-004 when the circuit condition clears; an admin may force-release only after step-up re-authentication per REQ-SEC-011, in which case the override must write an `audit_events` record with the admin identity, timestamp, and the explicit override reason. (b) `RME_OCC`-sourced suspension — the admin view must display "OCC retry exhaustion — incident resolution required" with a link to the associated `rme_incidents` record; a "Release position" action becomes available only after the linked incident record has been marked resolved by an admin; attempting to release without the incident marked resolved must be blocked with an explanatory message. (c) `CORPORATE_ACTION`-sourced suspension — the admin view must display "Corporate action detected — re-anchor required" and must offer only the "Re-anchor and release" action governed by REQ-PLC-010; no direct state-flip release is available for this source; the re-anchor action requires step-up re-authentication per REQ-SEC-011. (d) `ADMIN`-sourced suspension — the admin view must display "Manually suspended" and must offer a "Release suspension" action; this action requires step-up re-authentication per REQ-SEC-011 and must write an `audit_events` record with the admin identity, timestamp, and release reason. This requirement closes the gap where admin-forced suspension and RME-forced suspension share the same `Suspended` state (REQ-PLC-005a) but previously had no distinct portal enforcement of their separate resolution paths, meaning an operator could inadvertently clear a safety-triggered suspension using the same action intended for a manual hold.

## Part 9 — Future and Out of Scope

*Requirements here are intentionally deferred. Do not implement them until this section is updated and moved to the appropriate part above.*

### V1.5 and Later

- `REQ-NEXT-001` Corporate actions support for splits, bonuses, dividends, and symbol continuity belongs to the next phase.
- `REQ-NEXT-002` Corporate-action-adjusted analytics are out of scope for the early simplified phase.
- `REQ-NEXT-003` Multi-account, team, advanced signal-routing, richer charting, and other expanded capabilities belong after the core platform is stable.
- `REQ-NEXT-004` Paper trading mode (simulated live execution using real market data without actual orders) is a future capability to be added after the core RME and live signal workflows are stable.
- `REQ-NEXT-005` Market regime detection and regime-based RME parameter switching are future enhancements once the core RME is operational.
- `REQ-NEXT-006` Statistical cross-position correlation exposure modelling (beyond sector classification) is a future enhancement. For V1, sector concentration limits and sector exposure relative to existing positions serve as the primary correlation control, as required by REQ-RME-017.
- `REQ-NEXT-007` Advanced sizing models including Kelly Fraction, Equal Risk Contribution, and Rebalancing-based sizing are future additions once the foundational sizing models are validated through backtesting.
- `REQ-NEXT-008` Step-up re-authentication for sensitive *regular-user* portal actions such as manual trade-ledger adjustments and RME profile changes on live positions is deferred to a future version. Admin step-up re-authentication for destructive admin actions is not deferred — it is covered by REQ-SEC-011 and applies from Phase A onward.
- `REQ-NEXT-009` Point-in-time universe tracking: storing historical Nifty 500 membership derived from each admin CSV upload so that backtests can use the universe that was active at each historical date, eliminating survivorship bias. This is a future enhancement once the core backtest engine is stable.
- `REQ-NEXT-010` A dedicated read-only compliance or support reviewer role with access to audit events, job outcomes, signal history, and reconciliation views across all users is a future addition. For V1, the admin is the only privileged role and handles any compliance or audit access needs directly.
- `REQ-NEXT-011` If the REQ-ORDER-010b verification forces the platform onto the REQ-ORDER-010a advisory-only fallback, a post-V1 phase must investigate alternative non-REST, non-branded-button execution paths to restore platform-native execution assistance without relaxing REQ-ORDER-006 or REQ-ORDER-010. The primary candidate for investigation is a FYERS-hosted deep-link order ticket pre-filled with symbol, side, quantity, order type, price, and CNC product type, where final submission happens entirely inside FYERS's own UI. Feasibility is currently unverified and depends on FYERS offering such a surface; the investigation must confirm deep-link availability, attribute coverage, product-type selection semantics, and any callback or reconciliation surface before any implementation is scheduled.

### Explicitly Out of Scope for Early Milestones

- `REQ-OOS-001` Options, futures, and other derivatives.
- `REQ-OOS-002` Instruments outside the Nifty 500 listed on NSE.
- `REQ-OOS-003` Short selling or short-side strategy support.
- `REQ-OOS-004` Tax reporting.
- `REQ-OOS-005` Mobile-native apps.
- `REQ-OOS-006` Public leaderboards ranking users, Signal types, or symbols by performance.
- `REQ-OOS-007` Platform-curated "top picks," "stocks to watch," or similar lists generated by the platform rather than surfaced from each user's own Signal Subscriptions. This guardrail protects the user-self-directed framing required by REQ-LEGAL-006.
- `REQ-OOS-008` Copy-trading, mirror-trading, or auto-replication of one user's Signal Subscriptions, positions, or trades to any other user.
- `REQ-OOS-009` Platform-operated model portfolios, advisory portfolios, or portfolio recommendations presented to users.
- `REQ-OOS-010` Tip-based content, analyst commentary, chat rooms, discussion boards, or any surface where one user's opinion on a security is visible to another user. This preserves the boundary that the platform emits information derived from each user's own configured scans, not third-party views.
- `REQ-OOS-011` **OAuth provider outage — known single-point-of-failure (S-4).** The platform relies on three OAuth identity providers (Google, Microsoft, Facebook/Meta) for all portal authentication. An outage of all three simultaneously would prevent any user — including the admin — from logging in to the portal. No fallback authentication mechanism (local accounts, backup credentials, emergency access tokens) is in scope for Phase A or Phase B. This is an accepted risk for a private-validation and pre-commercial platform where the user base is small and the admin has direct database and infrastructure access via Azure. For Phase C (commercial SaaS), a fallback authentication path — such as an admin-only emergency local-account login gated by the same MFA requirement as REQ-BCP-009 — should be evaluated and scheduled as a separate engineering workstream before Phase C entry, but is not a gating condition for that phase under the current requirements. This limitation must be disclosed in the admin portal runbook as an explicitly accepted operational risk.
