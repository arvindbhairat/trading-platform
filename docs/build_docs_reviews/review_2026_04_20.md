# SignalStack Build-Documentation Review — 2026-04-20

Reviewer perspectives applied simultaneously: senior technical reviewer, software/solution architect, application security reviewer, professional discretionary/systematic trader. Compliance, SEBI, DPDP, KYC, and tax concerns are out of scope per `docs/build_docs_reviews/prompt.md`. Findings are prioritised by whether they materially reduce the risk of incorrect trading decisions, data loss, security compromise, or unbuildability. Over-engineering is called out explicitly where the existing spec carries more complexity than the phased rollout justifies.

All citations are to file and requirement ID / section heading in the repository snapshot dated 2026-04-20.

---

## 1. Executive Summary

The SignalStack build documentation is, on the whole, unusually disciplined for a pre-build project. The canonical-doc/ADR/requirements-ID pattern is respected, terminology is genuinely canonical, and the hard invariants that usually break retail trading platforms — per-position event serialisation, per-user trade-ledger locking, execution via a branded-button widget rather than backend REST, single-instance Worker Service — are all named, reasoned, and pinned to REQ IDs or ADRs. The phased rollout (Phase A private validation → Phase B pre-commercial → Phase C commercial SaaS) is credibly sequenced in `docs/implementation-roadmap.md`, and the boundary requirements (REQ-BOUNDARY-001..004) do a good job of suppressing speculative features.

That said, there are a small number of genuinely critical gaps — none of them compliance-related — that will cost real money, real user trust, or real engineering weeks if they are allowed to reach Phase B. The three most important are:

1. **The intent-ledger / FYERS-callback reconciliation contract is under-specified for realistic failure modes** (`docs/requirements-spec.md` REQ-ORDER-012..015f, `docs/system-architecture.md` "FYERS API Connect Branded Button Contract"). The current spec says callbacks confirm submission not fill, and that fills must come via LADS, but the handling of "user closed the pop-up", "widget succeeded, callback lost", "LADS fill arrives before callback", and "user opens a second modal for the same symbol" is not pinned. This is the single most likely source of ghost positions and double-entries in production.

2. **The per-position `_version` OCC model in ADR-0003 is sound, but the reader-side contract is still ambiguous in a few places** — notably the precedence between `ledger_snapshot_version` cache invalidation (REQ-PORT-031a / REQ-RME-006d / REQ-DASH-010) and the RME's own OCC retry loop when a position is being simultaneously updated by LMDS and LADS at the same tick. A stricter ordering rule is needed or the 3-retry ceiling in REQ-RME-CONC-005 will be hit legitimately under normal EOD load with pyramiding users.

3. **The CNC product-type verification gate (REQ-ORDER-010b) with the advisory-only fallback (REQ-ORDER-010a) creates a bright-line behaviour change across the platform that is not covered by a kill-switch, a dashboard banner, or a Telegram operator alert.** If the sandbox probe fails silently — or returns a false negative — every user on the platform is silently moved to advisory-only execution with no surfaced explanation. Traders will assume the platform is broken. This is the classic "fallback is worse than outage" pattern.

Beyond those three, the review identifies a handful of architectural rough edges (Worker Service scale-out enforcement, LKG cache staleness surfacing, MDP-abstraction gaps around intraday WebSocket realities), a set of security concerns (HMAC nonce domain separation, admin step-up scope, Telegram channel integrity), and a meaningful cluster of trader-experience gaps (pyramiding stop-update semantics, partial-fill representation, XIRR inputs during suspension).

There are also two notable **over-engineering risks**: the three-layer Worker singleton enforcement is appropriate for Phase B+ but is being asked to hold in Phase A on a single-developer team, and the reconciliation machinery in REQ-RECON-001..008 is shaped for a bigger platform than the Nifty 500 long-only universe warrants on day one.

The spec is buildable. None of the findings below are blocking at a document level — they are items that should be resolved before code is committed to the corresponding Phase, not items that should stop the Phase 0 work that is already queued.

## 2. Critical Gaps

The following are gaps whose absence will, with high confidence, produce either incorrect trading outcomes, data loss, or unbuildable code. Everything else in this review is ranked below these.

**CG-1. Execution-assistance failure-mode matrix is missing.** REQ-ORDER-012..015f and the Branded Button Contract in `docs/system-architecture.md` describe the happy path and the LADS-gated fill path, but the document set does not enumerate the Cartesian product of `{modal opened, modal cancelled, modal submitted}` × `{callback received OK, callback received error, callback lost}` × `{LADS fill received, LADS fill never arrives, LADS fill arrives first}`. Without an explicit matrix, three implementers will write three different reconciliation behaviours. *Smallest change*: add a table to `docs/requirements-spec.md` Part 7 under REQ-ORDER-015 listing each of the 9+ cells and the expected state of `intent_ledger` / `positions` / Telegram notification for each. A one-page table is enough; no new code paths are needed.

> **✅ RESOLVED 2026-04-20.** Added `REQ-ORDER-015g` to `docs/requirements-spec.md` immediately after REQ-ORDER-015f. The requirement contains a 9-cell matrix covering every combination of widget outcome (cancelled, error, success), callback fate (received OK, error, lost), and LADS fill fate (fill arrives, fill arrives first, fill never arrives). Each cell specifies the final `intent_ledger` status, the `positions` state change, and the user notification. Five cross-cell invariants are pinned (submission-vs-fill distinction, Telegram LADS-gating, orphan advisory, idempotency of callback/fill ordering). All nine cells plus invariants are required to be covered by Phase 7 contract tests.

**CG-2. CNC-verification fallback has no user-visible signal.** REQ-ORDER-010b requires a sandbox CNC probe at Phase 1; REQ-ORDER-010a is the advisory-only fallback. There is no requirement that users must see *which mode they are in*, no admin alert when the system downgrades, and no cooldown on re-probing. *Smallest change*: add REQ-ORDER-010c — "When advisory-only fallback is active, the portal must display a persistent banner on Dashboard and Position Detail; `notifications.admin.execution_mode_degraded` must fire on entering and leaving the fallback state; the sandbox probe must retry on a bounded schedule recorded in `sys_config.orders.cnc_probe_schedule`".

> **✅ RESOLVED 2026-04-20.** Added `REQ-ORDER-010c` to `docs/requirements-spec.md` immediately after REQ-ORDER-010b. The requirement specifies: (a) a persistent non-dismissible user banner on Dashboard and all Position Detail / chart pages when advisory-only fallback is active; (b) a `notifications.admin.execution_mode_degraded` admin notification delivered via both Telegram and email on every mode transition (entering and leaving fallback); (c) a `sys_config.orders.cnc_probe_schedule` key (default `never` — manual re-probe only, overridable to a cron expression) and a manual re-probe action in the admin portal; (d) persistence of the current mode and transition timestamp in non-editable `sys_config` status keys so mode survives restarts. Three new `sys_config` seed rows added to `docs/system-config.md`: `orders.cnc_probe_schedule`, `orders.execution_assistance_mode`, `orders.execution_assistance_mode_updated_at`.

**CG-3. Reader-side ordering between `ledger_snapshot_version` and RME OCC is under-specified.** REQ-PORT-031a says readers must observe a consistent snapshot by keying caches on `ledger_snapshot_version`; REQ-RME-CONC-005 says the RME retries 3× on OCC conflict and then freezes the position. These interact: if the RME retry loop is still running when a reader samples `ledger_snapshot_version`, the reader may see a version that is about to be rolled back by a freeze. *Smallest change*: pin that `ledger_snapshot_version` is incremented only after the RME write is durably persisted (not at the start of the OCC attempt), and forbid readers from incrementing it. Add this as an invariant note under REQ-PORT-031a.

> **✅ RESOLVED 2026-04-20.** Added a three-part invariant block to the end of `REQ-PORT-031a` in `docs/requirements-spec.md`. The invariants pin: (i) `ledger_snapshot_version` is incremented only *after* all covered writes have durably committed — never at the start of a write attempt or mid-OCC-retry; (ii) the field gates trade-ledger consistency only, not RME position fields; readers needing both must independently check the position's `_version` OCC field alongside the `ledger_snapshot_version` check; (iii) during an OCC retry loop, the full snapshot-consistent read protocol (REQ-RME-006d) must be re-executed from the user document at the start of each retry, not just the position re-read.

**CG-4. Partial fills are not a first-class concept.** The Branded Button widget returns a single callback and LADS emits fill events, but REQ-PLC-00x treats `Open` as a binary state. Real NSE CNC orders can fill partially across the session. If a 100-share intent fills 60 + 40 across two fills, the current spec implicitly assumes the second fill simply updates the same position. If it doesn't (e.g., separate `orderId`s from FYERS), a second position will be created and the partial unique index on `{user_id, symbol}` over non-terminal states (REQ-PLC-007a) will reject the second. *Smallest change*: make the partial-fill assumption explicit. Either (a) require LADS to coalesce multi-fill orderIds to one `intent_id` and update the same position, or (b) allow multiple `Open` positions per user+symbol when originated from the same `intent_id`. Pick one; document it.

> **✅ RESOLVED 2026-04-20.** Chose option (a): LADS coalesces multi-fill events for the same FYERS `order_id` into updates on the same position document. Added a "Partial-fill coalescing rule" paragraph to the end of `REQ-PLC-007a` in `docs/requirements-spec.md`. The rule states: one `order_id` maps to exactly one `intent_ledger` record and therefore to exactly one `positions` document; subsequent fills for the same `order_id` must be applied as quantity-and-price updates on the existing `Open` position, never as new position creation events. A two-fill contract test is required to verify combined quantity and weighted average price.

**CG-5. Telegram bot-token compromise has no defined response.** Telegram is a listed notification channel (REQ-NOTIFY-00x) but the notification ADR / requirements do not say what happens if the bot token is exfiltrated or the Telegram channel is hijacked. Given this is the primary out-of-band notification for trader-facing exits/stops, a silent hijack is a meaningful risk vector. *Smallest change*: require token rotation on a defined cadence in `sys_config.notifications.telegram.rotation_days`, and require an admin break-glass that disables Telegram delivery globally via a single sys_config flag. No new channel needed; this is a documented procedure.

> **✅ RESOLVED 2026-04-20.** Added `REQ-NOTIFY-022a` to `docs/requirements-spec.md` immediately after REQ-NOTIFY-022. The requirement defines three controls: (a) token rotation cadence — `sys_config.notifications.telegram.rotation_days` (default 90 days) with a `telegram_token_rotation_due` dual-channel (Telegram + email) admin notification and 7-day remind-again window; (b) global Telegram disable break-glass — `sys_config.notifications.telegram.global_disable` (default `false`) that halts all Telegram dispatch for all users, requires step-up re-auth to toggle, fires an email-only admin notification on change, and shows a persistent admin banner; (c) token replacement disable-and-re-enable cycle — the replacement flow (REQ-NOTIFY-015) automatically sets `global_disable = true` during validation and `false` on success, ensuring no delivery against a stale token. Two new `sys_config` seed rows added to `docs/system-config.md`: `notifications.telegram.rotation_days` and `notifications.telegram.global_disable`.

## 3. RME Findings

### 3.1 Event Serialisation and OCC

ADR-0003 is substantively the correct design: Option A (OCC via `_version`) for correctness and Option C (per-position `Channel<RmeEvent>`) for latency. The ADR is genuinely one of the stronger documents in the set. Two sub-gaps:

- The ADR shows the producer list (LMDS, LADS, EODSR, EOD stop update, Portfolio heat recalc, Admin) but does not rank event *priority* on ingestion to the Channel. Under a gap-open scenario, LMDS ticks, LADS fills, and the EOD stop-update job can queue simultaneously for the same position. A LIFO channel would process the stop-update first (risk-safe); a FIFO would process the LMDS tick first (stale). REQ-RME-CONC-003 says FIFO; this is correct only if stop-update events are *not* routed through the Channel but applied synchronously to the position snapshot the RME is about to read. Document this carve-out explicitly in ADR-0003.
- The 3-retry OCC ceiling in REQ-RME-CONC-005 is reasonable for single-writer contention but is low for a pyramiding user with 3–5 open events on the same symbol during a fast tick. A hard ceiling that causes a "freeze with visibility" (REQ-RME-CONC-007) under *legitimate* contention will scare traders. Either raise to 8 and add jitter, or add a `retry_reason` dimension on the `rme_incidents` emission so operators can distinguish "real conflict" from "retry exhaustion under normal load".

> **✅ RESOLVED 2026-04-20.** Two changes made to `docs/adr/0003-rme-per-position-event-serialisation.md`: (1) Added an **EOD Stop-Update Event Carve-Out** section under Layer 1 documenting that `TrailingStopUpdateEvent` must NOT be routed through the per-position Channel — the EOD stop-update job applies its recalculation synchronously before LMDS/LADS pollers start for the new session, relying on OCC as the write guard. The channel consumer must reject any `TrailingStopUpdateEvent` arriving on the channel and log it as an error. (2) Added an **OCC retry ceiling and retry_reason observability** note under Layer 2: every `rme_incidents` record written on OCC exhaustion must include a `retry_reason` field with values `concurrent_writer_conflict` (genuine concurrent writer) vs `normal_load_exhaustion` (rapid sequential writes under pyramiding load). The admin System Health widget must surface incidents by `retry_reason`.

### 3.2 Sizing Models

`docs/portfolio-risk-guidelines.md` requires Fixed %, ATR, Heat-based, and Drawdown-adjusted sizing. The spec is clear on inputs, outputs, and the 1R definition, and the drawdown table (5/10/15/20/25/30%) is sensible. One gap: there is no requirement on *which* sizing model is the default on first user onboarding, and there is no guardrail against a user choosing Heat-based before they have any positions (where the formula divides by portfolio equity that may not yet be populated from UAD). *Smallest change*: name Fixed % as the default in REQ-RME-SIZE-00x and require a positive-equity precondition on Heat-based.

> **✅ RESOLVED 2026-04-20.** Added `REQ-SIZING-005a` to `docs/requirements-spec.md` immediately after REQ-SIZING-005. The requirement specifies that Portfolio Heat-Based Sizing requires a positive, non-zero platform-visible equity base; if equity is zero or the `equity_curve` collection has no completed-session records, the RME falls back to Fixed Percentage Risk Per Trade with a non-blocking advisory to the user. The fallback is recorded in the sizing audit output. Default sizing model (Fixed %) was already pinned in REQ-SIZING-005.

### 3.3 Stop Models

Fixed, ATR, Trailing %, Trailing ATR, Swing Low, Break-Even, and Time stops are all specified. The Trailing ATR stop is specified as "ratchet only, never widens", which is correct. Two sub-gaps:

- Swing-Low stop requires a lookback; `docs/portfolio-risk-guidelines.md` does not pin the default lookback in bars or the tie-breaker on equal lows. *Smallest change*: default to 20 bars on the user's chart timeframe; on ties, take the most recent.
- Time stop semantics at a holiday/half-day are undefined. *Smallest change*: declare that the Timeframe and Calendar Layer is authoritative and that time stops count trading bars, not calendar days. One sentence in `docs/requirements-spec.md`.

> **✅ RESOLVED 2026-04-20.** Expanded `REQ-STOP-003` in `docs/requirements-spec.md` with two inline addenda: (1) **Swing Low Stop default lookback** — default is 20 bars on the Signal Subscription's configured chart timeframe, seeded in `sys_config` under `risk.swing_low_stop.default_lookback_bars`; ties resolved by most recent swing low. (2) **Time Stop session-counting semantics** — session count is measured in NSE trading sessions per the internal trading calendar; partial/Muhurat half-day sessions count as full trading sessions for Time Stop purposes.

### 3.4 Drawdown and Heat Gates

The drawdown table is advisory per REQ-BOUNDARY-004, which is defensible for a Phase A audience. The portfolio-heat formula is clear. However, there is no spec for *how heat is computed while a position is `Suspended`* (see §8). If a Suspended position's risk is still counted, a user cannot free up heat without closing. If it is not counted, a stuck Suspension silently raises the user's risk budget. *Smallest change*: declare Suspended positions *do* contribute to heat, and surface Suspension prominently in the dashboard so traders know to resolve it.

> **✅ RESOLVED 2026-04-20.** Added `REQ-HEAT-008` to `docs/requirements-spec.md` immediately after REQ-HEAT-007. The requirement declares that Suspended positions continue to contribute to portfolio heat at their last-known risk amount until they reach Closed or Rejected. Suspension visibility is mandated on three surfaces: (a) Portfolio Dashboard — count of suspended positions and aggregate heat contribution as a distinct heat breakdown line; (b) Positions Summary page — status badge on each suspended row; (c) Position Detail page — banner explaining the position is suspended and still consuming risk budget.

### 3.5 Pyramiding

Pyramiding is addressed in `docs/portfolio-risk-guidelines.md`. The document is clear on when pyramiding is allowed but silent on how *stop updates* propagate across existing pyramid tranches when a new tranche is added. The most common professional convention is that a new tranche raises the combined stop to the highest individual stop among all tranches (never lowers). The spec is silent; two implementers will disagree. *Smallest change*: add a one-line rule in `docs/portfolio-risk-guidelines.md` under Pyramiding: "A new tranche never lowers the effective stop of the combined position."

> **✅ RESOLVED 2026-04-20.** Added `REQ-PYR-011` to `docs/requirements-spec.md` immediately after REQ-PYR-010 and a **Stop Propagation Across Pyramid Tranches** section to `docs/portfolio-risk-guidelines.md` under Pyramiding. The invariant: the new effective combined stop must never be set below the highest individual tranche stop in effect immediately before the add; if the combined-stop formula produces a lower value, the prior highest stop is used as the floor. REQ-PYR-011 requires a unit test asserting this invariant.

### 3.6 Lifecycle and Exit Priority

The `PendingEntry → Open → Suspended → Closed/Rejected` lifecycle with advisory flags is good. Exit priority 1–8 in `docs/portfolio-risk-guidelines.md` is clear. One gap: the transition from Open → Suspended is not pinned to a producer. Is it LADS (account-data drift), admin, the RME on repeated OCC failure (REQ-RME-CONC-007), or a reconciliation discrepancy? All four are plausible. *Smallest change*: list the exhaustive set of producers that can transition a position to Suspended and require that every such transition writes an explanation to `rme_incidents` with a `source` field.

> **✅ RESOLVED 2026-04-20.** Added `REQ-PLC-005a` to `docs/requirements-spec.md` immediately after REQ-PLC-005. The requirement lists the four authorised `source` values (`LMDS`, `RME_OCC`, `CORPORATE_ACTION`, `ADMIN`) with triggering conditions, and mandates that every transition atomically writes an `rme_incidents` record with `source`, `reason`, a position state snapshot, and a timestamp. The `ADMIN` path additionally requires an `audit_events` record with the admin user ID. The requirement notes that `ADMIN` and `RME_OCC` suspensions have distinct resolution paths from `LMDS` and `CORPORATE_ACTION` suspensions.

### 3.7 RME Full Specification Gaps

The following gaps were identified by cross-referencing `docs/build_docs_reviews/RME_full_spec.md` against the existing build documents. Several areas specified in the full spec were absent or underspecified in `docs/requirements-spec.md`.

**Dynamic Trigger Recalibration (RME_full_spec §2–3, §9):** Every trigger execution must recalculate ALL active price levels — not just stop and average price.

> **✅ RESOLVED 2026-04-20.** Added a new **Dynamic Trigger Recalibration** section with `REQ-RME-022` to `docs/requirements-spec.md` immediately before the Position Lifecycle section. The requirement pins that after any trigger execution (stop-loss exit, trailing stop update, add-on fill, reduce fill, or break-even activation) the RME must recompute all of: (a) active stop loss level; (b) trailing stop level; (c) all remaining add levels and quantities; (d) all remaining reduce levels and quantities; (e) exit trigger levels. Recalibration must complete before the next event is processed. Partial recalibration is declared a contract violation. Both live and backtest modes must use the same recalibration logic.

**Composite Scoring Formula (RME_full_spec §4):** Optimisation ranking used only expectancy in R; full spec specifies a multi-component weighted composite score.

> **✅ RESOLVED 2026-04-20.** Added `REQ-RME-020a` to `docs/requirements-spec.md` immediately after REQ-RME-021. The requirement defines the full weighted Composite Score formula (Normalised CAGR 0.20, Sharpe 0.15, Expectancy 0.15, Profit Factor 0.10, Stability Score 0.10, Regime Consistency 0.10, Capital Efficiency 0.10, Trade Quality 0.10, minus Drawdown Penalty 0.10) with component definitions. Configurations below `sys_config.rme.optimisation.min_trades_for_valid_result` (default 10) are marked low-confidence and excluded from top-ranked suggestions.

**Robustness Factor (RME_full_spec §4.3, §5, §6):** No robustness adjustment existed; full spec requires Parameter Sensitivity, Cross-Symbol Consistency, and Walk-Forward Stability multiplier.

> **✅ RESOLVED 2026-04-20.** Added `REQ-RME-020b` to `docs/requirements-spec.md` immediately after REQ-RME-020a. The requirement defines the Robustness Factor as the product of three normalised sub-scores: Parameter Sensitivity Score (`1 − variance of scores across neighbouring grid configurations`), Cross-Symbol Consistency Score (inverse CV of Expectancy in R across symbols in the same run), and Walk-Forward Stability Score (correlation of in-sample vs out-of-sample Composite Score across `sys_config.rme.optimisation.walk_forward_folds` folds, default 4). The Robustness Factor is stored per configuration and displayed alongside the Composite Score.

**Multi-Timeframe Evaluation (RME_full_spec §7):** Optimisation grid did not include timeframe as a dimension; full spec requires Daily, Weekly, Monthly, Rolling N-day, and combination evaluations.

> **✅ RESOLVED 2026-04-20.** Added `REQ-RME-020c` to `docs/requirements-spec.md` immediately after REQ-RME-020b. The requirement mandates evaluation across Daily, Weekly, Monthly, Rolling {3,5,7,10,15}-day timeframes, plus two multi-timeframe combinations (Weekly trend + Daily execution; Rolling 5-day + Daily). Timeframe is added as a dimension to the developer-defined optimisation grid. The results screen must support filtering and sorting by timeframe.

## 4. Architectural Findings

**A-1. Three-layer Worker singleton enforcement is the right target but is front-loaded.** The IaC `workerCount=1` + Azure DevOps pipeline gate + Redis `rme:worker:singleton` lease design is correct and will matter in Phase C. For Phase A, the Redis lease alone is enough. Front-loading all three layers is reasonable only if the IaC and pipeline gate are authored once and left untouched until Phase C — treat them as one-time work, not as an ongoing engineering burden.

> **✅ RESOLVED 2026-04-20.** Updated Phase 0 in `docs/implementation-roadmap.md` to state explicitly that all three enforcement layers are authored once in Phase 0 and treated as frozen scaffolding — not to be revisited or "improved" until the Phase C multi-instance partitioning extension in ADR-0003 is formally adopted in a new ADR. The IaC and pipeline gate are not active engineering concerns between Phase 0 and Phase C.

**A-2. MDP abstraction assumes REST-only on the server side, with WebSockets only in the browser.** This is enforced in CLAUDE.md and REQ-MARKET-002 variants. It is a good constraint for FYERS. It will become awkward for TrueData / GDF where the *intended* production pattern is a server-side WebSocket. Document this now, in `docs/adr/` as an ADR draft: "MDP migration will re-open server-side WebSocket as an option and REQ-MARKET-002 will be superseded." Without that, the migration will feel like a spec violation when it arrives.

> **✅ RESOLVED 2026-04-20.** Created `docs/adr/0005-mdp-server-side-websocket-migration-path.md` as a Draft ADR. The ADR records that REQ-MARKET-002a/b is a FYERS-era implementation constraint, not a permanent platform principle; that a commercial provider migration will supersede it with new requirements (REQ-MARKET-002d/e) permitting server-side WebSocket if fully encapsulated in the adapter; that the FYERS adapter remains REST-only; and that a dedicated migration ADR is required before any server-side WebSocket adapter is built. Key design notes on Phase C interaction (WebSocket subscription scope must align with per-instance position partition) are included.

**A-3. Azure App Config LKG cache (ADR-0002) is a good design; its failure surfacing is thin.** `config.source.last_reached_seconds` is exposed as a metric, but there is no requirement that this metric breaches a threshold into an operator alert. If App Config is unreachable for 20 hours but the LKG is still within the 24h ceiling, nothing alerts. *Smallest change*: add a threshold (e.g., 6h) above which a dashboard banner and an admin Telegram notification fire.

> **✅ RESOLVED 2026-04-20.** Added a **LKG staleness alert threshold** section to `docs/adr/0002-observability-and-configuration.md` requiring: (a) `config.last_known_good.staleness_alert_threshold_seconds` sys_config key (default 21600 — 6 hours); (b) when `config.source.last_reached_seconds` exceeds this threshold, the admin System Health widget must show a persistent non-dismissible banner naming the affected service instance and elapsed time; (c) a one-time `config.app_config_unreachable_threshold_exceeded` admin notification fires via Telegram+email (edge-triggered — fires once on first breach, resets after successful reconnect). Constraint that threshold must be strictly less than `max_age_seconds` is enforced at startup with a Warning log. Added the new seed row to `docs/system-config.md`.

**A-4. Modular monolith is correct for this scope.** The Next.js thin frontend + ASP.NET Core API + .NET Worker + MongoDB + SQL Server split is well-chosen for the developer profile in CLAUDE.md. No change recommended. Flag for the record: the repo-structure in `docs/repo-structure.md` layers `apps/{web,api,worker}` with shared packages which is appropriate.

> **ℹ️ NO CHANGE REQUIRED.** Architecture is appropriate for the scope; confirmed for the record.

**A-5. EODSR, LMDS, LADS, DS, HDS, and the RME are all Worker Service components but their cohabitation is not scheduled.** `docs/implementation-roadmap.md` phases the builds but the runtime schedule (what runs when, Mon–Fri vs weekend, and what is serialised vs parallel inside the single Worker) is only implicit. *Smallest change*: a short "Worker Service schedule" section in `docs/system-architecture.md` that names the intraday cadence and the end-of-day pipeline ordering. Half a page.

> **✅ RESOLVED 2026-04-20.** Added a **Worker Service Schedule** section to `docs/system-architecture.md` immediately before Cross-Cutting Concerns. The section covers: (1) pre-session setup — EOD stop-update job runs synchronously before LMDS/LADS start (ADR-0003 carve-out); Symbol Validity Probe on first admin token generation; (2) market hours — LMDS continuous at 90 s, LADS at 15 min intervals, Notification Delivery Job continuous; (3) post-market EOD pipeline — LMDS/LADS stop, DS runs at 17:00 IST, EODSR starts on DS success marker, RME optimisation runs after EODSR; (4) weekends/holidays — LMDS/LADS inactive, admin-triggered ops only; (5) explicit serialisation rules including the constraint that LMDS/LADS must not run concurrently with DS/EODSR on the same trading day.

**A-6. SQL Server per-symbol table-suffix pattern (`D_{suffix}` / `W_{suffix}` / `M_{suffix}`) is sound but will pay a cost in cross-symbol queries.** `docs/data-management.md` pins the suffix as stable and immutable. Confirmed-acceptable only if the query patterns never require "top N by momentum across Nifty 500". If a future requirement needs that (ranking, universe screens), document now that it will require a materialised-union view or a switch to a single partitioned table; do not let a future screener requirement trigger a silent schema migration.

> **✅ RESOLVED 2026-04-20.** Added a **Cross-symbol query limitation** note to the Market Data Database section of `docs/data-management.md`. The note explicitly states the per-symbol table pattern is optimised for single-symbol sequential reads and carries a high cost for cross-symbol queries; names the two acceptable migration paths (pre-computed aggregate table updated by DataSync — preferred, or fleet-wide migration to single partitioned table); declares that neither path is a silent upgrade and both require a new ADR and REQ-MIGRATION-004 governance; requires this constraint to be noted in any future screener or ranking requirement before implementation begins.

**A-7. Intent ledger with unique `{nonce}` and compound `{user_id, status, created_at}` index is correct.** Confirm whether the nonce is ever used for *idempotent* re-submission (user re-clicks the button). If yes, the unique index is right. If no (single-use only), say so in REQ-ORDER-012 to avoid a future retrofit.

> **✅ RESOLVED 2026-04-20.** Confirmed: the nonce is strictly single-use. Added `REQ-ORDER-009c` to `docs/requirements-spec.md` immediately after REQ-ORDER-009b explicitly stating: the nonce is single-use and not for idempotent re-submission; each Phase 1 recalculation issues a new independent nonce; the nonce is consumed on the first accepted intent-ledger write; any subsequent write with the same nonce is rejected with `nonce_already_used` and the REQ-ORDER-018b guard-state banner is shown; a failed intent write does not consume the nonce — the user must return to Phase 1 for a fresh payload. The `orders.payload_nonce_ttl_seconds` (default 300 s) expiry window already seeded in system-config.md prevents stale-tab re-submissions.

## 5. Security Findings

**S-1. HMAC payload domain separation is not pinned.** The Branded Button Contract describes an HMAC-signed payload from the platform to the widget. If the same HMAC key is reused for any other purpose (cookie sign, CSRF token, webhook verification) a confused-deputy path opens. *Smallest change*: require a domain-separation prefix string (e.g., `fyers.intent.v1:`) inside every HMAC input, and require the signing key to be isolated from any other HMAC key. One sentence in REQ-ORDER-013 and a named `orders.intent.hmac_key` in `docs/system-config.md`.

**S-2. Single-active session (REQ-SEC-010) plus admin step-up re-auth (REQ-SEC-011) is the right baseline; the step-up scope is vague.** Which admin operations demand step-up? Seeding sys_config? Rotating a Telegram token? Forcing a user's position to Suspended? Without a list, the step-up will either be annoyingly present or missing from the places that matter. *Smallest change*: add a small table to `docs/requirements-spec.md` naming the operations that require step-up.

**S-3. FYERS admin daily-token handling for MDP ingestion.** The admin daily-token flow is mentioned but the failure path when the admin forgets to refresh the token before market open is not. DS, HDS, and EODSR all break silently if the token is stale. *Smallest change*: require a pre-market token-validity probe (at a fixed IST time in `sys_config`) with a Telegram admin alert on stale. This is one sys_config key and one scheduled task.

**S-4. OAuth provider configuration (Google/Microsoft/Facebook) is correct at a requirements level; no mitigation is stated for OAuth-provider outage.** For a Phase A user base this is acceptable. Record as an explicit known limitation, not as a gap.

**S-5. Intent-ledger tamper resistance.** Intent documents are server-written and referenced by the widget, but the review found no guarantee that an intent document, once submitted to the widget, is immutable on the server. If the server can mutate an intent mid-flight, a malicious admin or a bug can edit an intent's price or quantity after the user has seen it. *Smallest change*: declare `intent_ledger` documents immutable after `status = Submitted`; all subsequent data goes into sibling documents (reconciliation, fills).

**S-6. Portal Live Data (PLD) via user token in the browser is acceptable but must not leak into backend logs.** With OTLP/Serilog on, the user's FYERS token can easily end up in a trace attribute by accident. *Smallest change*: add a Serilog destructuring policy requirement in `docs/engineering-standards.md` that redacts any property matching `*token*`, `*access_token*`, `*Authorization*`. Standard practice; not overkill.

**S-7. Admin-initiated position-state overrides should write an immutable audit.** The `rme_incidents` collection is a reasonable home. Confirm that admin overrides write to `rme_incidents` with `source=admin`, the admin user ID, and the prior position snapshot.

**S-8. CSRF.** Next.js frontend + ASP.NET Core API — the spec does not explicitly state the CSRF model. For an OAuth-plus-bearer model this is usually fine but needs one sentence in `docs/engineering-standards.md` confirming the chosen pattern (bearer tokens + SameSite cookie for session).

## 6. Trader-Experience Findings

**T-1. A trader can initiate an entry from the chart but the chart is not required to reflect pending-entry state.** REQ-CHART-00x and REQ-ORDER-01x do not pin that a `PendingEntry` intent is visible on the chart as an overlay. Without it, a trader who clicks "execute" and then navigates the chart to another symbol cannot see their own pending work and may retry. *Smallest change*: require a small chip or overlay on the chart showing any non-terminal intent on the currently viewed symbol.

> **✅ RESOLVED 2026-04-20.** Added `REQ-CHART-004a` to `docs/requirements-spec.md` immediately after REQ-CHART-004. The requirement mandates a non-dismissible pending-submission chip in the position context section whenever the user has a `pending`-status `intent_ledger` record for the currently viewed symbol. The chip shows action type, elapsed time, and "Awaiting FYERS confirmation." The chip lifecycle is fully pinned: it transitions to the REQ-ORDER-015e awaiting-fill indicator on `matched` status, to the `unresolved` advisory on timeout, and to the REQ-ORDER-015 error surface on `submission_failed`. This closes the pre-callback visibility gap that REQ-ORDER-015e (which covers only `matched` status) left open.

**T-2. XIRR during suspension is not specified.** REQ-DASH-010 defines XIRR via Newton-Raphson over the user's ledger. If a position is `Suspended` with an unresolved fill, does its presumed market value feed XIRR? This changes the displayed number dramatically. *Smallest change*: pin that `Suspended` positions are marked-to-last-known-price with a disclosure footnote on the dashboard.

> **✅ RESOLVED 2026-04-20.** Added `REQ-DASH-003b` to `docs/requirements-spec.md` immediately after REQ-DASH-003a. The requirement pins that Suspended positions contribute to the XIRR terminal cash-flow value at last-known mark-to-market price (SQL Server close, or most recent FYERS live quote if fresher). A dashboard disclosure footnote is required whenever any Suspended position is contributing, stating the count and noting that values are based on last-known price. The same rule applies to backtest XIRR (REQ-BTSTORE-006) and the portfolio analytics layer.

**T-3. Pyramiding UX is under-specified.** A trader adding a second tranche will expect to see prior tranches, the combined cost basis, and the effective stop. Only the cost basis is implied by the portfolio math. *Smallest change*: require the Position Detail view to show all contributing intents and the effective combined stop (see §3.5).

> **✅ RESOLVED 2026-04-20.** Added `REQ-PYR-012` to `docs/requirements-spec.md` immediately after REQ-PYR-011. The requirement mandates a per-tranche breakdown on the Position Detail page for any position with more than one confirmed add fill. The breakdown must show: each tranche with fill date, quantity, fill price, and initial stop; the combined weighted-average entry price and total quantity; and the REQ-PYR-011 floor-adjusted effective combined stop in the RME advisory panel. The breakdown persists on closed position records for post-exit review. Single-tranche positions show no breakdown.

**T-4. Telegram notifications on entry-fill are LADS-gated (REQ-ORDER-015f).** This is correct. But the Telegram message content has no spec beyond idempotency via `telegram_message_id`. Traders care about: symbol, side, quantity, fill price, stop, R-risk, and the entry intent source (manual vs signal). *Smallest change*: pin a message template in `docs/requirements-spec.md` so Phase 4 and Phase 6 do not ship divergent formats.

> **✅ RESOLVED 2026-04-20.** Added `REQ-NOTIFY-024` to `docs/requirements-spec.md` immediately before the Execution Confirmation and Order Placement section. The requirement locks the eight required fields for both the Telegram dispatch and the portal feed entry on a LADS-confirmed fill: (a) symbol + exchange code, (b) transaction side, (c) filled quantity, (d) weighted average fill price (INR, 2 d.p.), (e) initial RME stop level (INR, 2 d.p.), (f) risk as % of equity + INR amount, (g) intent source (Signal name or Manual), (h) chart deep link. Partial-fill notifications must additionally state filled vs requested quantity. The field set is declared a breaking-change contract: additions or removals require a REQ update, preventing Phase 4 and Phase 6 from shipping silently divergent formats.

**T-5. Watchlist/Chart <-> Signal parity.** A signal displayed on the dashboard may not match what the chart shows if the chart is served from different cache-TTLs. *Smallest change*: require both views to render from the same `ledger_snapshot_version`-keyed cache or to display a "last updated" timestamp, so traders can sanity-check concurrency.

> **✅ RESOLVED 2026-04-20.** Added `REQ-WATCH-002a` to `docs/requirements-spec.md` immediately after REQ-WATCH-002. The requirement mandates that signal advisory data shown on the watchlist and on the chart page for the same symbol must reflect the same data epoch. Two compliant approaches are offered — shared `ledger_snapshot_version` cache key (approach a, preferred), or per-surface "Signals as of {timestamp}" indicators (approach b). Either satisfies the requirement; the chosen approach must be recorded in `docs/engineering-standards.md` under the caching conventions section. The invariant is explicit: a trader must never face an unindicated discrepancy between watchlist and chart advisory state.

**T-6. Exit-priority display.** Priority 1–8 is a platform-level policy but users will want to see *which priority fired* on a closed position. *Smallest change*: require the `positions` terminal document to record the `exit_reason` with the priority rank, surfaced on the Position Detail.

> **✅ RESOLVED 2026-04-20.** Added `REQ-PLC-011` to `docs/requirements-spec.md` immediately before REQ-PLC-010. The requirement mandates that every terminal position document (Closed or Rejected) records an `exit_reason` field with both a machine-readable reason code and the numeric exit priority rank (1–8 per REQ-STOP-012, or 0 for out-of-band `manual_exit` and `admin_forced_close`). All eight in-priority-list reason codes are enumerated. The field and priority rank must be surfaced on the Position Detail page for all closed positions. Backtest position records (REQ-BTSTORE-005) must carry the same fields for consistency between live and backtest exit-cause analysis.

**T-7. Fundamental widget consent.** TradingView iframe widgets load third-party JS. The trader experience is fine; for the record, flag that any future blocker of third-party content in the user's browser (extension, corporate firewall) will silently break REQ-CHART-010..013. This is known, not a gap.

## 7. NFR Gaps That Actually Matter

These are the NFRs whose absence will actually show up as engineering pain. NFRs that are already covered appropriately are not relisted.

**N-1. Load-test acceptance thresholds are named for Phase B but the test fixture is not.** `docs/engineering-standards.md` commits to a pre-Phase-B load test. The spec does not pin the target p95 latency on `/positions`, `/dashboard`, or the RME Channel drain rate under N concurrent users. *Smallest change*: one table in `docs/engineering-standards.md` with 3–5 endpoint-level SLOs.

> **✅ RESOLVED 2026-04-20.** Added a **Load-test SLO targets (Phase B gate)** table to `docs/engineering-standards.md` under the Performance and resilience subsection. Five p95 targets are pinned at 20 concurrent users on a production-equivalent Azure-hosted environment: `GET /api/dashboard` ≤ 500 ms; `GET /api/positions` ≤ 300 ms; `GET /api/signals/{symbol}` ≤ 200 ms; RME Channel drain (event enqueue to durable risk-state commit) ≤ 2 s; WebSocket push (LMDS tick to client frame) ≤ 1 s. Any target miss must be recorded in `audit_events` with p95 measured value and remediation action before the Phase B transition is unblocked.

**N-2. Observability budget during a 50× tick spike is not named.** OTLP collector dual-replica (REQ-NFR-009a) is correct. There is no statement on what the system does when collector ingest is saturated (drop, back-pressure, local buffer). *Smallest change*: require local file buffer with a bounded size and a named metric for spill. One paragraph in ADR-0002.

> **✅ RESOLVED 2026-04-20.** Added an **OTLP collector saturation policy** section to `docs/adr/0002-observability-and-configuration.md`. Policy: collector uses a bounded local disk buffer (default 256 MB) as first-line defence; emits `otel.collector.buffer_spill_total` counter on ceiling hits and `otel.collector.buffer_fill_ratio` gauge each flush cycle; a non-dismissible admin System Health banner fires on any spill increment; a one-time `otel.collector.buffer_near_capacity` admin notification (Telegram + email, edge-triggered) fires at ≥ 80% fill. Under sustained saturation, trace spans are deprioritised vs metrics and structured error/warning logs. Alert rules relying on metric absence must account for collector saturation as a benign explanation.

**N-3. RTO/RPO for MongoDB and SQL Server.** The data-management doc names retention, but recovery targets are implicit. For a trading platform, RPO > a few minutes during market hours is unacceptable (positions lost). *Smallest change*: name RPO ≤ 1 min / RTO ≤ 15 min for MongoDB during market hours, looser values off-hours. SQL Server (historical) can be much looser.

> **✅ RESOLVED 2026-04-20.** Added a **Data Recovery Targets (RTO/RPO)** subsection to `docs/engineering-standards.md` under Operational Standards. Targets: MongoDB (positions, intent ledger, trade ledger, rme_incidents) — market hours RPO ≤ 1 min / RTO ≤ 15 min; off-hours RPO ≤ 4 hours / RTO ≤ 1 hour. SQL Server (historical OHLCV) — any window RPO ≤ 24 hours / RTO ≤ 4 hours (rebuildable via HDS + DS; daily Azure Backup sufficient). Redis — no durability requirement; RTO ≤ 15 min. MongoDB market-hours targets require continuous backup or change-stream-based replication — daily snapshot alone is insufficient. Recovery exercises must be validated in Phase C chaos exercises.

**N-4. Test coverage targets are 70% .NET / 60% TS.** For the RME, 70% is too low. The RME is the correctness-critical surface; it should be 95%+ on unit tests plus a separate contract-test floor. *Smallest change*: carve the RME out of the general target with a dedicated line in `docs/engineering-standards.md`.

> **✅ RESOLVED 2026-04-20.** Added an **RME coverage exception** bullet to `docs/engineering-standards.md` under Testing Standards → Coverage targets. The RME is carved out of the general .NET 70% target and must independently reach ≥ 95% line coverage by unit tests. Additionally, a dedicated contract-test floor is required: at least one contract test per documented state-transition (PendingEntry → Open → Suspended → Closed/Rejected and all sub-paths) and per OCC scenario (clean commit, single-retry success, 3-retry exhaustion/freeze). Both the 95% unit-test target and the contract-test floor gate Phase 6 acceptance per REQ-NFR-014.

**N-5. Time-source agreement.** EODSR, LMDS, LADS, and the Timeframe/Calendar Layer all consume time. There is no requirement that they agree on an NTP source or on IST as the canonical zone. Implicit, but leave no room to guess. *Smallest change*: declare IST as the canonical trading zone; all stored timestamps are UTC; all display and scheduling is IST; single sentence in `docs/engineering-standards.md`.

> **✅ RESOLVED 2026-04-20.** Added an explicit IST/UTC time-source convention to `docs/engineering-standards.md` under Data Standards. The convention declares IST (Asia/Kolkata, UTC+05:30) as the canonical trading time zone for scheduling, display, time-stop evaluation, and NSE calendar logic; all components that consume time (EODSR, LMDS, LADS, Timeframe/Calendar Layer, RME) must agree on this zone; all stored timestamps are UTC — IST conversion happens only at the presentation or scheduling layer. This closes the implicit assumption and ensures all Worker Service components and the API share one authoritative time contract.

## 8. Logical Inconsistencies

**L-1. "Drawdown is advisory" (REQ-BOUNDARY-004) vs the graduated drawdown table in `docs/portfolio-risk-guidelines.md`.** The table is prescriptive; the requirement is advisory. Either say the table is a *default* that can be relaxed, or promote the table to prescriptive for Phase A. Right now the two can be quoted against each other in code review.

> **✅ RESOLVED 2026-04-20.** Added an enforcement-category addendum to `REQ-DRDN-003` in `docs/requirements-spec.md` and updated the Exit Priority Note in `docs/portfolio-risk-guidelines.md`. Both documents now distinguish two categories explicitly: (a) *Platform-enforced restrictions on RME output* — 5% (algorithmic size reduction, REQ-DRDN-005), 10% (add-on recommendation suppression), and 20% (new-entry signal blocking and Phase 1 modal rejection, REQ-ORDER-004) — applied automatically by the platform with no user acknowledgement; (b) *User-advisory notifications* — 15%, 25%, and 30% — surface a prominent advisory; the user retains full discretion. The addendum also pins that none of the six responses involve autonomous order placement or position closure (consistent with REQ-BOUNDARY-004), and that while threshold VALUES are configurable per REQ-DRDN-004, the ENFORCEMENT CATEGORY of each level is fixed and cannot be changed by configuration. This eliminates the code-review ambiguity.

**L-2. Backend-to-FYERS is REST-only (CLAUDE.md), MDP is REST-only on server, Worker is single-instance.** These three together mean that during market hours a single Worker is serially polling REST for every symbol for DS/LMDS. Confirm the MDP bulk-quote rate-limit analysis in `docs/implementation-roadmap.md` Phase 2 preconditions actually fits a single-instance Worker — i.e., confirm that Nifty 500 in the required cadence fits inside FYERS's documented per-minute quota with headroom. If it does not, either the cadence or the single-instance invariant gives way, and both are guardrails. A calibration note (similar to ADR-0004's calibration-note deliverable) should be required as a Phase 2 precondition.

> **✅ RESOLVED 2026-04-20.** Extended the Phase 2 Bulk Quotes rate-limit precondition in `docs/implementation-roadmap.md` with a **Resolution clause**. The clause cross-references the pre-computed sensitivity analysis in `docs/operations/fyers-api-budget.md` (which already demonstrates that even under the conservative per-symbol assumption, the 90-second default keeps Phase A under the 80% budget threshold). The clause explicitly pins the resolution path when verification reveals a lower-than-modelled quota: lengthen the poll interval by adjusting `sys_config` seed — never relax the single-instance Worker constraint (ADR-0003) or the server-side REST-only MDP constraint (CLAUDE.md, REQ-MARKET-002), both of which are non-negotiable guardrails independent of rate-limit economics. If Nifty 500 monitoring cannot fit at any meaningful cadence within those constraints, the finding must be recorded in `docs/operations/fyers-api-budget.md` as a known limitation and treated as the primary trigger for prioritising the MDP migration per ADR-0005.

**L-3. "Callback confirms submission, not fill" (REQ-ORDER-015) vs Telegram notification on entry-fill (REQ-ORDER-015f) vs reconciliation (REQ-RECON-001..008).** The three are internally consistent but the ordering guarantees are not stated. If LADS fills a position *before* the intent callback arrives (possible under poor network), the Telegram notification may fire before `intent_ledger` is updated. The trader will be confused. *Smallest change*: pin an event ordering rule: Telegram fires only after both `intent_ledger.status=Submitted` and the matching LADS fill are durably persisted.

> **✅ RESOLVED 2026-04-20.** Added a **Dispatch ordering invariant** paragraph to the end of `REQ-NOTIFY-024` in `docs/requirements-spec.md`. The invariant pins a mandatory write sequence for all LADS-initiated fill notifications, specifically covering the fill-before-callback case (REQ-ORDER-015g matrix row 4): (1) LADS must transition `intent_ledger` from `pending` to `matched` with `match_source = "lads_reconciliation"`; (2) LADS must update `positions` to `Open`; (3) only then may the Telegram notification and portal feed entry be dispatched. The callback, when it eventually arrives, stamps `callback_received_at` on the already-`matched` record without triggering a second notification. A contract test is required to assert that, for the fill-before-callback case, `intent_ledger.status = matched` and `positions.lifecycle_state = Open` are both true at the time the Telegram notification is observed as dispatched. This eliminates the scenario where the Telegram notification references an `intent_ledger` record still in `pending` state.

**L-4. Position unique-index constraint (REQ-PLC-007a) over non-terminal states vs partial fills.** See CG-4. The two collide.

> **✅ RESOLVED 2026-04-20 (via CG-4).** The collision between the `{user_id, symbol}` partial unique index and multi-fill orders is fully resolved by the CG-4 resolution already applied to `REQ-PLC-007a`: one FYERS `order_id` maps to exactly one `intent_ledger` record and therefore to exactly one `positions` document; all subsequent fills for the same `order_id` accumulate into that one document via LADS quantity-and-price updates. The unique index is therefore never violated by legitimate partial fills — only by genuine concurrent duplicate-creation attempts, which the index is specifically designed to block. No additional change required.

**L-5. Admin-forced Suspend and RME-forced Suspend share the same state with different recovery paths.** Admin resume and RME self-recovery should not be the same operation. Currently, both just flip the state.

> **✅ RESOLVED 2026-04-20.** Added `REQ-ADMIN-016` to `docs/requirements-spec.md` immediately before Part 9. The requirement prohibits a single generic "Resume Position" or "Release Suspension" action in the admin portal and requires source-specific resolution flows for each of the four authorised suspension sources (per REQ-PLC-005a): (a) `LMDS` — display "Self-monitoring — may auto-resolve"; no release action by default; admin override requires step-up re-auth and an `audit_events` record. (b) `RME_OCC` — display "OCC retry exhaustion — incident resolution required"; "Release" action is blocked until the linked `rme_incidents` record is marked resolved by an admin. (c) `CORPORATE_ACTION` — display "Corporate action detected — re-anchor required"; only the REQ-PLC-010 re-anchor flow is offered; step-up re-auth required. (d) `ADMIN` — display "Manually suspended"; "Release suspension" action available with step-up re-auth and an `audit_events` record. This ensures an operator cannot inadvertently clear an RME- or LMDS-triggered safety suspension through the same UI action used to release a manual hold.

## 10. Edge Cases / Failure Modes

- **Holiday open.** Half-days (e.g., Muhurat) are not named in the Timeframe/Calendar Layer behaviour.
- **Single-stock circuit lock.** If a symbol is locked upper/lower circuit for the day, LMDS will receive no ticks; stop evaluation on that position will not fire. The spec does not pin "do nothing" as the expected behaviour, but it is. Pin it.
- **Widget closed after submit.** If the FYERS branded button submits and the user force-closes the tab before the callback resolves, the intent_ledger row will sit in `Submitted` indefinitely. Reconciliation (REQ-RECON-00x) will eventually resolve via LADS, but a TTL / timeout on `Submitted` intents should be named.
- **Nonce reuse attempt.** The unique index on `{nonce}` handles this at the storage layer. The *user-facing* error message should be specified ("This order has already been submitted; check your positions"), otherwise implementers will surface an opaque 500.
- **Clock skew between Worker instances during the pipeline-gate upgrade.** If the IaC is ever edited to allow two Workers, the Redis lease is the last line; verify the lease TTL is short enough that a dead Worker releases within the next job cycle.
- **App Config returns a stale value.** Handled by LKG cache; add staleness-visibility per A-3.
- **OCC retry storm during a corporate-action backfill.** If a backfill re-writes many positions and bumps `_version`, the RME will see apparent conflicts. Require backfills to pause RME (a Redis flag) rather than race it.
- **Telegram bot rate limit.** Bulk exits on a gap-down day can hit Telegram's per-chat rate limit. Require a local queue with back-off.

## 11. Over-Engineering Risks

The overarching principle in `docs/build_docs_reviews/prompt.md` asks for explicit flagging of complexity that exceeds phased-rollout need. Three areas merit this call-out.

**O-1. Three-layer Worker singleton enforcement front-loaded in Phase 0.** IaC + pipeline gate + Redis lease is the right target for Phase C. For a Phase A single-developer team, the Redis lease alone is sufficient. Recommend authoring the IaC and pipeline gate once and then *not* revisiting them until Phase C — treat them as frozen scaffolding, not as active code. If this is already the intent, say so in `docs/implementation-roadmap.md` to relieve the implementer of the impression that all three must be lovingly maintained from Phase 0.

**O-2. Reconciliation (REQ-RECON-001..008) is shaped for a larger platform.** For a Phase A user base in the tens, daily manual reconciliation with a small set of heuristics is sufficient. The full eight-requirement reconciliation engine is appropriate in Phase B. Consider labelling REQ-RECON-005..008 as Phase-B-gated to avoid Phase-A over-investment.

**O-3. Market Data Provider abstraction with three supported vendors on day one.** The abstraction is correct; *implementing* all three adapters before any one is in production is over-investment. Keep the abstraction; ship only the FYERS adapter in Phase A, with the MDP interface defined so that the TrueData/GDF adapter is a later addition. This appears to be the intent but is not stated as a non-goal anywhere.

Two additional items to note as **not** over-engineering, despite looking like it at first glance:

- The per-user trade-ledger write lock (REQ-PORT-031 + fencing tokens) is *not* overkill. Two concurrent writes on the same ledger will corrupt XIRR; this is a correctness problem, not a throughput one.
- The OCC `_version` model is *not* overkill. The alternative (coarse lock per user) will visibly lag the RME on any active user.
