# Build-Documentation Review — 2026-04-25

Reviewer perspectives applied simultaneously: senior technical reviewer, software/solution architect, application security reviewer, professional discretionary/systematic trader. Compliance, SEBI, DPDP, KYC, tax, and data-residency concerns are out of scope per `docs/build_docs_reviews/prompt.md`. Findings are prioritised by whether they materially reduce the risk of incorrect trading decisions, data loss, security compromise, or unbuildability. Over-engineering is flagged explicitly where the existing spec carries more complexity than the phased rollout justifies.

This review is a **fresh pass** following the 2026-04-20 review. It does not re-raise items already closed there. Where a prior finding was resolved but the resolution introduced a new gap or ambiguity, that secondary gap is recorded here under its own identifier. All citations are to file and requirement ID in the repository snapshot dated 2026-04-25.

---

## 1. Executive Summary

1. The documentation is unusually disciplined. The prior 2026-04-20 review closed 30+ findings, and the resulting spec is materially tighter than most retail-trading platform documentation I have seen at pre-build. The hard invariants — per-position event serialisation (ADR-0003), per-user trade-ledger write lock with fencing tokens (REQ-PORT-031/031a/031b), intent-ledger immutability (REQ-ORDER-014b), callback-vs-fill separation (REQ-ORDER-015 / -015g), and single-instance Worker enforcement (REQ-RME-CONC-006) — are the right correctness anchors for a platform that will touch user capital.

2. **Risk Management Engine:** the RME is the correctness-critical surface of the platform and is the strongest-specified section of the spec. Scoring (REQ-RME-020a/b/c), robustness factor, multi-timeframe evaluation, dynamic trigger recalibration (REQ-RME-022), nightly BTE-vs-live parity (REQ-NFR-017), and the 95% unit-test carve-out in `docs/engineering-standards.md` together form a credible trust envelope. However, three RME gaps remain — the Suspended-state channel leak (§3.2), the missing runbook for the REQ-RME-CONC-007 frozen-with-visibility admin flow (§3.3), and a backtest-starting-equity semantic that undermines historical backtest integrity (§3.5).

3. **Trader usability:** the Phase 1 modal is well specified for entry hygiene but has one meaningful usability regression — the estimated fill value shown in the modal (REQ-ORDER-007) is not pinned to a freshness contract, so a trader sitting on the modal for 60+ seconds while price moves will submit against stale context. There is also no "fast exit" for emergencies: every exit requires the Phase 1 modal → widget chain, which is correct for advisory-only design but penalises the reflex-driven exit that traders expect on a gap-down.

4. **Security:** the intent HMAC domain separation (REQ-ORDER-009b) and the Serilog redaction policy (engineering-standards) are the right baseline. The remaining security gaps are operational: (a) the admin's own equity-override path (REQ-RME-006c) has no systemic alert when the override silently diverges from real FYERS net equity, (b) `amr`-claim MFA validation per OAuth provider (REQ-BCP-009) is not enumerated per provider, and (c) the Phase 0 Worker singleton lease has a documented-but-thin degradation path if Redis is down at startup — correct at ADR-0003 scale but warrants a specific operational runbook.

5. **Over-engineering risk:** Phase 0 has drifted into SRE-mature-infrastructure-before-any-product territory. The Phase 0 roadmap now requires the seeder console app + three-tier migration pipeline + singleton-lease IaC + App Config LKG cache + OTLP collector dual-replica + saturation policy + sys_config sentinel check — all before the first line of product code. For a single-developer team targeting a handful of Phase A testers, this is a materially heavier setup than the early phase requires. The correct resolution is not to remove any of it but to explicitly document that these are one-time-author-and-freeze items (Phase 0 roadmap already says this for the singleton; extend that language to the rest).

6. **Operational readiness:** of the sixteen runbooks in `docs/operations/runbooks/README.md`, three are Phase A mandatory (in stub form, pending field-test) and thirteen are Phase B mandatory (not drafted). Two of the Phase-B runbooks — `admin resolution for the RME concurrency-freeze state` (REQ-RME-CONC-007) and `MongoDB replica-set failover during LADS polling` (REQ-PORT-021a) — are actually pre-Phase-A-production-use items given the correctness invariants they enforce, and should be promoted to Phase A mandatory in the runbook catalog before the first non-admin tester is onboarded.

7. **Critical gaps identified in this pass:** four net-new critical gaps (CG-6 through CG-9) that will, with high confidence, produce either incorrect trading outcomes or unbuildable code if left unresolved. The most important is **CG-6** — REQ-PORT-005a silently excludes non-Nifty 500 holdings from RME equity computations, which is the documented-but-understated cause of the equity-base-override divergence problem and, at scale, the single biggest source of "why did the platform size my trade this way?" trader confusion.

8. **Scope discipline:** the boundary requirements (REQ-BOUNDARY-001–004) and the non-negotiable guardrails in `CLAUDE.md` are being respected. The out-of-scope list (REQ-OOS-001–011) is genuinely out of scope. The Phase A tester ceiling is being enforced by design in the approval flow. No speculative features crept in between reviews.

9. The spec remains buildable. None of the findings below are blocking at a documentation level. They should be resolved before committing code to the corresponding phase, but they do not stop Phase 0 work that is already queued.

## 2. Critical Gaps

Gaps whose absence will, with high confidence, produce either incorrect trading outcomes, data loss, or unbuildable code. Ranked above everything else in this review.

**CG-6. Non-Nifty 500 holdings silently excluded from equity base with no user-visible reconciliation.** `REQ-PORT-005a` says trades and holdings in symbols outside the symbol master "must be silently ignored and must not be ingested into the trade ledger, displayed in the portal, or considered in any RME calculation including portfolio heat, position sizing, drawdown tracking." `REQ-RME-006a/b/c/d` then computes the RME's "platform-visible equity base" from Nifty 500 holdings + cash only, and `REQ-RME-006b` does surface the three-line disclosure panel (FYERS total / platform-visible equity / excluded). So far, good. **The gap is the divergence-over-time alert that is missing.** A user who deposits ₹10 lakh into FYERS, buys a mid-cap outside Nifty 500, and then trades Nifty 500 stocks on the platform will see their platform-visible equity base grow as those trades fill, while their FYERS total equity also grows from the outside-universe position's P&L — but the platform has no way of knowing that they added capital that should have bumped the RME's sizing denominator. The RME will under-size their trades. Conversely, a user who sells a non-Nifty 500 holding is burning the capital they thought the RME was sizing against. *Smallest change*: require a non-blocking advisory on the dashboard and a one-time Telegram notification if FYERS-total-account-value diverges from platform-visible-equity-base by more than a configurable percentage (`sys_config.risk.equity_base.external_divergence_warn_pct`, default 15%) from the last reconciled state, so the user is prompted to either add the symbol to their watchlist (if it becomes Nifty 500), enable the manual equity override (REQ-RME-006c), or accept the silent exclusion. Without this, sizing errors are a slow-burn trust problem that only surfaces when a user questions a position size.

**CG-7. Phase 1 modal estimated-fill-value has no freshness contract.** `REQ-ORDER-007` requires the modal to display "estimated fill value at the last available quoted price" and `REQ-ORDER-008` says the value "must recalculate in real time" on user edit — but neither requirement pins the quote source or the refresh cadence when the user is *not* editing. The signed-payload nonce has a 300-second TTL (`orders.payload_nonce_ttl_seconds`) and the widget-invocation guard allows 120 seconds (`orders.widget_timeout_seconds`), so a trader can sit on the modal for up to 5 minutes while price moves materially. For a Nifty 500 large-cap during market hours this is 30-60 basis points of drift; for a mid-cap in a volatile session it can be 2–3%. The trader is submitting against an estimate that looked right when the modal opened. *Smallest change*: require the Phase 1 modal to refresh the estimated fill value on a fixed cadence (add `sys_config.orders.phase1_quote_refresh_seconds`, default 5), source the quote from the same Portal Live Data path used for the chart page, and display the quote-as-of timestamp prominently next to the estimated fill value. If the quote drifts more than `integrations.fyers.price_deviation_warning_pct` (already seeded) from the original at signed-payload time, re-surface the REQ-ORDER-011 warning automatically without requiring user edit. This prevents the trader-surprise failure mode where the modal said one thing and FYERS filled at another.

**CG-8. Admin-caused Suspended states are not enumerated as REQ-PLC-005a sources.** `REQ-PLC-005a` lists exactly four authorised producers of the `Suspended` state: `LMDS`, `RME_OCC`, `CORPORATE_ACTION`, `ADMIN`. But the documentation describes at least *five* admin-origin Suspended transitions that don't fit cleanly into the single `ADMIN` bucket: `REQ-ADMIN-007` (kill switch activation → reason `kill_switch_activated`), `REQ-ADMIN-010` (per-user signal suspension → reason `user_signal_suspended`), `REQ-ADMIN-001a` (account deactivation → reason `account_deactivated`), `REQ-ADMIN-013` (Signal type disabled platform-wide → reason `signal_type_disabled`), and `REQ-STRAT-007a` (user-paused subscription → reason `subscription_paused`). These five reason codes all produce Suspended state but are not consistently classified against the four REQ-PLC-005a sources, and REQ-ADMIN-016 (source-specific resolution flows) only covers the four original sources. The consequence is that an admin suspending a user account via REQ-ADMIN-001a produces Suspended positions that REQ-ADMIN-016 has no corresponding resolution flow for — the admin UI will show them alongside `ADMIN`-sourced manual suspensions but the resolution path is "reactivate the account" (REQ-ADMIN-001b), not "release suspension." *Smallest change*: extend the REQ-PLC-005a producers table to list all six admin-origin reason codes under the `ADMIN` source, with distinct `triggering_condition` values that map to the appropriate recovery path (kill switch: on deactivation, don't auto-release — require fresh EODSR per REQ-ADMIN-007; account deactivation: on reactivation, rely on REQ-ADMIN-001b and re-run account sync; etc.). Then expand REQ-ADMIN-016 to name the per-reason resolution semantics so the admin UI can present the correct action instead of offering a blanket "Release suspension" that may re-enter the wrong state.

**CG-9. Backtest starting equity default is semantically wrong for historical windows.** `REQ-BTSTORE-006a` says the starting-equity input "must be pre-populated with the user's current account equity derived from their latest portfolio snapshot." This is a reasonable default for a forward-looking paper-trade backtest, but the platform's backtest window is historical (over existing SQL Server OHLCV). Using *today's* equity as the starting equity for a backtest that ran from 2022-01-01 to 2023-12-31 produces an equity curve that doesn't correspond to anything the user would have actually experienced — the 2023 year-end equity in the backtest will be today's equity × the strategy's R multiple, not today's equity itself. This distorts the reported drawdown, maximum drawdown in R, and XIRR in ways that can make a strategy look far safer (or far more dangerous) than it is. The per-trade R statistics are correct; only the portfolio-level figures are wrong. *Smallest change*: change the default to a fixed nominal starting equity (e.g., ₹10 lakh, seeded in `sys_config.strategies.backtest.default_starting_equity_inr`) and clearly label it "notional starting equity for backtest comparison" in the UI. Leave the user's override capability intact. Add a caveat in the backtest result header stating that portfolio-level figures (equity curve, drawdown %, XIRR) are scaled to the notional starting equity and are meaningful only in comparison across configurations, not as a projection of real outcomes on the user's own account.

## 3. Risk Management Engine Findings

### 3.1 Robustness (handling missing, stale, partial data)

`REQ-RME-006a/b/c/d` and the snapshot-consistent read contract in REQ-RME-006d together form a genuinely robust equity-read model under concurrent ledger writes. Two sub-gaps remain:

**RME-R1. Snapshot retry exhaustion vs override-in-effect.** REQ-RME-006d declares that when the manual equity override (REQ-RME-006c) is active, the override value substitutes for ledger-derived equity at sizing time, but the snapshot-consistent read is still required for the *other* ledger-derived inputs (current portfolio heat, open quantities, holdings composition) because they must be internally consistent with each other. This is correct in principle but in practice it means a user with an active override will still hit snapshot-retry exhaustion if the ledger is contended — they will see "portfolio state is updating — please retry shortly" even though the thing they think drives sizing (their override) is stable. Trader UX concern. *Smallest change*: when an override is active, relax the retry-exhaustion message to "your override is in effect; retrying with current portfolio state" so the trader understands the override is not in question.

**RME-R2. Equity-base read during a LADS-sustained failure.** REQ-PORT-021a suspends new entry intent creation platform-wide if three consecutive LADS cycles abort. Good. But the Phase 1 modal (REQ-ORDER-007) reads current equity state at modal-open time; if a LADS-sustained failure occurred *after* modal-open but before click, the user can sign and submit a payload against equity state that is no longer reliable. *Smallest change*: require the signed-payload endpoint (REQ-ORDER-009b) to re-validate platform-wide LADS health at signing time and refuse to sign if a sustained-failure state is active. This adds one sys_config check to the signing path; no new infrastructure.

### 3.2 Flexibility

The rule coverage — per-trade risk cap, per-position stop, trailing stop (percentage and ATR), break-even, time stop, swing-low, volatility-based sizing, max daily/weekly/monthly loss, max open positions, max concentration per sector, portfolio heat, drawdown thresholds, pyramiding with never-lowers-stop invariant (REQ-PYR-011), and staged entries/exits — is genuinely complete for an NSE long-only retail trader. One missing rule:

**RME-F1. Correlation-aware exposure is deferred to REQ-NEXT-006.** This is a defensible Phase A choice; REQ-RME-017 uses sector (Industry) as the V1 correlation proxy. The gap is that **the proxy is weak for NSE where industries like "Banking" and "Finance" (both real NSE Industry classifications) are highly correlated during risk-off episodes.** A user concentrated across these two industries hits no cross-industry cap today. *Smallest change*: add a configurable "correlated-industry groups" map in `sys_config` (e.g., `risk.correlated_industry_groups`) that treats specified industry pairs as a single sector for concentration-limit purposes. Seed with the obvious pairs (Banking+Finance, Metals+Metal Products, Oil+Gas). Admin can update the map as sector correlation evolves. This doesn't require statistical correlation modelling — just a grouping table.

### 3.3 Backtestability

REQ-NFR-017 (nightly BTE-vs-live RME parity on a fixed synthetic fixture) is a strong guarantee. REQ-RME-022 (dynamic trigger recalibration) applies identically to live and backtest. The one new gap:

**RME-B1. Signal Subscription version pinning in live RME vs backtest.** REQ-STRAT-017b says the Signal Subscription RME configuration is versioned copy-on-write; positions reference the version they were created under for the whole lifecycle. REQ-STRAT-028 says entry signals carry the contributing Signal Subscription version IDs as provenance. But when a backtest is launched from the Signal Builder for an already-deployed Subscription, it's unclear whether the backtest uses the *current live version* or the version at the time the entry signals in the backtest data were generated. Both are defensible; the spec is silent. *Smallest change*: require the backtest-launch UI to default to the current live version and offer an explicit "backtest against historical version N" toggle for reproducibility testing. Store the chosen version ID on the backtest run record.

### 3.4 Lifecycle coverage (pre-trade, in-trade, post-trade)

The lifecycle states (PendingEntry → Open → Suspended → Closed/Rejected) and the advisory flags model (REQ-PLC-002) are clean. REQ-PLC-011 (exit_reason + priority rank on terminal positions) closes the prior post-trade auditability gap. Two new gaps here:

**RME-L1. Suspended-state channel leak risk.** REQ-RME-CONC-005(c) says "channels for positions that are in Open or Suspended state but have no enqueued events must remain live in the registry until those positions close; they must not be garbage-collected based on idle time alone." For Phase A (≤150 open positions) this is fine. But if ADMIN- or CORPORATE_ACTION-sourced Suspended positions accumulate (e.g., a long-running corporate action re-anchor queue), each holds a permanent background task in the Worker. Over months this could produce hundreds of idle channels. *Smallest change*: add a `channel.lifecycle.phase_a_max_active_channels` sys_config gauge (no enforcement, observability only) and an admin System Health warning at 80% of the validated Phase A ceiling. The admin then has the trigger to resolve or archive stale Suspended positions before the worker restart surfaces the leak.

**RME-L2. Frozen-with-visibility admin resolution runbook missing.** REQ-RME-CONC-007 describes the OCC-exhaustion freeze path but references a runbook "that document[s] the admin resolution procedure, including how to verify position document consistency before clearing the incident." The runbook catalog (`docs/operations/runbooks/README.md`) does not list this runbook. Without it, the first time this fires in production, the admin will be debugging an RME concurrency fault at the moment it most needs to be deterministic. *Smallest change*: add this runbook to the catalog and mark it Phase A mandatory (promote from its current implicit Phase B classification). Write the stub before Phase 6 code is committed.

### 3.5 Transparency

REQ-RMET-004 (persist reason each signal allowed/blocked/downsized) and REQ-SIZING-009 (all sizing suggestions explainable) are the right transparency primitives. REQ-STRAT-028 added the provenance fields for entry signals. The remaining gap is backtest-specific:

**RME-T1. Backtest starting equity displayed but not labeled.** See CG-9. The backtest result UI will show an equity curve that says "starting equity: ₹X lakh" where X is today's value, but the trader reading the 2022-year-end figure has no way to know the equity curve is a scaled synthetic and not a projection of what would have happened on their actual account.

### 3.6 Advisory-only enforcement

REQ-BOUNDARY-004 + REQ-RME-011 + REQ-ORDER-006 + REQ-ORDER-010 together enforce the advisory-only invariant well. The REQ-DRDN-003 clarification (platform-enforced restrictions vs user-advisory notifications) is an important distinction that was correctly pinned in the prior review. One remaining concern:

**RME-A1. "Block new trade signal recommendations" at 20% drawdown (REQ-DRDN-003 category a) is algorithmic enforcement but uses the term "block" in a way a reasonable reader could interpret as autonomous action.** The enforcement is: the RME does not surface the recommendation and the Phase 1 modal rejects a manually-initiated entry for the symbol. The user is still free to log into FYERS directly and place the order. This is consistent with REQ-BOUNDARY-004 but the word "block" in the requirement text is load-bearing and easy to misread. *Smallest change*: rename the REQ-DRDN-003 enforcement language from "block" to "suppress platform advisory and reject in the Phase 1 modal" so there is no chance an implementer or a user confuses this with an order-level block.

## 4. Architectural Findings

**A-8. Phase 0 roadmap has drifted into pre-product SRE.** Phase 0 now requires: repo scaffolding + linting + CI/CD + MongoDB / SQL Server / Redis + Worker Service three-layer singleton enforcement (IaC + pipeline gate + Redis lease) + sys_config seeder console app + sentinel-row startup check + OTLP collector + Serilog redaction policy + Azure App Configuration + Key Vault + LKG cache + structured logging + health checks. For a single-developer team targeting 30 Phase A testers, most of this is right *eventually* but is heavier than needed *now*. The 2026-04-20 review resolution already marked the three-layer singleton as "frozen scaffolding until Phase C"; extend this framing to the other Phase 0 items. *Smallest change*: add a section header in `docs/implementation-roadmap.md` Phase 0 labelled "One-time scaffolding (author once, freeze until phase gate)" covering: the three-layer singleton (already done), the sys_config seeder + sentinel-row check, the LKG cache wiring, and the OTLP saturation policy. The list makes explicit that these are not ongoing engineering work and should not be revisited during the Phase 1–7 build.

**A-9. Modular monolith + per-app repo layout + shared packages is correct.** The `apps/{web,api,worker}` + `packages/{shared-types,ui,config,testing}` + `infra/{docker,azure}` split in `docs/repo-structure.md` is appropriate for the developer profile and phase. No change.

**A-10. MDP abstraction integrity — verify adapter test harness enforces the boundary.** CLAUDE.md, REQ-MARKET-002, and ADR-0005 make clear that the MDP abstraction must hide provider specifics. But there is no requirement that a contract-test suite exercises the MDP interface against *both* a FYERS adapter and a stub "alternate provider" adapter to prove the boundary holds. Engineering-standards names contract tests for each concrete provider but not cross-provider-swap tests. *Smallest change*: add a requirement that before Phase B, a smoke test swaps the active `market_data.provider.active` from `fyers` to a stub TrueData adapter that returns canned OHLCV and asserts that DataSync, EODSR, and the chart layer continue to function without code changes. This is one integration test; it validates the abstraction's promise.

**A-11. REQ-PORT-031b fencing token covers writes only; reader-side snapshot-consistent reads don't participate.** REQ-PORT-031b introduces a fencing token on the per-user ledger-write path to guard against Redis lock-key eviction. The fencing token gates writes: any MongoDB write whose stored fence token has advanced past the holder's is rejected as a stale-write abort. But the reader-side snapshot-consistent read protocol (REQ-RME-006d) uses `ledger_snapshot_version` alone, with no fencing-token participation. If a Redis eviction causes an evicted-lock writer to commit a stale write that incorrectly advances `ledger_snapshot_version` before the fencing-token check rejects the rest of the writer's work, a reader sampling `ledger_snapshot_version` during that window can observe the advance and conclude its snapshot is consistent when in fact the writer's work is about to be torn down. The window is narrow and the REQ-PORT-031a invariants pin ledger_snapshot_version increment to *after* durable commit, so in practice this race is closed — but the wording in REQ-PORT-031b does not explicitly call out that the fencing-token abort path must not have already advanced `ledger_snapshot_version`. *Smallest change*: add one sentence to REQ-PORT-031b specifying that a fencing-token abort must roll back (or never increment) the `ledger_snapshot_version`. This closes the last corner of the reader-writer ordering story.

**A-12. Single-instance Worker + MongoDB replica-set failover produces a sustained LADS abort window.** REQ-PORT-021a handles this explicitly (graduated suspension on ≥3 consecutive LADS aborts for MongoDB reasons). Good. But the same failover window affects every Worker-side MongoDB write: intent-ledger updates, RME channel consumer writes, notification writes. During a 10–30 second MongoDB failover the Worker may drop events entirely (channel consumer sees write errors and the OCC retry spins). REQ-PORT-021a mentions this obliquely but doesn't pin behaviour for non-LADS paths. *Smallest change*: add a requirement that all Worker-side MongoDB writes use the standard MongoDB driver retry semantics (`retryWrites: true`, which the driver applies by default) and that the RME channel consumer treats driver-level retry exhaustion as a third-consecutive-retry equivalent — triggering the same admin advisory path as REQ-PORT-021a. This is one line in the engineering-standards doc, not a code change.

**A-13. Per-symbol SQL Server table pattern + EODSR iteration cost.** EODSR must evaluate all active non-excluded symbols against every active Signal Subscription per REQ-STRAT-013. With 500 symbols, 30 users, and 5 Subscriptions per user on average, the naive implementation reads 500 × 150 = 75,000 historical-data slices per EOD run. REQ-STRAT-013a clarifies that a single shared market-data read pass may be used for efficiency, but doesn't mandate it. *Smallest change*: pin "single-pass read" as the required implementation pattern in REQ-STRAT-013a — 500 symbols × 1 daily-candle-range read per EOD run, cached in Worker memory during the run, with each Subscription evaluated against the cached data. Otherwise a naive implementer will produce an EODSR that runs for 20+ minutes and degrades the overall EOD pipeline timing.

**A-14. Worker Service schedule section is good but silent on pre-market maintenance.** The Worker Service Schedule section in system-architecture.md covers pre-session setup, market hours, post-market EOD pipeline, and weekends. It does not name a "maintenance window" — the time outside market hours when operator actions (Universe Sync, HistoricDataSeed, sys_config changes) can safely run without interfering with scheduled jobs. *Smallest change*: add a one-paragraph "Maintenance window" subsection stating that admin-triggered operations are available at any time but have preferred windows (pre-market 07:00–08:30 IST for Universe Sync; post-EODSR 20:00+ IST for large HDS seeds). Informational; no new functionality.

## 5. Security Findings

**S-9. Admin MFA claim validation is under-specified for the three OAuth providers.** REQ-BCP-009 requires admin sign-in to carry an `amr` (or equivalent) claim indicating MFA was used. The three supported providers (Google, Microsoft, Facebook/Meta) emit this claim differently: Google's `hd` + `amr` follows OAuth 2.0 conventions; Microsoft (Entra ID) emits `amr` with values like `pwd`, `rsa`, `mfa`; Facebook/Meta does not expose MFA state in its standard OAuth response at all in the same way. The requirement assumes all three providers expose the claim, which is false for Facebook. *Smallest change*: state in REQ-BCP-009 that only Google and Microsoft may be the admin's bound OAuth provider (not Facebook/Meta) because Facebook's OAuth response does not reliably expose MFA state. Regular users may continue to use any of the three providers. Add one sentence and tighten the admin-bootstrap validation accordingly.

**S-10. Admin equity-base-override divergence has no security monitoring.** REQ-RME-006c permits manual equity override and requires a staleness warning after 30 days. But the override itself is a per-user value that can dramatically inflate the RME's sizing denominator — a malicious user (in a later phase where there are more than a handful) could set an override to 10× their real equity and use the platform to size far larger positions than their real capital supports. They'd still have to fund the trade at FYERS, but the platform's "your risk per trade is 0.5%" math would be operating against a 10× inflated denominator. *Smallest change*: cap the override at `min(FYERS_total_account_value × 1.5, FYERS_total_account_value + ₹10 lakh)` so the override can compensate for non-Nifty 500 holdings but cannot materially exceed the user's real FYERS account value. Also add an admin-visible notification (`user_equity_override_unusual`) if any user's override exceeds their FYERS total by more than 50%.

**S-11. Signed-payload nonce replay during tab-background** — on the edge. REQ-ORDER-009c already pins nonce single-use + 300s TTL. The remaining edge case: a user opens the Phase 1 modal, backgrounds the tab for 200 seconds, returns, clicks confirm. The nonce hasn't expired, but the modal's displayed quote and the underlying market have. The trader submits against a stale payload that is cryptographically valid. This is not a *security* issue (the payload is the user's own signed intent) but it is a trader-experience one. *Smallest change*: add a visibility-change listener in the portal that, on tab refocus, refreshes the signed payload and updates the modal. One frontend addition; no spec change needed beyond documenting it.

**S-12. Widget SDK URL pinning has no integrity check.** System-architecture's FYERS API Connect Branded Button Contract says the SDK URL is "pinned in platform configuration" and "a change-detection step in the deployment pipeline triggers re-execution of the contract test suite before any release that picks up a new SDK revision." This is a *URL* pin, not an *integrity* pin. If the SDK is ever replaced at the FYERS-hosted URL (maliciously or accidentally) between deployments, the platform picks up the new version with no detection. *Smallest change*: require the deployment pipeline to fetch the current SDK content, compute its hash, and compare against a committed expected-hash value (`integrations.fyers.api_connect_sdk_expected_hash`); if it differs, fail the build and require contract-test re-run. This is standard SRI-style pinning applied to a build-time check. One config key, one pipeline step.

**S-13. `payload_signature` retention vs key rotation.** REQ-ORDER-014b retains `payload_signature` on the `intent_ledger` record for audit. When the HMAC signing key is rotated (REQ-BCP-008), old signatures become un-verifiable against the current key. This is correct (rotation should invalidate old signatures for signing-new-things), but the audit trail loses the ability to re-verify historical intents. *Smallest change*: either (a) require the old HMAC key to be retained in Key Vault under a versioned secret for audit-verification purposes only (Azure Key Vault already supports this pattern), or (b) document that post-rotation, old signatures are not re-verifiable and rely on the immutability invariant (REQ-ORDER-014b) as the integrity guarantee. Pick one; document it.

## 6. Trader-Experience Findings

**T-8. No fast-exit affordance for panic-close scenarios.** The standard exit flow is chart-page → Phase 1 modal → FYERS widget → widget pop-up → user confirms → submit. For an advisory-only platform this chain is correct, but for a trader facing a gap-down or an emergency exit scenario, five clicks is four too many. REQ-STOP-008 says the exit action is accessible from the chart page at any time (advisory or not), which is correct, but doesn't specifically offer a "one-click exit" affordance. *Smallest change*: require the positions summary page row to include a persistent "Exit position" action button that opens the Phase 1 modal pre-populated with full-exit quantity at market order type. The flow still goes through the modal and widget (advisory-only invariant preserved), but the number of clicks to initiate is one. One UI change; no spec change to the execution model.

**T-9. Position freshness indicator is per-symbol but not per-portfolio.** REQ-DASH-013 requires a data-freshness timestamp on the dashboard. Good. REQ-STOP-006c requires a per-position delay indicator when quotes are delayed. Good. But during a LADS-sustained-failure or provider-unavailable window, a trader looking at a portfolio with 10 positions sees 10 per-position indicators, each saying different things. There's no single "the portfolio state you're looking at is X minutes stale" indicator. *Smallest change*: require a portfolio-level freshness indicator on the dashboard health strip (REQ-DASH-012) showing the age of the oldest position-data component in the visible portfolio. Single roll-up number, visible at a glance.

**T-10. Notification feed has no unread-count delineation by severity.** REQ-NOTIFY-014 requires a feed indicator with unread count. In practice, the notification types range from noise-level (`add_advisory`, `reduce_advisory`) to critical (`stop_breach`, `market_halt_active`). A trader seeing "17 unread" in the corner doesn't know if 17 are add advisories or 1 stop-breach + 16 add advisories. *Smallest change*: require the unread indicator to show two numbers — critical-unread-count and total-unread-count — with critical defined as the non-suppressible set in REQ-PROFILE-006. Single UI change; no backend change needed.

**T-11. Telegram message content for exit advisories not pinned to a template.** REQ-NOTIFY-024 pinned the entry-fill notification template (which was a CG from the prior review). The exit advisory notification (REQ-NOTIFY-006 `exit_alert` type) has no corresponding template. Two implementers will produce divergent formats. *Smallest change*: pin the exit-advisory Telegram template fields in the same way REQ-NOTIFY-024 pinned entry-fill: symbol, exit reason (human-readable + priority rank), current price, distance to stop, open quantity, realized-PnL-if-exited, chart deep link. One REQ addition.

**T-12. Pending-entry chip on chart (REQ-CHART-004a) doesn't show signal provenance.** REQ-CHART-004a requires a chip showing action type, elapsed time, and "Awaiting FYERS confirmation." For multiple simultaneous signals from different Signal Subscriptions, the chip doesn't identify *which* subscription produced the pending entry. REQ-STRAT-028 added provenance to entry signals. The chart chip should surface it. *Smallest change*: extend REQ-CHART-004a to require the chip to show the originating Signal Subscription name (and "Manual" if the intent was not signal-driven). This is a display-only change; the data is already in the intent_ledger/entry_signals record.

**T-13. Watchlist/chart signal-parity approach choice is deferred to engineering-standards but not pinned.** REQ-WATCH-002a offers two compliant approaches (shared cache key vs per-surface timestamps) and says the choice "must be recorded as a note in `docs/engineering-standards.md` under the caching conventions section." The engineering-standards doc does not currently have such a section. *Smallest change*: pick approach (a) — shared cache key on `ledger_snapshot_version` — and document it in engineering-standards now, before Phase 7. Approach (b) is a fallback that adds two visible "as of" indicators that traders will eventually find confusing; (a) is the cleaner choice.

## 7. Non-Functional Gaps That Actually Matter

**N-6. Phase B load-test target users (20) is below Phase A user ceiling (30).** Engineering-standards' load-test target is 20 concurrent users. REQ-LEGAL-003 sets the Phase A tester ceiling default at 30 (and allows up to 50). The Phase B gate test is sized lower than the Phase A active production cap. Even if 20 concurrent is realistic at any one moment, the test should validate the configured ceiling. *Smallest change*: change the load-test target in engineering-standards to 30 concurrent users to match the Phase A default ceiling, and require the test to run at the *current* `operations.phase_a.tester_ceiling` value at the time the test is executed rather than a hard-coded 20.

**N-7. RME contract test coverage of state transitions is mandated but the specific transition list is not in the spec.** Engineering-standards requires "at least one contract test per documented state-transition (PendingEntry → Open → Suspended → Closed/Rejected and all sub-paths)." But the documented state-transition list lives implicitly across REQ-PLC-002, -003, -005a, -007, -008, -009, -010, REQ-ADMIN-001a, -007, -010, -013, REQ-STRAT-007a, etc. An implementer can comply with the letter of "at least one per documented transition" without exercising all real-world transitions. *Smallest change*: produce an authoritative transition matrix as a sub-section of REQ-PLC-002 listing every (from-state, event, to-state, source, reason-code) tuple. The contract-test floor is then explicit. This is a one-page table and is the kind of artefact you want before Phase 6 starts coding the state machine, not after.

**N-8. SLO breach observability is named but the alert-routing is not.** REQ-SLO-008 says SLO breaches must be observable via OTLP as dedicated metrics. Good. But there is no requirement that the SLO-breach metrics route to Telegram or email when they fire. Without a routing rule, the metrics will sit in the observability backend and only an operator who opens Grafana will know. *Smallest change*: add a requirement that critical SLO breaches (REQ-SLO-009 RME event processing > p95 5s, REQ-SLO-010 stop-detection-to-notification > p95 15s) emit a one-time admin Telegram + email notification on first breach per session, with a 1-hour cooldown to prevent spam. One sys_config key (cooldown duration), one alert routing rule.

## 8. Logical Inconsistencies

**L-6. `risk.time_stop.default_sessions` default is 10 in system-config.md but REQ-STOP-003 doesn't pin a default for the Time Stop session count.** REQ-STOP-003 says the count is configurable per Signal Subscription. The seed table in system-config.md has `risk.time_stop.default_sessions = 10`. But the requirement doesn't explicitly reference this seed key as the default for new Signal Subscriptions. An implementer reading REQ-STRAT-016/017 won't know to pull from this sys_config key. *Smallest change*: add one line to REQ-STOP-003 stating "the default session count for new Signal Subscriptions is `sys_config.risk.time_stop.default_sessions`" so the reference is explicit.

**L-7. `REQ-CHART-005a` (chart navigation to archived symbol) and `REQ-WATCH-001` (archived symbol stays on watchlist with red indicator) are internally consistent, but both behave differently from `REQ-CHART-013` (search bar excludes archived).** A trader who has an archived symbol on their watchlist clicks through to the chart, sees the red archived indicator, and wants to add an alternate symbol via the chart's search bar — but can't search for it if the alternate is also archived. The behaviour split (existing access OK, new addition blocked) is defensible but not consistent across surfaces (search is hard-blocked; navigation is permitted). *Smallest change*: document this choice as deliberate in REQ-CHART-013 with a one-line rationale ("search add-flow excludes archived symbols to prevent accidental new exposure to delisted names; existing access via watchlist or deep link remains supported per REQ-WATCH-001 and REQ-CHART-005a"). One sentence.

**L-8. `REQ-DRDN-002` advises but `REQ-DRDN-003` enforces; both share the `risk.drawdown.*` namespace.** The system-config keys for daily/weekly/monthly loss limits (advisory) and for the six graduated thresholds (some advisory, some enforced) are all under `risk.drawdown.*`. They serve different enforcement semantics. An admin editing a `risk.drawdown.*` key has no clear way to know whether the change is advisory-only or enforcement-changing. *Smallest change*: rename the seed keys to `risk.drawdown_advisory.*` and `risk.drawdown_enforcement.*` (or add a `category_subgroup` field to the seed-table view) so the admin UI surfaces the distinction. One naming change; existing code doesn't exist yet.

## 9. Underspecified Areas

**U-7. Per-symbol lot-size data is not modelled.** REQ-SIZING-010 and REQ-EXEC-004 require quantity rounding to NSE/FYERS minimum quantities. Most Nifty 500 stocks trade at lot size 1 in equity (CNC), so the requirement is satisfied trivially today. But NSE occasionally introduces stocks with non-1 lot sizes (mostly futures, occasionally equity for high-priced shares). The platform's symbol master has no `lot_size` field; the symbol_master schema in `docs/data-management.md` does not include it. *Smallest change*: add `lot_size: integer (default 1)` to the symbol master schema and the CSV import path. The CSV doesn't currently provide it; the admin must edit it manually for the rare exceptions.

**U-8. `manual_adjustments` write path is not explicitly listed under REQ-PORT-031 lock acquirers.** REQ-PORT-031 lists the write paths that must acquire the per-user trade-ledger lock: LADS intraday polling, on-login sync, EOD sync, manual sync, admin rebuild, single-symbol backfill. Manual adjustments (REQ-PORT-014/015 / REQ-RECON-003/004) are not listed. They modify the FIFO state and the trade ledger semantics, so they must be lock-protected. *Smallest change*: add manual-adjustment write paths to the REQ-PORT-031 acquirer list with blocking-wait semantics (admin-initiated, similar to admin rebuild).

**U-9. RME profile optimisation runs and FYERS budget interaction.** REQ-RME-020/021 and REQ-RME-020a/b/c describe the optimisation workflow. REQ-RATE-011 budgets DataSync, HDS, EODSR-market-reads, LMDS, and admin misc — but does not budget RME profile optimisation runs, which read SQL Server (no FYERS calls) and are therefore correctly excluded from the FYERS budget. The gap is on the *SQL Server* side: a heavy optimisation run with multi-timeframe + walk-forward folds × Composite Score components × Robustness Factor calculations will pin SQL Server reads for the duration. The spec doesn't specify a concurrency cap. REQ-SLO-007 caps backtests at 5 platform-wide and 1 per user — does this apply to optimisation runs too? *Smallest change*: state explicitly in REQ-RME-020 that optimisation runs share the REQ-SLO-007 cap (5 platform-wide / 1 per user, queued with visible position). One sentence.

**U-10. Phase 1 modal during a market halt (REQ-HALT-005) does not specify behaviour for in-progress modals.** REQ-HALT-005 covers display of the halt warning when the modal is opened during an active halt. It does not specify what happens to a modal that was already open when a halt is detected — does the warning auto-appear, does the modal close, does the signed payload remain valid? *Smallest change*: pin that an in-progress modal must auto-display the halt warning (server-pushed via WebSocket per REQ-NFR-013) and may continue to be submitted at the user's discretion. Closing the modal automatically would surprise the user; not warning them would mislead them.

## 10. Edge Cases and Failure Modes Not Addressed

**EC-1. FYERS daily token expires mid-EODSR run.** REQ-NOTIFY-022/022b cover proactive token-validity checks. REQ-MARKET-005 covers the loud-failure path on stale token at job startup. The middle case — token was valid when EODSR started but expired during the run — is not covered. EODSR doesn't directly use the admin FYERS token (it reads SQL Server), so for EODSR specifically this is moot. But for DataSync running its 10-session recovery, mid-run expiry is real. *Smallest change*: pin that DataSync must re-check admin token validity at every batch boundary and gracefully exit with `partial_completion_token_expired` outcome rather than fail randomly mid-batch.

**EC-2. Single-stock circuit lock for a position with active stop advisory.** Pinned by REQ-PLC-004 circuit-limit fields and REQ-STOP-011, but the operational consequence — LMDS receives no ticks, so stop monitoring on that position is effectively suspended — is correctly named in REQ-STOP-006b. The remaining case is what happens at session close when the stock unlocks: REQ-HALT-004 covers market-wide halt clear, but the symbol-level circuit clear is silent. Does the LMDS resume normally and re-evaluate against the current price? Does the RME process queued events? *Smallest change*: add to REQ-PLC-004 that on circuit-clear (LMDS observes the symbol exiting the circuit limit band), the RME re-evaluates all active price levels for the position against the first post-clear price tick, equivalent to the post-halt-clear behaviour in REQ-HALT-004.

**EC-3. User changes their FYERS account while a position is Open.** A user could (in theory) re-bind their FYERS account to a different brokerage account with different holdings. Today's spec assumes one user → one FYERS account → one stable broker identity. If a user does change accounts, every Open position references the prior holdings, and the FYERS-driven account sync (REQ-PORT-018, on-login sync) will produce massive mismatches. The reconciliation flow (REQ-RECON-001..008) assumes the broker is the same; it would surface massive deltas as if a CA happened on every position. *Smallest change*: state that re-binding to a different FYERS account is not supported by the platform; the user must close all positions through the original account first. If FYERS does permit this (the spec is unclear), require a hard block. Phase A acceptable risk; document it.

**EC-4. EODSR fails after partial signal generation but DataSync succeeded.** REQ-STRAT-027 requires atomic-run semantics: either the full universe is evaluated or no entry signals are emitted. Good. The edge case is when EODSR retries are exhausted and the run is marked `failed_for_review`. The recovery path is "admin-triggered manual retry per REQ-MARKET-008." But the manual retry is a fresh run; it doesn't pick up where the failed run left off. For a 500-symbol universe with intermittent SQL Server contention, this means the operator may do several full re-runs to get a clean session. *Smallest change*: not really a defect — atomic-run is the right semantic — but flag in the operations runbook that manual retries are full re-runs, not resumes. Operator expectation-setting only.

**EC-5. User opens multiple Phase 1 modals across different tabs for different symbols simultaneously.** REQ-ORDER-005 prevents duplicate in-flight orders for the same symbol/action. It does not prevent multiple in-flight orders for *different* symbols. A user with 10 entry signals could open 10 modals across 10 tabs, sign 10 payloads, and submit 10 orders before any LADS cycle catches up. Each individual order is correctly intent-logged; the cumulative portfolio impact is not pre-validated. By the time LADS processes, the user may be substantially over portfolio heat. *Smallest change*: at signed-payload time (REQ-ORDER-009b), include the count of pending intents for the user in the signing decision; if pending intents would together push portfolio heat above the configured maximum, refuse to sign with a clear "you have N pending orders that, if filled, would breach your portfolio heat limit" message. One additional check; small payload field.

**EC-6. Signal Subscription versioning during an EODSR-in-progress save.** REQ-STRAT-017b solves the race using copy-on-write with `effective_from = next EOD run`. Good for the steady-state case. The edge case: what if the admin saves a Signal Subscription change *during* an EODSR run? The new version's effective_from is "the start of the next scheduled EODSR" but an in-flight run is currently writing entry signals against the old version. The spec says the in-flight run "always completes under the version it started with" — correct. But what if the user pauses/resumes the Subscription via REQ-STRAT-007a during the run? Pause is not a versioned change; it's a state change. *Smallest change*: pin that pause/resume during an in-flight EODSR run does not affect the run; the run continues as scheduled. One sentence in REQ-STRAT-007a.

**EC-7. Telegram bot rate limit (~30 messages/sec per bot).** Not addressed anywhere. On a market-wide gap-down day with 30 users each having 5+ open positions hit by stop breaches, the platform will emit 150+ Telegram messages in a few minutes. Telegram's bot API will throttle. Without local backoff awareness, the Notification Delivery Job will hammer the API and produce delivery failures. *Smallest change*: require the NDJ to implement Telegram-side rate-limit awareness (read the `Retry-After` header on 429 responses and back off accordingly). REQ-NOTIFY-008 mentions exponential back-off but doesn't pin the Retry-After header. One sentence in REQ-NOTIFY-008.

**EC-8. OAuth provider refresh token revocation while a session is active.** REQ-AUTH-013 says the platform terminates the session on a token-revocation response. Good. But the platform's session lifetime is 24 hours (REQ-SESSION-001) and the platform doesn't *refresh* the OAuth token mid-session — it keeps the user signed in via its own session record. Provider revocation only matters when the platform next attempts a refresh, which the spec implies happens at "configured schedule or sensitive action." Without a periodic refresh, a revocation can persist undetected for up to 24 hours. *Smallest change*: pin a periodic refresh interval (e.g., every 4 hours during an active session) so revocation is caught within hours, not days. One sys_config key.

## 11. Over-Engineering Risks

The 2026-04-20 review flagged three over-engineering risks. Two are now correctly framed in the implementation-roadmap as Phase-deferred or one-time-author-and-freeze. One additional area emerged in this pass:

**O-4. Composite Score with Robustness Factor multi-timeframe walk-forward optimisation grid is appropriate for a hedge fund, heavy for a single-trader Phase A platform.** REQ-RME-020a + 020b + 020c describe a profile-optimisation engine that ranks configurations by a 9-component weighted Composite Score multiplied by a 3-factor Robustness Factor across multiple timeframes with walk-forward folds. This is a genuinely well-designed quantitative framework, and it is appropriate for the platform's eventual purpose. For Phase A, a single trader testing the platform on their own portfolio will likely be served by a much simpler "rank by expectancy in R, with at least 10 trades and max drawdown under 25%" filter. The full Composite + Robustness machinery will be expensive to test end-to-end and is frontloaded ahead of any user-research that confirms which components actually drive the trader's choice. *Smallest change*: do not remove the requirement, but add a Phase-A-only "simple ranker" mode (`sys_config.rme.optimisation.ranker_mode`, values `simple` (Phase A default) or `composite_robust`) that skips the Robustness Factor and the multi-timeframe combination evaluation, returning ranked configurations by Expectancy in R with the existing `min_trades_for_valid_result` floor. Keeps the full engine in the codebase, defers the UI complexity until Phase B+. This is a documentation change to REQ-RME-020 + a new sys_config seed key.

**O-5. Equity-curve-based sizing (REQ-DRDN-006) is configurable-but-disabled by default; the build cost is high.** REQ-DRDN-006 specifies that sizing must reduce on a declining equity curve, with a configurable lookback (`risk.equity_curve_sizing.lookback_sessions`, default 20). The feature is gated by `risk.equity_curve_sizing.enabled` (default false). For Phase A with a single trader who has no equity curve history yet, this feature will sit disabled for months. The implementation cost (read equity_curve, compute trend, modulate sizing, audit the modulation) is non-trivial. *Smallest change*: defer the implementation to Phase B explicitly in the roadmap. The spec keeps the requirement; the roadmap acknowledges it as Phase B work, not a Phase 6 deliverable. This is a one-line edit to `docs/implementation-roadmap.md` Phase 6.

**O-6. RME profile optimisation result staleness indicator (REQ-RME-021) is correctly specified but the data-staleness detection is intricate.** REQ-RME-021 says optimisation results carry a staleness indicator if the underlying historical data or scan parameters have changed. REQ-STRAT-026 adds the `code_version` comparison. Combined, the staleness check has to consider: (a) any new candles in SQL Server for the symbol since the run, (b) any change in Signal Subscription parameter set since the run, (c) any change in the Signal type's `code_version` since the run. Fine at design level; expensive to wire up correctly across three different triggers. *Smallest change*: pin the staleness check as a single computed field at the time the result is read, rather than a watcher across three independent change sources. One paragraph in REQ-RME-021.

The two items the prior review correctly identified as **not** over-engineering remain not over-engineering: REQ-PORT-031 fencing tokens and the OCC `_version` model are both correctness-essential.
