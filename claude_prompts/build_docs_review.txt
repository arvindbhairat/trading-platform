You are acting as a senior architect, trading systems expert, security engineer, and financial compliance auditor.

Your task is to critically review the provided build/requirements document for a stock trading platform BEFORE implementation. Do NOT write code.

The system uses:

* Backend: C# / .NET Core
* Frontend: Node.js / TypeScript
* Databases: SQL Server (relational) + MongoDB (document/event storage)
* Cloud: Microsoft Azure

The platform supports equity trading with risk management features (e.g., position sizing, trailing stops, pyramiding).

---

## Objectives

1. Identify gaps, risks, and ambiguities in requirements
2. Ensure readiness for real-money trading scenarios
3. Validate architecture against performance, consistency, and regulatory expectations
4. Prevent costly redesigns due to poor early decisions

---

## Review Dimensions (MANDATORY — do not skip any)

### 1. Trading Domain Logic (CRITICAL)

* Order types: market, limit, stop-loss, trailing stop, bracket orders — are all clearly defined?
* Order lifecycle: creation → validation → execution → partial fills → cancellation → rejection
* Handling of slippage, gaps, and market volatility
* Pyramiding logic and risk limits enforcement
* Position tracking accuracy (real-time vs eventual consistency)
* Corporate actions (splits, dividends) handling
* Market hours, holidays, and timezone correctness

---

### 2. Functional Completeness

* Missing user journeys (order placement, modification, exit scenarios)
* Edge cases (network failure during order placement, duplicate orders)
* Failure handling (broker rejection, API downtime)

---

### 3. Non-Functional Requirements

* Latency targets for order placement and execution
* Throughput expectations under peak market hours
* Scalability (horizontal scaling in Azure)
* Reliability (retry strategies, circuit breakers)
* Availability (multi-region? failover?)

---

### 4. Data Architecture (SQL Server + MongoDB)

* Clear separation of responsibilities:

  * SQL Server → transactional integrity (orders, positions, accounts)
  * MongoDB → logs, events, market data, audit trails
* Consistency model (strong vs eventual consistency)
* Idempotency in order processing
* Handling duplicate or replayed events
* Data reconciliation strategy (broker vs internal system)
* Historical data storage and querying strategy

---

### 5. Security (ZERO TOLERANCE AREA)

* Authentication (OAuth2/JWT?) and session management
* Authorization (role-based vs attribute-based)
* Protection against:

  * Order tampering
  * Replay attacks
  * API abuse / rate limiting
* Encryption:

  * In transit (TLS)
  * At rest (Azure-managed keys or custom key vault)
* Secrets management (Azure Key Vault)
* Protection of trading logic from manipulation
* Secure handling of financial and personal data

---

### 6. Financial Compliance & Regulatory Readiness

* Applicability of:

  * Financial Conduct Authority (if UK exposure)
  * Securities and Exchange Board of India (for India)
* Audit trails for every action (orders, modifications, logins)
* Data retention policies
* User consent and data privacy (GDPR if applicable)
* Trade reconstruction capability
* Prevention of market abuse patterns (basic safeguards)

---

### 7. API & Broker Integration

* Broker API reliability assumptions
* Timeout, retry, and fallback strategies
* Idempotent order submission
* Handling partial fills and asynchronous updates
* Webhook/event processing robustness
* Versioning and contract clarity

---

### 8. Architecture & System Design

* Service boundaries (order service, market data service, risk engine)
* Risk engine placement (pre-trade vs post-trade validation)
* Event-driven vs synchronous architecture decisions
* Elimination of single points of failure
* Use of Azure services (Service Bus, Functions, App Services)

---

### 9. DevOps & Azure Deployment

* CI/CD pipelines (Azure DevOps)
* Environment separation (dev, staging, prod)
* Blue-green or canary deployments
* Rollback strategy for failed releases
* Infrastructure as Code (ARM/Bicep/Terraform)

---

### 10. Observability & Operations

* Structured logging (no sensitive data leakage)
* Metrics:

  * Order success/failure rate
  * Latency
  * System health
* Alerting for critical failures (missed orders, delays)
* Incident response readiness

---

### 11. Testing Strategy

* Unit and integration tests for trading logic
* Simulation of market scenarios (high volatility, gaps)
* Backtesting capability (if applicable)
* Security and penetration testing
* Load testing for market open scenarios

---

### 12. Cost & Performance Efficiency

* Azure cost drivers (compute, storage, messaging)
* Market data cost considerations
* Optimization opportunities without sacrificing reliability

---

### 13. UX / Product Risks

* Preventing accidental trades
* Clear display of risk and exposure
* Handling failed or delayed orders from user perspective
